1. Service Decomposition

StrategyHowExample
By business capabilityAlign services to business functionsOrder, Payment, Inventory, Shipping
By subdomain (DDD)Bounded context = one serviceUser identity vs. user preferences
By team (Conway's Law)Service boundaries match team boundariesTeam owns full stack for one service

Rule of thumb: A microservice should be independently deployable. If you have to deploy two services together for one feature, they're probably too coupled — consider merging them or redesigning the API boundary.

4. API Gateway Pattern

// Spring Cloud Gateway configuration @Configuration public class GatewayConfig { @Bean public RouteLocator routes(RouteLocatorBuilder builder) { return builder.routes() .route("order-service", r -> r .path("/api/v1/orders/**") .filters(f -> f .stripPrefix(2) .addRequestHeader("X-Gateway-Auth", "internal") .circuitBreaker(c -> c.setName("orders").setFallbackUri("forward:/fallback")) .requestRateLimiter(r2 -> r2.setRateLimiter(redisRateLimiter())) ) .uri("lb://ORDER-SERVICE") // lb:// = load-balanced via service discovery ) .build(); } }

Gateway responsibilities: authentication/authorization, rate limiting, SSL termination, request routing, load balancing, observability (correlation IDs), request/response transformation, API versioning.

5. Event-Driven Architecture

// Kafka producer — publish domain event @Service public class OrderEventPublisher { private final KafkaTemplate<String, OrderEvent> template; public void publishOrderPlaced(Order order) { var event = new OrderPlacedEvent(order.getId(), order.getItems(), Instant.now()); template.send("order.placed", order.getId().toString(), event) .whenComplete((result, ex) -> { if (ex != null) log.error("Failed to publish order event", ex); }); } } // Kafka consumer — idempotent processing @KafkaListener(topics = "order.placed", groupId = "inventory-service") public void onOrderPlaced(OrderPlacedEvent event, Acknowledgment ack) { try { if (processedEvents.contains(event.getId())) { // idempotency check ack.acknowledge(); return; } inventoryService.reserve(event.getItems()); processedEvents.add(event.getId()); ack.acknowledge(); // manual commit — only after successful processing } catch (InsufficientStockException e) { // publish compensating event or send to DLT (Dead Letter Topic) template.send("order.placed.DLT", event); ack.acknowledge(); } }

6. Saga Pattern — Distributed Transactions

TypeHow it worksBest For
ChoreographyEach service publishes events; others react. No central orchestrator.Simple flows, loose coupling
OrchestrationCentral saga orchestrator calls each service and handles failures.Complex flows, clear visibility
// Orchestration saga — order placement // Step 1: Reserve inventory // Step 2: Charge payment // Step 3: Schedule shipping // Compensating transactions on failure: // If payment fails → release inventory reservation // If shipping fails → refund payment + release inventory public class PlaceOrderSaga { public SagaResult execute(OrderRequest req) { String reservationId = null; String chargeId = null; try { reservationId = inventory.reserve(req.getItems()); chargeId = payment.charge(req.getPayment(), req.getTotal()); String shipmentId = shipping.schedule(req.getAddress()); return SagaResult.success(reservationId, chargeId, shipmentId); } catch (PaymentException e) { if (reservationId != null) inventory.release(reservationId); return SagaResult.failure("Payment failed"); } catch (ShippingException e) { payment.refund(chargeId); inventory.release(reservationId); return SagaResult.failure("Shipping failed"); } } }

8. Interview Q&A

What is the difference between choreography and orchestration in the Saga pattern?
Choreography — each service publishes events and reacts to others' events. No central coordinator. Each service knows what to do when it receives an event and what to publish next.
Pros: loose coupling, no single point of failure, simpler services.
Cons: hard to see the full flow, complex distributed logic, cyclic dependencies possible.

Orchestration — a central saga orchestrator calls each service step by step. It knows the entire workflow and handles compensations on failure.
Pros: centralized visibility, clear business process, easier to debug.
Cons: orchestrator becomes a dependency bottleneck, more coupling.

Choose choreography for simple flows (2–3 steps). Use orchestration for complex, long-running business processes where you need clear visibility and audit trails.
How would you handle eventual consistency in a microservices system?
Design approaches:
1. Accept it — design UX to handle stale data (show "as of X minutes ago", use optimistic UI updates).
2. Compensating transactions — instead of rollback, issue a reverse operation (refund, re-stock).
3. Idempotent consumers — events may be delivered twice; use deduplication (event ID in DB) to process each only once.
4. Sagas — coordinate distributed state changes with explicit compensation logic.
5. CQRS + Event Sourcing — keep write and read models separate; read model is eventually consistent with write model.

Key insight: strong consistency in distributed systems requires synchronous calls (increasing coupling and latency). Eventual consistency is the trade-off for autonomy and resilience.
How do you prevent the "distributed monolith" anti-pattern?
A distributed monolith has microservice deployment but tight coupling — services must be deployed together, or can't function independently. Signs: synchronous call chains across 5+ services per request, shared databases, services that frequently change together.

Prevention:
1. Database per service — no shared DB; each owns its schema
2. API versioning — consumers aren't broken by contract changes
3. Async communication — decouple services in time via events
4. Bounded contexts — services own their domain, no cross-domain joins
5. Consumer-driven contract testing — verify API compatibility without deploying all services
6. Independent deployability test — can you deploy service A without changing B?
