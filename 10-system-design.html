1. CAP Theorem

A distributed system can guarantee at most 2 of the 3 properties simultaneously:

PropertyMeaning
ConsistencyEvery read receives the most recent write or an error
AvailabilityEvery request receives a non-error response (may not be the latest data)
Partition toleranceSystem continues operating even when nodes can't communicate
In practice, network partitions (P) are unavoidable — you must choose between C and A during a partition. CP systems return errors when partitioned (consistent but unavailable); AP systems return stale data (available but inconsistent). PACELC extends CAP: even when no partition (E), choose Latency (L) vs. Consistency (C).
DatabasePostureReason
PostgreSQLCPStrong ACID guarantees; replication lag means eventual consistency
CassandraAP (tunable)Leaderless replication; tunable quorum (ONE/QUORUM/ALL)
DynamoDBAP (default) / CPEventually consistent reads by default; strongly consistent optional
Redis (cluster)APAsync replication; split-brain possible

4. Message Queues

SystemModelThroughputBest For

RabbitMQAMQP, exchanges/queuesThousands/secTask queues, complex routing, RPC
SQSManaged, at-least-onceHigh (with FIFO limits)AWS workloads, simple queuing

Kafka retains messages for a configurable period (default 7 days) — consumers can replay events. RabbitMQ deletes messages after consumption — no replay. Choose Kafka when you need event sourcing, audit trails, or multiple independent consumers of the same stream.

5. Database Sharding

StrategyHowProsCons
Range shardingShard by value range (user_id 0-999 → shard 1)Easy range queriesHot spots if data is skewed
Hash shardingshard = hash(key) % NEven distributionRange queries span all shards; resharding is hard

Geo shardingShard by geographic regionRegulatory compliance, latencyCross-region queries complex
Consistent hashing minimizes data movement when adding/removing shards. A new node takes a portion from a neighbor rather than reshuffling everything. Cassandra, DynamoDB, and Redis Cluster use consistent hashing.

6. High Availability Patterns

  • Load balancing: Round-robin, least connections, IP hash. L4 (TCP) vs L7 (HTTP-aware, sticky sessions).
  • Active-Active: Multiple nodes handle traffic; any node can fail without outage. Requires data synchronization.
  • Active-Passive: Primary handles traffic; standby takes over on failure. Simpler but slower failover.
  • Health checks + auto-healing: Kubernetes readiness/liveness probes, ELB health checks. Replace unhealthy instances automatically.
  • Multi-AZ/Multi-region: Survive datacenter failure. Multi-region adds latency but survives regional outages.
  • Blue-green deployment: Two identical environments; switch traffic instantly. Easy rollback.
  • Canary deployment: Route small % of traffic to new version; increment if healthy.

8. Interview Q&A

Design a URL shortener (bit.ly). Walk through your design.
Requirements: ~100M URLs/day write, 10B reads/day, short URLs unique, must be permanent.

Scale estimates: 1157 writes/sec, 115,740 reads/sec. Read:Write = 100:1.

Core design:
1. Short code generation: hash(long_url) → take 6 chars, or use distributed ID (Snowflake) → base62 encode → 6 chars = 56B combinations. Handle collision with append counter.
2. Storage: {short_code → long_url} in DB. PostgreSQL with index on short_code, or DynamoDB for scale.
3. Read path: Client → CDN → API Gateway → Redis cache (miss → DB → cache-aside) → 301/302 redirect.
4. Caching: 80% traffic to 20% URLs — cache hot URLs in Redis with LRU eviction.
5. 301 vs 302: 301 = permanent (browser caches, reduces server hits), 302 = temporary (allows analytics of every request). Choose 302 for analytics.
6. Analytics: Publish click events to Kafka → stream processor → analytics DB (Clickhouse).
What is the trade-off between SQL and NoSQL databases?
SQL (PostgreSQL, MySQL): ACID transactions, rich query language, joins, schema enforcement, strong consistency. Best for: financial transactions, relational data, complex reporting, data integrity requirements.

NoSQL:
- Key-value (Redis, DynamoDB): O(1) lookups, massive scale, limited query patterns
- Document (MongoDB): Flexible schema, nested documents, good for catalogs/content
- Column-family (Cassandra): Write-heavy, time-series, wide rows
- Graph (Neo4j): Relationship traversal (social networks, recommendations)

Common mistake: choosing NoSQL for scale before exhausting SQL optimization (indexing, read replicas, sharding). PostgreSQL handles hundreds of thousands of writes/sec with proper indexing. Start with SQL; migrate if you hit real limits.
How would you design a notification system to send millions of emails per day?
Architecture:
1. API layer: Accepts notification requests, validates, writes to Kafka topic "notifications.pending"
2. Preference service: Checks user notification preferences (opted out? channel preference?)
3. Templating service: Renders email from template + data, deduplicates by idempotency key
4. Sending service: Consumes from Kafka, calls SES/SendGrid API with retry + exponential backoff
5. Delivery tracking: Webhook from email provider → status DB (delivered/bounced/opened)

Scale considerations:
- Rate limit per provider (SES = 14 emails/sec on sandbox, scales with verified sending)
- Partition Kafka by user_id for per-user ordering guarantees
- Separate priority queues: transactional (order confirmed) vs. marketing (newsletter)
- Dead letter topic for failed sends with alerting
- Idempotency keys prevent duplicate sends on retry
