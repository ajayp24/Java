1. Creational Patterns

CREATIONAL

Singleton (Thread-Safe)

// Best: Enum Singleton (serialization-safe, reflection-safe) public enum AppConfig { INSTANCE; private final Properties props = new Properties(); public String get(String key) { return props.getProperty(key); } } // Alternative: Static inner class (lazy, no sync overhead) public class Singleton { private Singleton() {} private static class Holder { static final Singleton INSTANCE = new Singleton(); } public static Singleton getInstance() { return Holder.INSTANCE; } }

Builder

public class HttpRequest { private final String url; private final String method; private final Map<String, String> headers; private final int timeoutMs; private HttpRequest(Builder b) { this.url = b.url; this.method = b.method; this.headers = Map.copyOf(b.headers); this.timeoutMs = b.timeoutMs; } public static class Builder { private final String url; // required private String method = "GET"; // optional with default private Map<String, String> headers = new HashMap<>(); private int timeoutMs = 5000; public Builder(String url) { this.url = url; } public Builder method(String m) { this.method = m; return this; } public Builder header(String k, String v) { headers.put(k, v); return this; } public Builder timeout(int ms) { this.timeoutMs = ms; return this; } public HttpRequest build() { return new HttpRequest(this); } } } HttpRequest req = new HttpRequest.Builder("https://api.example.com") .method("POST") .header("Authorization", "Bearer token") .timeout(10_000) .build();

Factory Method & Abstract Factory

// Factory Method — subclass decides which class to instantiate interface NotificationFactory { Notification create(String recipient); } class EmailFactory implements NotificationFactory { public Notification create(String to) { return new EmailNotification(to); } } // Static factory — preferred over constructors in many cases // (see LocalDate.of(), Optional.of(), List.of()) class NotificationService { public static NotificationService forEmail() { return new NotificationService("email"); } public static NotificationService forSms() { return new NotificationService("sms"); } public static NotificationService forPush() { return new NotificationService("push"); } }

2. Structural Patterns

STRUCTURAL

Decorator

// Add behavior to objects without modifying class interface DataSource { void writeData(String data); String readData(); } class FileDataSource implements DataSource { /* writes to file */ } class EncryptionDecorator implements DataSource { private final DataSource wrapped; public EncryptionDecorator(DataSource d) { this.wrapped = d; } public void writeData(String data) { wrapped.writeData(encrypt(data)); } public String readData() { return decrypt(wrapped.readData()); } } // Composing decorators at runtime DataSource source = new EncryptionDecorator( new CompressionDecorator( new FileDataSource("data.txt") ) ); // Java uses this: BufferedReader(new InputStreamReader(new FileInputStream(...)))

Proxy

// Same interface as real object — controls access class CachingProxy implements UserRepository { private final UserRepository real; private final Map<Long, User> cache = new ConcurrentHashMap<>(); public User findById(long id) { return cache.computeIfAbsent(id, real::findById); } } // Spring AOP, JPA lazy loading, Spring Security, @Transactional all use Proxy // Java: java.lang.reflect.Proxy for dynamic proxies at runtime

Adapter & Facade

// Adapter — bridge incompatible interfaces class LegacyPaymentAdapter implements ModernPaymentGateway { private final LegacyPaymentSystem legacy; public PaymentResult charge(Money amount, Card card) { return convertResult(legacy.processPayment(amount.toDouble(), card.getNumber())); } } // Facade — simplified interface to complex subsystem class OrderFacade { private final InventoryService inventory; private final PaymentService payment; private final ShippingService shipping; private final NotificationService notify; public Order placeOrder(Cart cart, PaymentInfo pi) { inventory.reserve(cart); payment.charge(cart.total(), pi); Order order = shipping.schedule(cart); notify.confirmOrder(order); return order; } }

3. Behavioral Patterns

BEHAVIORAL

Strategy

// Encapsulate interchangeable algorithms behind an interface @FunctionalInterface interface SortStrategy<T> { void sort(List<T> list); } // With lambdas, Strategy reduces to just a Function/FunctionalInterface List<User> users = ...; users.sort(Comparator.comparing(User::getName)); // sort by name users.sort(Comparator.comparing(User::getAge).reversed()); // sort by age desc

Observer

// Publish-subscribe — decouples producers from consumers interface EventListener<T> { void onEvent(T event); } class EventBus<T> { private final List<EventListener<T>> listeners = new CopyOnWriteArrayList<>(); public void subscribe(EventListener<T> l) { listeners.add(l); } public void publish(T event) { listeners.forEach(l -> l.onEvent(event)); } } // Java provides: Observable (deprecated), PropertyChangeListener // Spring: @EventListener, ApplicationEventPublisher

Template Method

// Define skeleton of algorithm, subclasses fill in steps abstract class DataExporter { public final void export(DataSet data) { // final = template method List<String> formatted = format(data); // abstract — varies validate(formatted); // concrete — shared write(formatted); // abstract — varies logCompletion(); // concrete hook — shared } protected abstract List<String> format(DataSet data); protected abstract void write(List<String> rows); protected void validate(List<String> rows) { /* default validation */ } } // Spring uses this: JdbcTemplate, RestTemplate, AbstractController

Chain of Responsibility

interface RequestHandler { void setNext(RequestHandler next); void handle(Request req); } abstract class BaseHandler implements RequestHandler { private RequestHandler next; public void setNext(RequestHandler n) { this.next = n; } protected void passToNext(Request req) { if (next != null) next.handle(req); } } // Spring Security Filter chain, Servlet Filters, log4j2 appenders all use CoR

6. Interview Q&A

What is the difference between Strategy and State pattern?
Both patterns use an object to encapsulate variable behavior, but their intent differs:

Strategy — the client chooses and sets the algorithm externally. The strategy doesn't change on its own. Example: sorting algorithm chosen at runtime.

State — the object changes its own behavior when its internal state changes. States know about each other (transitions). Example: Order status (PENDING → PROCESSING → SHIPPED → DELIVERED) — the order transitions itself.

Key difference: Strategy is set by the client and doesn't self-transition; State is internal and drives its own transitions.
When would you use a Proxy vs Decorator pattern?
Both wrap an object implementing the same interface, but the intent differs:

Proxy controls access to the subject — it adds access control, lazy loading, logging, or remote delegation. The client often doesn't know it's talking to a proxy. Examples: Spring AOP proxy for @Transactional, lazy JPA entity loading, virtual proxies.

Decorator adds new responsibilities — it extends behavior. Decorators are typically composed by the client explicitly. Examples: Java I/O streams (BufferedInputStream wraps FileInputStream), adding retry/timeout to HTTP calls.

Rule of thumb: Proxy = same behavior + access control. Decorator = additional/enhanced behavior.
How does the Builder pattern improve code quality compared to telescoping constructors?
Telescoping constructors — you create multiple overloaded constructors with increasing numbers of parameters. Problems: caller must know the correct parameter order, optional parameters must have defaults in every combination, easy to accidentally swap two int parameters with no compile error.

Builder — each parameter is set by a named method. Benefits: readable (method names = parameter names), order-independent, optional parameters are truly optional (use defaults), validates in build(), immutable result. Lombok @Builder generates this automatically.

For objects with more than 3–4 parameters (especially optional ones), prefer Builder.
Explain how Spring uses the Template Method pattern.
JdbcTemplate is the canonical example. It defines the skeleton algorithm for executing SQL:
1. Get connection from pool (concrete — Spring handles)
2. Prepare statement (concrete — Spring handles)
3. Execute query (concrete — Spring calls)
4. Map result set to objects (abstract — YOU provide via RowMapper/lambda)
5. Close connection, handle exceptions (concrete — Spring handles)

You only provide the variable part (the SQL and row mapping). Spring handles all the boilerplate resource management.

Same pattern in RestTemplate (HTTP handling), TransactionTemplate (transaction management), and RabbitTemplate (message handling).
