3. HashMap Internals (Critical Interview Topic)

HashMap is backed by an array of "buckets" (linked lists/trees). Understanding its internals is essential for senior interviews.

How HashMap Works

// Step 1: hash(key) — spreads hash to reduce collisions static final int hash(Object key) { int h; return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16); } // Step 2: bucket index = hash & (capacity - 1) (faster than modulo) int index = hash & (capacity - 1); // Step 3: store in bucket (linked list until 8 entries → treeify to RedBlackTree) // Step 4: on get, compute same index, traverse list/tree comparing equals() // Key parameters: int DEFAULT_INITIAL_CAPACITY = 16; // must be power of 2 float DEFAULT_LOAD_FACTOR = 0.75f; // resize when 75% full int TREEIFY_THRESHOLD = 8; // list → Red-Black Tree at 8 nodes int UNTREEIFY_THRESHOLD = 6; // tree → list when shrinks to 6

Rehashing

// When size > capacity * loadFactor → rehash // Default: rehash when 16 * 0.75 = 12 entries stored // New capacity = old * 2 (always power of 2) // All entries recomputed and redistributed — O(n) operation // Performance tips: Map<String, User> map = new HashMap<>(64, 0.75f); // If you expect ~40 entries: capacity = 40/0.75 = 54, round up to 64 (next power of 2)
If two objects are equal (equals() returns true), they MUST have the same hashCode(). Violating this breaks HashMap — you'll store successfully but never be able to retrieve the entry.

null Keys and Values

HashMap<String, String> map = new HashMap<>(); map.put(null, "value"); // allowed — null key stored at bucket 0 map.put("key", null); // allowed — null values allowed // Hashtable (legacy): no null keys or values → NullPointerException // ConcurrentHashMap: no null keys or values → NullPointerException

ConcurrentHashMap vs synchronizedMap

// ConcurrentHashMap — Java 8+ uses CAS + synchronized on individual bins // Multiple reads/writes can happen concurrently without full lock ConcurrentHashMap<String, Integer> chm = new ConcurrentHashMap<>(); // Atomic operations — key methods chm.putIfAbsent("key", 1); // atomic chm.computeIfAbsent("key", k -> compute(k)); // atomic compute chm.merge("key", 1, Integer::sum); // atomic merge/update chm.getOrDefault("key", 0); // read with default // Collections.synchronizedMap — wraps entire map with single lock // All operations serialized — poor throughput under contention Map<String, String> syncMap = Collections.synchronizedMap(new HashMap<>());

BlockingQueue for Producer-Consumer

BlockingQueue<Task> queue = new LinkedBlockingQueue<>(100); // bounded // Producer thread queue.put(task); // blocks if queue full queue.offer(task, 5, TimeUnit.SECONDS); // timeout // Consumer thread Task t = queue.take(); // blocks if queue empty Task t = queue.poll(5, TimeUnit.SECONDS); // timeout

9. Interview Q&A

How does HashMap handle collisions in Java 8+?
In Java 8+, when a bucket exceeds 8 entries (TREEIFY_THRESHOLD), the linked list is converted to a Red-Black Tree, reducing worst-case lookup from O(n) to O(log n). When entries drop below 6 (UNTREEIFY_THRESHOLD), it converts back to a linked list.

Before Java 8, buckets were always linked lists, making a pathological attack with many hash collisions O(n) per operation. The treeification in Java 8 mitigates this to O(log n).
What happens if you use a mutable object as a HashMap key and then mutate it?
The entry becomes unretrievable. When you put the entry, HashMap computes hashCode() and stores it in the correct bucket. After mutation, hashCode() returns a different value, so get() looks in a different bucket and finds nothing.

The entry still exists in the map (at the old bucket location) but you can never find it via normal get(). This causes a memory leak.

Best practice: Only use immutable objects (String, Integer, enums, records) as HashMap keys.
What is the difference between fail-fast and fail-safe iterators?
Fail-fast: Throws ConcurrentModificationException if the collection is structurally modified during iteration (except through the iterator's own remove()). Works by checking a modCount counter. Used by ArrayList, HashMap, HashSet iterators.

Fail-safe: Operates on a snapshot/copy of the collection, so modifications during iteration are safe (but you won't see new changes). Used by CopyOnWriteArrayList, ConcurrentHashMap iterators. Higher memory cost.

Key point: Fail-fast is a best-effort mechanism — not a guarantee. Never rely on it for correctness; use proper synchronization or concurrent collections instead.
When would you choose LinkedList over ArrayList?
Almost never in practice. Despite LinkedList's O(1) insert at head/middle in theory, the real-world performance is usually worse than ArrayList due to:
1. Cache misses — ArrayList elements are contiguous in memory (cache-friendly); LinkedList nodes are scattered
2. Object overhead — each node has prev/next pointers + object header (~48 bytes per Integer vs ~4 bytes in ArrayList)
3. GC pressure — many small node objects

Use ArrayDeque instead of LinkedList for stack/queue operations. The only real use case for LinkedList is when you need both List and Deque interfaces from the same reference.
How does ConcurrentHashMap achieve thread safety without locking the entire map?
Java 8+ implementation uses a combination of:
1. Volatile reads for simple gets (no locking needed for reads of already-written values)
2. CAS (Compare-And-Swap) for bucket initialization and certain updates
3. synchronized on individual bin (bucket) only when modifying a bucket, not the whole table

This allows concurrent reads from any bucket and concurrent writes to different buckets, significantly improving throughput compared to a single-lock approach. Reads are effectively lock-free. The size() method uses distributed counters (LongAdder pattern) to avoid contention.
