1. Thread Lifecycle

NEW → RUNNABLE → (RUNNING) → BLOCKED / WAITING / TIMED_WAITING → TERMINATED // State transitions: // NEW → RUNNABLE : thread.start() // RUNNABLE → BLOCKED : trying to acquire synchronized lock held by another // RUNNABLE → WAITING : Object.wait(), Thread.join(), LockSupport.park() // RUNNABLE → TIMED_WAITING : Thread.sleep(n), Object.wait(n), Thread.join(n) // BLOCKED/WAITING → RUNNABLE : lock acquired / notify() / interrupt() // RUNNABLE → TERMINATED : run() completes or throws uncaught exception
// Creating threads — 3 ways // 1. Extend Thread (avoid — ties class to Thread) class MyThread extends Thread { public void run() { System.out.println("Running"); } } // 2. Implement Runnable (preferred — separates task from thread) Runnable task = () -> System.out.println("Running"); new Thread(task).start(); // 3. Submit to ExecutorService (best — reuse threads) ExecutorService exec = Executors.newFixedThreadPool(4); exec.submit(() -> System.out.println("Running in pool"));

2. synchronized & volatile

synchronized

// Instance method lock — locks on 'this' public synchronized void increment() { counter++; } // Static method lock — locks on Class object public static synchronized void staticIncrement() { staticCounter++; } // Synchronized block — lock on specific object (finer granularity) private final Object lock = new Object(); public void increment() { synchronized (lock) { counter++; } } // Double-checked locking — Singleton pattern public class Singleton { private static volatile Singleton instance; public static Singleton getInstance() { if (instance == null) { synchronized (Singleton.class) { if (instance == null) { // double check inside lock instance = new Singleton(); } } } return instance; } }
volatile is necessary in double-checked locking. Without it, the JVM may reorder the constructor call and reference assignment, causing another thread to see a partially constructed object.

wait() / notify() / notifyAll()

// Must be called inside synchronized block synchronized (this) { while (!condition) { // WHILE not if — guard against spurious wakeups wait(); // releases lock, thread goes WAITING } // condition is now true, proceed } // Signal one waiting thread synchronized (this) { condition = true; notify(); // wake one — prefer notifyAll() for safety notifyAll(); // wake all — safer but more contention }

3. Locks & Conditions (java.util.concurrent.locks)

ReentrantLock lock = new ReentrantLock(true); // fair=true — longest-waiting thread gets lock // Always unlock in finally! lock.lock(); try { // critical section } finally { lock.unlock(); } // tryLock — non-blocking attempt if (lock.tryLock(100, TimeUnit.MILLISECONDS)) { try { /* got lock */ } finally { lock.unlock(); } } else { /* couldn't get lock */ } // Condition variables — replacement for wait/notify Condition notFull = lock.newCondition(); Condition notEmpty = lock.newCondition(); // Producer lock.lock(); try { while (queue.isFull()) notFull.await(); queue.add(item); notEmpty.signal(); } finally { lock.unlock(); }

ReadWriteLock

ReadWriteLock rwLock = new ReentrantReadWriteLock(); // Many readers can hold the read lock simultaneously rwLock.readLock().lock(); try { return cache.get(key); } finally { rwLock.readLock().unlock(); } // Only one writer, exclusive of all readers rwLock.writeLock().lock(); try { cache.put(key, value); } finally { rwLock.writeLock().unlock(); } // Java 8+: StampedLock — optimistic reads (even faster) StampedLock sl = new StampedLock(); long stamp = sl.tryOptimisticRead(); // no lock — just a stamp int val = readValue; if (!sl.validate(stamp)) { // was data modified? stamp = sl.readLock(); // fall back to read lock try { val = readValue; } finally { sl.unlockRead(stamp); } }

4. Atomic Variables

// AtomicInteger — lock-free thread-safe operations using CAS AtomicInteger counter = new AtomicInteger(0); counter.incrementAndGet(); // atomic ++counter counter.getAndIncrement(); // atomic counter++ counter.addAndGet(5); // atomic counter += 5 counter.compareAndSet(0, 1); // if current==0, set to 1 (CAS) // AtomicReference — for arbitrary objects AtomicReference<User> ref = new AtomicReference<>(currentUser); ref.compareAndSet(currentUser, newUser); // atomic swap if current matches // LongAdder — better than AtomicLong under HIGH contention // Uses striped counters — each thread updates its own stripe, sum() combines all LongAdder adder = new LongAdder(); adder.increment(); adder.sum(); // not perfectly consistent but high throughput

5. ExecutorService & Thread Pools

// Thread pool types ExecutorService fixed = Executors.newFixedThreadPool(10); // fixed N threads ExecutorService cached = Executors.newCachedThreadPool(); // grows as needed, idle for 60s ExecutorService single = Executors.newSingleThreadExecutor(); // serial execution ScheduledExecutorService sched = Executors.newScheduledThreadPool(2); // cron-like // Scheduled tasks sched.schedule(task, 5, TimeUnit.SECONDS); // once after delay sched.scheduleAtFixedRate(task, 0, 1, TimeUnit.MINUTES); // every minute // Proper shutdown executor.shutdown(); // no new tasks, wait for running if (!executor.awaitTermination(30, TimeUnit.SECONDS)) { executor.shutdownNow(); // interrupt running tasks }

Custom ThreadPoolExecutor (Interview Favorite)

ThreadPoolExecutor executor = new ThreadPoolExecutor( 5, // corePoolSize — always alive 20, // maximumPoolSize — max when queue full 60, TimeUnit.SECONDS, // keepAliveTime — idle thread timeout new LinkedBlockingQueue<>(100), // work queue (bounded!) new ThreadFactory() { // custom thread naming private final AtomicInteger count = new AtomicInteger(1); public Thread newThread(Runnable r) { return new Thread(r, "worker-" + count.getAndIncrement()); } }, new ThreadPoolExecutor.CallerRunsPolicy() // rejection policy when queue full ); // Rejection policies: // AbortPolicy (default) — throws RejectedExecutionException // CallerRunsPolicy — runs in caller's thread (natural backpressure) // DiscardPolicy — silently drops task // DiscardOldestPolicy — drops oldest queued task, retries submit
Always use bounded queues in production. Unbounded queues (Executors.newFixedThreadPool uses LinkedBlockingQueue with Integer.MAX_VALUE capacity) can cause OutOfMemoryError under load.

6. Future & CompletableFuture

// Basic Future — blocking Future<String> future = executor.submit(() -> fetchData()); String result = future.get(5, TimeUnit.SECONDS); // blocks! // CompletableFuture — non-blocking pipeline CompletableFuture<User> userFuture = CompletableFuture .supplyAsync(() -> fetchUser(id)) // async — ForkJoinPool by default .thenApply(user -> enrichUser(user)) // transform result .thenApply(user -> validateUser(user)) .exceptionally(ex -> User.anonymous()) // handle error .whenComplete((u, ex) -> log.info("Done")); // always runs // Combine multiple futures CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> getUser(id)); CompletableFuture<Account> accountFuture = CompletableFuture.supplyAsync(() -> getAccount(id)); // Wait for both and combine CompletableFuture<Dashboard> dashboard = userFuture .thenCombine(accountFuture, (user, account) -> new Dashboard(user, account)); // Wait for first to complete CompletableFuture.anyOf(f1, f2, f3).thenAccept(System.out::println); // Wait for all to complete CompletableFuture.allOf(f1, f2, f3).join(); // Custom executor (don't use ForkJoinPool for blocking I/O!) ExecutorService ioPool = Executors.newCachedThreadPool(); CompletableFuture.supplyAsync(() -> callDatabase(), ioPool);

7. Concurrency Problems

Deadlock

// Classic deadlock: Thread A locks lockA then lockB // Thread B locks lockB then lockA synchronized (lockA) { synchronized (lockB) { /* ... */ } // Thread A } synchronized (lockB) { synchronized (lockA) { /* ... */ } // Thread B — DEADLOCK! } // Prevention: consistent lock ordering synchronized (lockA) { synchronized (lockB) { /* both threads same order */ } } // Detection: thread dumps, jstack, VisualVM

Race Condition & Livelock

// Race condition — counter++ is NOT atomic private int counter = 0; public void increment() { counter++; } // read-modify-write — 3 operations! // Fix: AtomicInteger, synchronized, or Lock private AtomicInteger counter = new AtomicInteger(0); public void increment() { counter.incrementAndGet(); } // Livelock — threads keep responding to each other without progress // e.g., two threads each back off when they see the other, retry, back off... // Fix: introduce randomized backoff or priority-based ordering

8. Concurrency Patterns

Thread Confinement

// ThreadLocal — each thread has its own copy private static final ThreadLocal<DateFormat> dateFormat = ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd")); // Get thread-local value DateFormat df = dateFormat.get(); // IMPORTANT: Always remove when done (especially in thread pools!) dateFormat.remove(); // prevent memory leaks in thread pools

CountDownLatch & CyclicBarrier

// CountDownLatch — wait for N tasks to complete CountDownLatch latch = new CountDownLatch(3); for (int i = 0; i < 3; i++) { executor.submit(() -> { doWork(); latch.countDown(); // count down when done }); } latch.await(); // main thread waits until count reaches 0 // CyclicBarrier — N threads wait for each other at a point CyclicBarrier barrier = new CyclicBarrier(3, () -> combineResults()); // Each thread calls barrier.await() — waits for all 3 before continuing // Reusable (unlike CountDownLatch) // Semaphore — limit concurrent access to N Semaphore semaphore = new Semaphore(10); // max 10 concurrent semaphore.acquire(); // blocks if 10 already acquired try { accessResource(); } finally { semaphore.release(); }

9. Interview Q&A

What is the difference between synchronized and ReentrantLock?
synchronized: built-in keyword, simpler, always unlocks on exception (JVM guarantees), can't interrupt a waiting thread, no fairness control, no condition variables (just wait/notify).

ReentrantLock: explicit lock/unlock (must be in finally!), can tryLock() with timeout, can interrupt waiting threads (lockInterruptibly()), supports fairness mode, multiple Condition objects, can check if lock is held (isHeldByCurrentThread()).

When to use: Use synchronized by default — simpler and less error-prone. Use ReentrantLock when you need timeout, interruptibility, or multiple conditions.
How would you design a thread-safe lazy-initialized singleton?
Three correct approaches:

1. Enum singleton (simplest, handles serialization and reflection attacks):
public enum Singleton { INSTANCE; }

2. Static inner class (Bill Pugh) — lazy, no synchronization overhead:
class Singleton { private static class H { static final Singleton I = new Singleton(); } public static Singleton get() { return H.I; } }

3. Double-checked locking with volatile — shown in code examples above.

Avoid: synchronized getInstance() method — synchronizes on every call, poor performance.
What is the difference between thenApply, thenCompose, and thenCombine in CompletableFuture?
thenApply(Function) — transforms the result synchronously, like stream's map(). Input: T, Output: U. Returns CompletableFuture<U>. Use for non-async transformation.

thenCompose(Function→CF) — like flatMap(). Input: T, Output: CompletableFuture<U>. Flattens the nested future. Use when the next step is also async (returns a CF). Avoids CompletableFuture<CompletableFuture<U>>.

thenCombine(CF, BiFunction) — combines two independent futures when BOTH complete. Use for parallel async operations that need to be merged.

Rule: thenApply for sync transform, thenCompose for chaining async calls, thenCombine for merging parallel results.
What is a memory visibility problem and how do you fix it?
CPUs have multiple cache levels. A write by Thread A to a field may sit in Thread A's CPU cache and not be visible to Thread B reading the same field from a different cache. This is a visibility problem — not a correctness issue on single-core systems but critical on multi-core.

Solutions:
1. volatile — guarantees writes are flushed to main memory and reads bypass cache
2. synchronized — entering/exiting a synchronized block establishes happens-before visibility
3. java.util.concurrent atomic classes — use volatile reads/writes internally
4. Properly constructed objects — final fields are safely published through constructors

The Java Memory Model defines happens-before guarantees — if A happens-before B, A's writes are visible to B.
How would you determine the right number of threads for a thread pool?
It depends on whether the tasks are CPU-bound or I/O-bound:

CPU-bound tasks: thread count = number of CPU cores (N_cpu). Adding more threads just causes context switching overhead. Often: N_cpu + 1.

I/O-bound tasks: threads spend time waiting for I/O. Formula: N_threads = N_cpu × (1 + W/C) where W=wait time, C=compute time. If 90% wait time, 10 cores → ~100 threads.

In practice: Start with a reasonable number, load-test, monitor CPU utilization and thread pool queue depth. If queue grows, add threads (up to I/O bound limit). If CPU at 100%, reduce threads. Use Virtual Threads (Java 21) for massively concurrent I/O workloads — they're cheap enough to create one-per-request.
