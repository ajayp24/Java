Spring Core

Spring IoC Container

Core

The Inversion of Control (IoC) container is Spring's central engine. Instead of your code creating and wiring objects, the container manages the entire lifecycle and graph of application objects (beans). You describe what you need; the container provides it. The primary interface is ApplicationContext, which extends BeanFactory with enterprise features: event publishing, internationalization, AOP, and eager bean instantiation.

IoC Container Hierarchy
  • BeanFactory: basic IoC — lazy instantiation, minimal footprint. Rarely used directly.
  • ApplicationContext: full-featured — eager singleton instantiation, AOP, events, i18n. Use this.
  • AnnotationConfigApplicationContext: reads @Configuration classes — used in standalone apps.
  • SpringApplication (Boot): bootstraps ApplicationContext automatically; type depends on classpath (Servlet, Reactive, None).
  • The container is built from BeanDefinitions: metadata describing class, scope, constructor args, property values.
JAVAApplicationContext bootstrap + event listening
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        // SpringApplication builds and refreshes the ApplicationContext
        ConfigurableApplicationContext ctx = SpringApplication.run(App.class, args);

        // Retrieve bean programmatically (rarely needed — prefer injection)
        OrderService svc = ctx.getBean(OrderService.class);
    }
}

// Listen to context events
@Component
public class StartupListener implements ApplicationListener<ContextRefreshedEvent> {
    @Override
    public void onApplicationEvent(ContextRefreshedEvent event) {
        // Runs once container is fully initialized
    }
}

// Or use functional approach (Spring 5+)
@EventListener(ApplicationReadyEvent.class)
public void onReady() { /* warm up caches, start background tasks */ }
Interview Focus
  • "What is IoC?" — The container owns object creation and wiring; code asks for collaborators rather than creating them.
  • Difference between BeanFactory and ApplicationContext — lazy vs eager, feature set.
  • Spring 6 requires Java 17+ and Jakarta EE 9+ (namespace jakarta.* not javax.*).
Spring Core

Dependency Injection

Core

DI is the mechanism IoC uses: the container injects dependencies into beans rather than beans fetching them. Spring supports three injection styles: constructor (preferred), setter, and field. Constructor injection is favored because it enforces immutability, makes dependencies explicit, and enables easy unit testing without a Spring context.

StyleMechanismImmutable?Use
ConstructorVia constructor paramsYes (final fields)Required, mandatory deps. Preferred.
Setter@Autowired on setterNoOptional/reconfigurable deps.
Field@Autowired on fieldNoAvoid — hides deps, breaks unit tests.
JAVAConstructor DI (preferred) vs field DI (avoid)
// PREFERRED: constructor injection — immutable, testable, no Spring needed in tests
@Service
public class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway payment;

    // @Autowired is optional when only one constructor exists (Spring 4.3+)
    public OrderService(OrderRepository repo, PaymentGateway payment) {
        this.repo    = repo;
        this.payment = payment;
    }
}

// AVOID: field injection — Spring must be present to test, can't make fields final
@Service
public class BadService {
    @Autowired private OrderRepository repo; // ← avoid
}

// Disambiguation: multiple beans of same type
@Service
public class NotificationService {
    public NotificationService(
            @Qualifier("emailChannel") NotificationChannel email,
            @Qualifier("smsChannel")   NotificationChannel sms) { ... }
}

// Optional dependency
public ReportService(ReportRepository repo,
        @Autowired(required = false) CacheManager cache) { ... }
Circular Dependency
  • Constructor injection with circular deps throws BeanCurrentlyInCreationException at startup — fail-fast, which is correct behavior.
  • Fix: refactor to break the cycle (introduce a third collaborator or event), or use @Lazy on one injection point as a last resort.
  • Field injection silently defers resolution, masking the design problem.

Bean Lifecycle

Core

Spring beans go through a well-defined lifecycle managed by the container: instantiation → property injection → awareness callbacks → initialization → in-use → destruction. Knowing the order of these phases is critical for integration tasks, connection pools, and graceful shutdown.

Lifecycle Phases (in order)
  • 1. Instantiation: container calls constructor.
  • 2. Dependency injection: properties / constructor args set.
  • 3. Aware interfaces: BeanNameAware, ApplicationContextAware etc. called.
  • 4. BeanPostProcessor.postProcessBeforeInitialization: AOP proxies, custom processing.
  • 5. @PostConstruct: called after all dependencies injected — preferred init hook.
  • 6. InitializingBean.afterPropertiesSet(): alternative init hook (legacy).
  • 7. @Bean(initMethod): XML/Java config custom init.
  • 8. BeanPostProcessor.postProcessAfterInitialization: AOP proxy wrapping.
  • 9. In use by the application.
  • 10. @PreDestroy: cleanup before container shuts down — preferred destroy hook.
  • 11. DisposableBean.destroy(): alternative (legacy). Close connections, stop threads.
JAVA@PostConstruct / @PreDestroy lifecycle hooks
@Component
public class ConnectionPool {
    private DataSource ds;

    @PostConstruct
    public void init() {
        // All dependencies injected — safe to use them here
        ds = createDataSource();
        warmUp(ds);
    }

    @PreDestroy
    public void shutdown() {
        // Called before container destroys this bean
        if (ds instanceof Closeable c) c.close();
    }
}

// SmartLifecycle: ordered startup/shutdown for infrastructure beans
@Component
public class KafkaConsumerManager implements SmartLifecycle {
    private volatile boolean running = false;

    @Override public void start()   { running = true;  /* start consumers */ }
    @Override public void stop()    { running = false; /* drain and stop */ }
    @Override public boolean isRunning() { return running; }
    @Override public int getPhase()     { return 0; } // lower = starts later, stops first
}
Spring Core

Bean Scopes

Important

A bean's scope determines how many instances the container creates and how long they live. The default is singleton — one instance per container, shared across all threads. Injecting a prototype bean into a singleton is a classic trap: the singleton holds one prototype instance forever, defeating its purpose.

ScopeInstancesContext
singletonOne per containerDefault. Stateless services, repositories.
prototypeNew per injection/getBean()Stateful beans. Container does not manage destroy.
requestOne per HTTP requestWeb: per-request state (e.g. auth context holder).
sessionOne per HTTP sessionWeb: per-user session data.
applicationOne per ServletContextWeb: shared across sessions in same app.
websocketOne per WebSocket sessionWebSocket-scoped beans.
JAVAPrototype in singleton — the correct fix with ObjectProvider
// PROBLEM: singleton holds one prototype forever
@Service
public class BadService {
    @Autowired
    private PrototypeBean pb; // same instance every time — scope defeated
}

// FIX: inject ObjectProvider — fetches a new instance each time
@Service
public class GoodService {
    private final ObjectProvider<PrototypeBean> provider;

    public GoodService(ObjectProvider<PrototypeBean> provider) {
        this.provider = provider;
    }

    public void doWork() {
        PrototypeBean fresh = provider.getObject(); // new instance each call
        fresh.execute();
    }
}

// Web scopes require proxy — singleton proxy delegates to per-request instance
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContext {
    private String traceId;
    // ... injected into singletons safely via proxy
}
Spring Core

Stereotype Annotations

Core

Stereotype annotations mark classes for component scanning. All are specializations of @Component and result in the class being registered as a Spring bean. The distinctions communicate architectural role and enable targeted AOP/post-processing.

@Component
Generic Spring-managed bean. Base annotation — all others inherit from it. Use when none of the specific stereotypes fits.
@Service
Business logic layer. Semantically signals service role. No extra behavior over @Component in stock Spring — but clearly communicates intent and enables targeted AOP.
@Repository
Extra behavior: persistence exceptions (e.g., SQLException) are translated to Spring's DataAccessException hierarchy via PersistenceExceptionTranslationPostProcessor.
@Controller
Spring MVC handler. Detected by DispatcherServlet. Returns view names (Thymeleaf, JSP). Methods annotated with @RequestMapping and variants.
@RestController
= @Controller + @ResponseBody. Every handler method serializes the return value directly to the HTTP response body (JSON/XML via Jackson/JAXB). No view resolution.
@Configuration
Declares @Bean factory methods. Proxied by CGLIB — inter-bean method calls return the singleton instance, not a new object. Use @Configuration(proxyBeanMethods=false) for lite mode.
JAVALayer-appropriate stereotype usage
@Repository
public class JpaOrderRepository implements OrderRepository {
    // SQLException → DataAccessException translation automatic
}

@Service
public class OrderService {
    // Business rules here, delegates to repository
}

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    private final OrderService service;
    public OrderController(OrderService service) { this.service = service; }

    @GetMapping("/{id}")
    public ResponseEntity<OrderDto> get(@PathVariable Long id) {
        return ResponseEntity.ok(service.findById(id));
    }
}
Spring Boot

Auto Configuration

Important

Spring Boot's auto-configuration scans the classpath and conditionally registers beans based on what's present — you get a configured DataSource because spring-boot-starter-data-jpa is on the classpath. Each auto-configuration class uses @Conditional* annotations so it backs off when you provide your own bean.

How It Works
  • @SpringBootApplication = @EnableAutoConfiguration + @ComponentScan + @Configuration.
  • Boot reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Boot 3) — lists all auto-config classes.
  • Each auto-config class is annotated with @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty etc.
  • If you define your own DataSource bean, DataSourceAutoConfiguration backs off entirely.
  • Debug with: --debug flag or spring.autoconfigure.report=true — prints "positive matches" and "negative matches".
JAVAWriting a custom auto-configuration
// Custom starter auto-config — registered in AutoConfiguration.imports
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)          // only if library is on classpath
@ConditionalOnMissingBean(AuditClient.class)   // back off if user provided one
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    public AuditClient auditClient(AuditProperties props) {
        return new AuditClient(props.getEndpoint(), props.getApiKey());
    }
}

// Type-safe configuration binding
@ConfigurationProperties(prefix = "audit")
@Validated
public class AuditProperties {
    @NotBlank private String endpoint;
    @NotBlank private String apiKey;
    // getters + setters
}

Configuration & Profiles

Important

Spring Boot externalizes configuration into property sources with a strict priority order — command-line args override env vars, which override application.yml. Profiles activate environment-specific beans and property files (application-prod.yml) without touching application code.

Property Source Priority (highest first)
  • Command-line arguments: --server.port=9090.
  • Java system properties: -Dserver.port=9090.
  • OS environment variables: SERVER_PORT=9090 (relaxed binding).
  • Profile-specific: application-{profile}.yml inside / outside jar.
  • application.yml inside / outside jar.
  • @PropertySource annotations on @Configuration classes.
YAMLapplication.yml multi-profile with groups
# application.yml — active profile from env or arg
spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:local}
    group:
      prod: "prod,monitoring,security"   # activate group → activates all 3

---
spring.config.activate.on-profile: local
datasource:
  url: jdbc:h2:mem:testdb

---
spring.config.activate.on-profile: prod
datasource:
  url: ${DB_URL}
  username: ${DB_USER}
  password: ${DB_PASS}
JAVA@Profile on beans, @ConfigurationProperties
// Bean active only in prod profile

@Profile("prod")
public class ProdEmailService implements EmailService { ... }

@Service
@Profile("!prod")     // active when NOT prod
public class StubEmailService implements EmailService { ... }

@ConfigurationProperties(prefix = "app.cache")

// Inject directly
@Value("${app.feature.enabled:false}")   // with default

Web Layer

Spring MVC

Core

Spring MVC is built on the Front Controller pattern. A single DispatcherServlet receives all requests, delegates to HandlerMapping to find the right controller method, invokes it, and routes the result through ViewResolver (or HttpMessageConverter for REST). Spring WebFlux is the reactive alternative — non-blocking, built on Project Reactor.

Request Processing Pipeline
  • DispatcherServlet → HandlerMapping (find controller method) → HandlerAdapter (invoke it).
  • HandlerInterceptor: pre/post/afterCompletion hooks around handler execution.
  • HttpMessageConverter: serializes/deserializes HTTP body — Jackson for JSON, JAXB for XML.
  • ContentNegotiation: picks converter based on Accept header or URL extension.
  • ModelAndView: returned by traditional controllers for view rendering.
JAVAHandlerInterceptor for request tracing
@Component
public class TraceInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        String traceId = UUID.randomUUID().toString();
        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);
        return true; // continue chain
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                  Object handler, Exception ex) {
        MDC.clear(); // prevent ThreadLocal leak in thread pool
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    private final TraceInterceptor traceInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(traceInterceptor)
                .addPathPatterns("/api/**");
    }
}
Web Layer

REST APIs

Core

REST APIs in Spring are built with @RestController. Design centers on: proper HTTP methods and status codes, meaningful resource URLs, consistent request/response models, and clean error contracts. ResponseEntity<T> gives full control over status, headers, and body.

JAVAREST controller — full CRUD with proper status codes
@RestController
@RequestMapping("/api/v1/orders")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService service;

    @GetMapping
    public Page<OrderDto> list(@PageableDefault(size = 20) Pageable p) {
        return service.findAll(p);             // 200 OK
    }

    @GetMapping("/{id}")
    public ResponseEntity<OrderDto> get(@PathVariable Long id) {
        return service.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build()); // 200 or 404
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public OrderDto create(@RequestBody @Valid CreateOrderRequest req) {
        return service.create(req);              // 201 Created
    }

    @PutMapping("/{id}")
    public ResponseEntity<OrderDto> update(@PathVariable Long id,
            @RequestBody @Valid UpdateOrderRequest req) {
        return ResponseEntity.ok(service.update(id, req));
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        service.delete(id);                      // 204 No Content
    }
}
API Design Principles
  • Version in URL path (/api/v1/) or Accept header — URL versioning is more visible and cache-friendly.
  • Use Location header in 201 response pointing to the new resource.
  • Paginate collections — never return unbounded lists; use Pageable with Spring Data.
  • Return consistent error bodies — use ProblemDetail (RFC 7807, built into Spring 6) for machine-readable errors.

Validation

Important

Spring integrates Jakarta Bean Validation (Hibernate Validator). Annotate fields with constraints; add @Valid or @Validated on the controller parameter to trigger validation. MethodValidationPostProcessor enables validation on service layer methods too.

JAVARequest DTO constraints + custom validator
public record CreateOrderRequest(
    @NotBlank(message = "customerId required")
    String customerId,

    @NotEmpty @Size(max = 50)
    List<LineItem> items,

    @Future
    LocalDate deliveryDate,

    @DecimalMin("0.01") @Digits(integer = 8, fraction = 2)
    BigDecimal totalAmount
) {}

// Custom constraint annotation
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = SkuValidator.class)
public @interface ValidSku {
    String message() default "Invalid SKU format";
    Class<?>[] groups()   default {};
    Class<?>[] payload() default {};
}

public class SkuValidator implements ConstraintValidator<ValidSku, String> {
    private static final Pattern PATTERN = Pattern.compile("[A-Z]{3}-\\d{4}");

    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        return value != null && PATTERN.matcher(value).matches();
    }
}
Validation Error Handling
  • @Valid failure → MethodArgumentNotValidException; handle in @ControllerAdvice to return structured 400 body.
  • @Validated with groups lets you apply different constraints at create vs update.
  • Never rely solely on frontend validation — always validate at the API boundary.

Exception Handling

Important

@ControllerAdvice / @RestControllerAdvice provides a global exception handling layer across all controllers. Methods annotated with @ExceptionHandler map exception types to HTTP responses. Spring 6 introduces ProblemDetail (RFC 7807) for standardized error bodies.

JAVAGlobal exception handler with ProblemDetail
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Resource Not Found");
        pd.setProperty("resourceId", ex.getId());
        return pd;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors()
            .stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                e -> Objects.requireNonNullElse(e.getDefaultMessage(), "invalid")
            ));
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation Failed");
        pd.setProperty("errors", errors);
        return pd;
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ProblemDetail handleGeneric(Exception ex) {
        log.error("Unhandled exception", ex);
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
            "An unexpected error occurred"); // never expose internal details
    }
}
Security

Spring Security

Security

Spring Security is a servlet filter chain: requests pass through a series of SecurityFilters before reaching the controller. The key filters: SecurityContextPersistenceFilter, UsernamePasswordAuthenticationFilter, ExceptionTranslationFilter, FilterSecurityInterceptor. Spring Security 6 uses a lambda DSL and removes the deprecated WebSecurityConfigurerAdapter.

JAVASpring Security 6 — SecurityFilterChain DSL
@Configuration
@EnableWebSecurity
@EnableMethodSecurity    // enables @PreAuthorize, @PostAuthorize
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)          // stateless REST: disable CSRF
            .sessionManagement(s -> s
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/actuator/health", "/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .exceptionHandling(e -> e
                .authenticationEntryPoint((req, res, ex) ->
                    res.sendError(HttpStatus.UNAUTHORIZED.value())))
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();   // never store plain-text passwords
    }
}

// Method-level security
@Service
public class AdminService {
    @PreAuthorize("hasRole('ADMIN') and #userId == authentication.principal.id")
    public void deleteUser(Long userId) { ... }
}
Security

JWT (JSON Web Token)

Security

A JWT is a compact, self-contained token: header.payload.signature. The server validates the signature without a database round-trip. Access tokens are short-lived (15 min); refresh tokens are long-lived and stored securely. JWTs can't be revoked mid-lifetime — plan for this.

JWT Structure
  • Header: algorithm (HS256, RS256) and token type.
  • Payload: claims — sub (subject), exp (expiry), iat (issued at), custom claims.
  • Signature: HMAC-SHA256 of base64(header) + "." + base64(payload) with secret key.
  • RS256 vs HS256: RS256 uses private key to sign, public key to verify — better for microservices (services don't need the secret).
JAVAJWT filter — validate token on every request
@Component
public class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain) throws IOException, ServletException {

        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res); return;
        }

        String token = header.substring(7);
        String username = jwtService.extractUsername(token); // throws if invalid/expired

        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            UserDetails user = userDetailsService.loadUserByUsername(username);
            if (jwtService.isTokenValid(token, user)) {
                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        chain.doFilter(req, res);
    }
}
Security Considerations
  • Never store JWTs in localStorage — vulnerable to XSS. Use HttpOnly cookies.
  • Short access token TTL (15 min) + refresh token rotation limits blast radius of stolen tokens.
  • Add JTI claim + server-side blocklist for immediate revocation (rare, but required for logout/compromise).
  • Use Spring Security's built-in NimbusJwtDecoder (spring-security-oauth2-resource-server) rather than rolling your own JWT parsing.

OAuth2 & OpenID Connect

Security

OAuth2 is an authorization framework; OpenID Connect (OIDC) adds authentication (identity) on top. Spring Security provides both client (your app delegates login) and resource server (your API validates tokens) support. The Authorization Code + PKCE flow is the current standard for web apps.

Key Roles
  • Resource Owner: the user.
  • Authorization Server: issues tokens — Keycloak, Auth0, Google, Okta, or Spring Authorization Server.
  • Resource Server: your API that validates access tokens.
  • Client: your web/mobile app that requests tokens on the user's behalf.
JAVAResource server JWT validation + scope-based authorization
# application.yml — resource server validates against OIDC provider
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/myrealm
JAVAResource server security config with JWT scopes
@Bean
public SecurityFilterChain resourceServer(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET,  "/api/**").hasAuthority("SCOPE_read")
            .requestMatchers(HttpMethod.POST, "/api/**").hasAuthority("SCOPE_write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2
            .jwt(jwt -> jwt
                .jwtAuthenticationConverter(keycloakRolesConverter())))  // custom claims
        .build();
}

// Extract roles from Keycloak's nested claim structure
private JwtAuthenticationConverter keycloakRolesConverter() {
    JwtGrantedAuthoritiesConverter gac = new JwtGrantedAuthoritiesConverter();
    gac.setAuthoritiesClaimName("realm_access.roles");
    gac.setAuthorityPrefix("ROLE_");
    JwtAuthenticationConverter conv = new JwtAuthenticationConverter();
    conv.setJwtGrantedAuthoritiesConverter(gac);
    return conv;
}

JAVACustom HealthIndicator + custom metric
@Component
public class DatabaseHealthIndicator implements HealthIndicator {
    private final DataSource ds;

    @Override
    public Health health() {
        try (Connection c = ds.getConnection()) {
            c.isValid(1);
            return Health.up()
                .withDetail("pool-size", poolSize())
                .build();
        } catch (SQLException e) {
            return Health.down().withException(e).build();
        }
    }
}

// Custom metric via Micrometer
@Service
public class OrderService {
    private final Counter orderCounter;
    private final Timer processingTimer;

    public OrderService(MeterRegistry registry) {
        orderCounter   = registry.counter("orders.created", "env", "prod");
        processingTimer = registry.timer("orders.processing.time");
    }

    public Order create(CreateOrderRequest req) {
        return processingTimer.record(() -> {
            Order o = doCreate(req);
            orderCounter.increment();
            return o;
        });
    }
}
Kubernetes Probe Mapping
  • /actuator/health/liveness → livenessProbe: is the app alive? Restart if dead.
  • /actuator/health/readiness → readinessProbe: is the app ready to serve traffic? Remove from service if not.
  • Keep liveness independent of external deps — a DB outage should mark readiness DOWN, not liveness (avoid restart loop).

Logging

Important

Spring Boot defaults to Logback via SLF4J facade. The facade (LoggerFactory) decouples code from the logging implementation — swap Logback for Log4j2 without changing business code. Structured logging (JSON output) and MDC (trace context propagation) are essential for distributed system observability.

JAVASLF4J best practices + MDC context
// Always use SLF4J — never use java.util.logging or log4j directly
private static final Logger log = LoggerFactory.getLogger(OrderService.class);
// Or with Lombok: @Slf4j on the class

public Order processOrder(Long orderId) {
    // Parameterized — no string concat unless log level enabled
    log.debug("Processing order id={}", orderId);

    // Guard expensive argument computation
    if (log.isDebugEnabled()) {
        log.debug("Order details: {}", expensiveToString(orderId));
    }

    try {
        Order o = repo.findById(orderId).orElseThrow();
        log.info("Order processed: id={} customer={} amount={}",
            o.getId(), o.getCustomerId(), o.getTotal());
        return o;
    } catch (Exception e) {
        log.error("Order processing failed: id={}", orderId, e); // exception as last arg
        throw e;
    }
}

    root: INFO
    com.acme.orders: DEBUG  # package-level override
    org.springframework.web: WARN

# Logback MDC pattern for plain-text (non-JSON)
# pattern: "%d{ISO8601} [%thread] [%X{traceId}] %-5level %logger - %msg%n"
Team Lead Guidance
  • Mandate structured JSON in production — log aggregators (Splunk, Loki, ELK) parse it without fragile regex.
  • Always propagate traceId + spanId via MDC — enables tracing a single request across dozens of log lines and services.
  • Never log passwords, PII, or auth tokens — use @JsonIgnore on sensitive fields and audit your log output.
Testing

Testing Spring Applications

Advanced

Effective Spring testing uses a test pyramid: many fast unit tests, moderate integration tests with sliced contexts, few end-to-end tests. The key insight: a test that loads the full ApplicationContext is 10–100× slower than a pure unit test. Choose the lightest tool that verifies the behavior.

AnnotationLoadsUse
@SpringBootTestFull contextIntegration/E2E — use webEnvironment=RANDOM_PORT for HTTP tests.
@WebMvcTestWeb layer onlyController tests — no service/repo beans loaded.
@DataJpaTestJPA + H2Repository tests — transactional, rolled back after each test.
@JsonTestJackson onlySerialization/deserialization tests.
No annotationNoneUnit tests — fastest; mock with Mockito.
JAVAUnit test (Mockito) + slice test (@WebMvcTest)
// Pure unit test — no Spring context, instant
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock    OrderRepository repo;
    @Mock    PaymentGateway  payment;
    @InjectMocks OrderService service;

    @Test
    void createOrder_chargesPayment() {
        Order saved = new Order(1L, BigDecimal.TEN);
        when(repo.save(any())).thenReturn(saved);

        service.create(new CreateOrderRequest("c1", BigDecimal.TEN));

        verify(payment).charge(eq("c1"), eq(BigDecimal.TEN));
    }
}

// Slice test — only web layer loaded, service mocked
@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired  MockMvc        mvc;
    @MockBean   OrderService   service;
    @Autowired  ObjectMapper   mapper;

    @Test
    void getOrder_returns200() throws Exception {
        given(service.findById(1L)).willReturn(Optional.of(anOrder()));

        mvc.perform(get("/api/v1/orders/1")
                .with(jwt()))                         // SecurityMockMvcRequestPostProcessors
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.id").value(1))
           .andExpect(jsonPath("$.status").value("PENDING"));
    }
}

Team Lead Testing Standards
  • Treat @SpringBootTest as expensive — cache the context by sharing config across test classes (@SpringBootTest on a base class).
  • Testcontainers for database/broker tests — no more fragile H2 compatibility shims.
  • Aim for fast feedback: unit tests <100ms, slice tests <5s, integration tests <30s.
  • Test the behavior, not the implementation — assert on outcomes, not on which mock methods were called.
