1. Lambdas & Functional Interfaces Java 8

A lambda is a concise way to create an anonymous implementation of a @FunctionalInterface — an interface with exactly one abstract method.

Key Functional Interfaces

InterfaceMethodUse Case
Predicate<T>boolean test(T t)Filter / condition
Function<T,R>R apply(T t)Transform one type to another
BiFunction<T,U,R>R apply(T t, U u)Two inputs, one output
Consumer<T>void accept(T t)Side effect, no return
Supplier<T>T get()Provide a value, no input
UnaryOperator<T>T apply(T t)Same type in and out
BinaryOperator<T>T apply(T t1, T t2)Two same-type inputs, same output
Comparator<T>int compare(T o1, T o2)Ordering / sorting
// Lambda syntax forms () -> "hello" // no params x -> x * 2 // one param, expression body (x, y) -> x + y // two params (String s) -> { return s.length(); } // block body, explicit return // Method references — 4 types String::toUpperCase // instance method on type — s -> s.toUpperCase() "hello"::contains // instance method on object — s -> "hello".contains(s) String::new // constructor reference — s -> new String(s) Math::abs // static method reference — n -> Math.abs(n) // Custom @FunctionalInterface @FunctionalInterface interface TriFunction<A, B, C, R> { R apply(A a, B b, C c); } // Function composition Function<String, String> trim = String::trim; Function<String, String> upper = String::toUpperCase; Function<String, String> process = trim.andThen(upper); // trim then upper // compose() is reverse order: trim.compose(upper) = upper then trim

2. Streams API Java 8

Streams enable declarative, pipeline-style processing of data. They are lazy — intermediate operations execute only when a terminal operation is invoked.

Stream Pipeline

// Source → Intermediate ops (lazy) → Terminal op (triggers execution) List<String> result = employees.stream() // source .filter(e -> e.getSalary() > 50_000) // intermediate .map(Employee::getName) // intermediate .distinct() // intermediate .sorted() // intermediate .limit(10) // intermediate .collect(Collectors.toList()); // terminal

Collectors

// groupingBy — group employees by department Map<String, List<Employee>> byDept = employees.stream() .collect(Collectors.groupingBy(Employee::getDepartment)); // groupingBy with downstream — count per department Map<String, Long> countByDept = employees.stream() .collect(Collectors.groupingBy( Employee::getDepartment, Collectors.counting() )); // partitioningBy — split into true/false groups Map<Boolean, List<Employee>> seniorOrNot = employees.stream() .collect(Collectors.partitioningBy(e -> e.getYears() > 5)); // joining — collect strings String names = employees.stream() .map(Employee::getName) .collect(Collectors.joining(", ", "[", "]")); // [Alice, Bob, Carol] // toMap Map<Long, Employee> byId = employees.stream() .collect(Collectors.toMap( Employee::getId, e -> e, (e1, e2) -> e1 // merge function on duplicate key ));

flatMap & Reduce

// flatMap — flatten nested collections List<String> allSkills = employees.stream() .flatMap(e -> e.getSkills().stream()) // List<List<String>> → Stream<String> .distinct() .collect(Collectors.toList()); // reduce — custom aggregation int totalSalary = employees.stream() .mapToInt(Employee::getSalary) .reduce(0, Integer::sum); // Parallel streams — use for CPU-bound ops on large data long count = list.parallelStream() // uses ForkJoinPool.commonPool() .filter(s -> s.startsWith("A")) .count(); // WARNING: parallelStream has overhead; only faster for large datasets & stateless ops
Never use parallel streams with I/O operations or stateful lambdas. The common ForkJoinPool is shared — blocking it affects the entire JVM. Use a custom pool for blocking parallel work.

3. Optional Java 8

// Creating Optional Optional<String> name = Optional.of("Alice"); // throws NPE if null Optional<String> empty = Optional.empty(); // explicit empty Optional<String> safe = Optional.ofNullable(val); // null-safe // Consuming name.isPresent(); // true name.isEmpty(); // false (Java 11+) name.get(); // "Alice" — NoSuchElementException if empty name.orElse("default"); // value or default (always evaluated) name.orElseGet(() -> computeDefault()); // lazy — only computed if empty name.orElseThrow(() -> new NotFoundException()); // Transforming name.map(String::toUpperCase); // Optional<String> name.filter(s -> s.length() > 3); // Optional<String> name.flatMap(s -> findUser(s)); // avoids Optional<Optional<User>> name.ifPresent(s -> System.out.println(s)); // side effect if present name.ifPresentOrElse( // Java 9+ s -> System.out.println(s), () -> System.out.println("empty") );
Don't use Optional as a field type or method parameter — it's designed for return values only. Never call .get() without checking isPresent() — use orElse/orElseGet instead.

6. Records Java 16+

Records are immutable data carriers — the compiler auto-generates constructor, getters, equals(), hashCode(), and toString().

// Declare a record record Point(int x, int y) {} Point p = new Point(3, 4); p.x(); // accessor (not getX()) p.y(); p.toString(); // Point[x=3, y=4] p.equals(new Point(3, 4)); // true — value equality // Records with custom compact constructor — validates inputs record Range(int min, int max) { Range { // compact constructor — no parameter list if (min > max) throw new IllegalArgumentException("min > max"); } int size() { return max - min; } // custom instance method static Range of(int min, int max) { return new Range(min, max); } } // Records can implement interfaces record Money(BigDecimal amount, Currency currency) implements Comparable<Money> { public int compareTo(Money other) { return amount.compareTo(other.amount); } } // Records are implicitly final — can't extend them or extend records // All fields are final — records are inherently thread-safe

7. Sealed Classes Java 17

Sealed classes restrict which classes can extend or implement them, enabling exhaustive type checking.

sealed interface Shape permits Circle, Rectangle, Triangle {} record Circle(double radius) implements Shape {} record Rectangle(double w, double h) implements Shape {} non-sealed class Triangle implements Shape {} // open for extension // With pattern matching (Java 21 finalized) — compiler knows all subtypes double area(Shape shape) { return switch (shape) { case Circle c -> Math.PI * c.radius() * c.radius(); case Rectangle r -> r.w() * r.h(); case Triangle t -> triangleArea(t); // No default needed — compiler verifies all cases covered! }; }

8. Pattern Matching Java 16–21

// Pattern matching for instanceof (Java 16) // Old way: if (obj instanceof String) { String s = (String) obj; System.out.println(s.length()); } // New way — binding variable if (obj instanceof String s && s.length() > 5) { System.out.println(s.toUpperCase()); // s is scoped here } // Switch expressions (Java 14+) String result = switch (day) { case MON, TUE, WED, THU, FRI -> "Weekday"; case SAT, SUN -> "Weekend"; }; // Pattern matching in switch (Java 21) String desc = switch (obj) { case Integer i when i < 0 -> "negative int"; case Integer i -> "positive int: " + i; case String s -> "string: " + s; case null -> "null"; default -> "other"; };

9. Interview Q&A

What is the difference between map() and flatMap() in streams?
map(Function<T, R>) — applies a function to each element and returns a Stream<R>. One element in, one element out. If the function returns a collection/Optional/Stream, you get a Stream of collections.

flatMap(Function<T, Stream<R>>) — applies a function that returns a Stream per element, then flattens all those streams into one. One element in, zero or more elements out.

Analogy: map() is like translating each word in a book; flatMap() is like translating each word into multiple synonyms and returning all of them in a flat list.
When would you use a parallel stream and what are the pitfalls?
Use when: CPU-bound processing on large datasets (generally 10,000+ elements), stateless and independent operations, computationally expensive per-element work.

Pitfalls:
1. Overhead — fork/join overhead means parallel is SLOWER for small datasets
2. Shared state — mutating shared variables causes race conditions
3. Order sensitivity — if order matters, use forEachOrdered() (kills performance benefit)
4. Blocking I/O — uses ForkJoinPool.commonPool() which is shared; blocking starves the entire JVM
5. Non-associative reduce — subtraction, string concat with side effects give wrong results

Always benchmark. Parallel isn't always faster.
What are the advantages of records over Lombok @Data?
Records advantages: Language feature (no annotation processing), guaranteed immutability (all fields final), compact constructors for validation, transparent — what you see is what you get, no build tool configuration needed, works natively in switch pattern matching and sealed hierarchies.

Lombok @Data advantages: Mutable fields (can use @Setter), works in older Java, more customization, @Builder integration, can extend classes.

Use records for: Pure data holders, DTOs, value objects, command/query objects, API response models.

Use Lombok for: Mutable domain entities, Spring JPA entities (must have no-arg constructor + setters), cases requiring more flexibility.
What is the difference between orElse() and orElseGet() in Optional?
orElse(T other) — always evaluates the argument, even if the Optional is present. If computing the default is expensive (DB call, object creation), you pay that cost every time even when the Optional has a value.

orElseGet(Supplier<T>) — lazily evaluates the supplier ONLY when the Optional is empty. Always prefer this for expensive defaults.

Example: optional.orElse(expensiveComputation()) always runs expensiveComputation(). optional.orElseGet(() -> expensiveComputation()) only runs it when empty.
