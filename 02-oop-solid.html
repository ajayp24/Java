OOP & SOLID Principles

Mastering object-oriented design and SOLID principles is what separates engineers who write code from engineers who design systems. Essential for Team Lead interviews.

1. The Four Pillars of OOP

Encapsulation

Bundling data and the methods that operate on it, hiding internal state. Achieved via access modifiers.

public class BankAccount { private double balance; // hidden state public void deposit(double amount) { if (amount <= 0) throw new IllegalArgumentException("Amount must be positive"); balance += amount; // controlled mutation } public double getBalance() { return balance; } // controlled access }

Inheritance

A class can inherit fields and methods from a parent class, promoting code reuse. Java supports single inheritance for classes.

public abstract class Vehicle { protected String brand; public abstract void start(); public void displayBrand() { System.out.println(brand); } } public class Car extends Vehicle { @Override public void start() { System.out.println("Car engine started"); } }

Polymorphism

Compile-time (static): Method overloading — same name, different parameters. Runtime (dynamic): Method overriding — subclass provides specific implementation.

// Runtime polymorphism Vehicle v = new Car(); v.start(); // calls Car.start() — resolved at runtime // Compile-time polymorphism (overloading) public int add(int a, int b) { return a + b; } public double add(double a, double b) { return a + b; }

Abstraction

Hiding implementation details, exposing only what's necessary. Achieved through abstract classes and interfaces.

Use interface when you want to define a contract that unrelated classes can implement. Use abstract class when you have shared implementation or state that subclasses need.

3. SOLID Principles Overview

SOLID is a set of five design principles that make software easier to understand, maintain, and extend. Critical for Team Lead interviews.

S

Single Responsibility Principle

A class should have only ONE reason to change — it should do one thing well.

// VIOLATION — UserService does too many things class UserService { public void saveUser(User user) { ... } public void sendWelcomeEmail(User user) { ... } public void generateReport() { ... } public String formatUserXml(User user) { ... } } // FIX — separate responsibilities class UserRepository { public void save(User user) { ... } } class EmailService { public void sendWelcome(User user) { ... } } class UserReportService { public void generate() { ... } } class UserXmlSerializer { public String serialize(User u) { ... } }

Team Lead insight: SRP also applies at the method and module level. A 500-line class almost always violates SRP. During code review, I ask: "What is this class's single responsibility?" If the answer has "and" in it, it needs splitting.

O

Open/Closed Principle

Software entities should be OPEN for extension but CLOSED for modification. Add new behavior by adding new code, not changing existing code.

// VIOLATION — add new payment means modifying existing class class PaymentProcessor { public void pay(String type, double amount) { if (type.equals("CREDIT")) { /* credit logic */ } else if (type.equals("PAYPAL")) { /* paypal logic */ } // Adding CRYPTO requires modifying this class } } // FIX — open for extension via interface interface PaymentMethod { void pay(double amount); } class CreditCardPayment implements PaymentMethod { public void pay(double amount) { /* credit logic */ } } class PayPalPayment implements PaymentMethod { public void pay(double amount) { /* paypal logic */ } } // Adding CRYPTO: just create CryptoPayment implements PaymentMethod class PaymentProcessor { public void process(PaymentMethod method, double amount) { method.pay(amount); // never needs to change } }
L

Liskov Substitution Principle

Subtypes must be substitutable for their base types without altering program correctness. If S extends T, you should be able to use S wherever T is expected.

// VIOLATION — Square extends Rectangle breaks LSP class Rectangle { protected int width, height; public void setWidth(int w) { width = w; } public void setHeight(int h) { height = h; } public int area() { return width * height; } } class Square extends Rectangle { public void setWidth(int w) { width = height = w; } // breaks Rectangle contract! } // This breaks with Square: Rectangle r = new Square(); r.setWidth(5); r.setHeight(10); // Expected area: 50, Actual: 100 — LSP VIOLATED // FIX — use composition, not inheritance interface Shape { int area(); } class Rectangle implements Shape { ... } class Square implements Shape { ... } // separate, no false IS-A

LSP contract rules: Method signatures must be compatible (preconditions can't be stronger, postconditions can't be weaker). Invariants of the base class must be preserved. Exceptions thrown must be the same or subtypes of base class exceptions.

I

Interface Segregation Principle

Clients should not be forced to depend on interfaces they don't use. Prefer many small, specific interfaces over one large "fat" interface.

// VIOLATION — fat interface forces unnecessary implementation interface Worker { void work(); void eat(); void sleep(); } class Robot implements Worker { public void work() { /* works */ } public void eat() { throw new UnsupportedOperationException(); } // forced public void sleep() { throw new UnsupportedOperationException(); } // forced } // FIX — segregate into focused interfaces interface Workable { void work(); } interface Eatable { void eat(); } interface Sleepable { void sleep(); } class HumanWorker implements Workable, Eatable, Sleepable { ... } class Robot implements Workable { ... } // only what it needs
D

Dependency Inversion Principle

High-level modules should not depend on low-level modules — both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

// VIOLATION — OrderService directly depends on concrete MySQLRepository class OrderService { private MySQLOrderRepository repo = new MySQLOrderRepository(); // tight coupling public void placeOrder(Order o) { repo.save(o); } } // FIX — depend on abstraction (interface), inject concrete via DI interface OrderRepository { void save(Order order); Optional<Order> findById(long id); } class OrderService { private final OrderRepository repo; // depends on abstraction @Autowired // Spring injects the concrete implementation public OrderService(OrderRepository repo) { this.repo = repo; } public void placeOrder(Order o) { repo.save(o); } } // Now swap MySQL for Mongo, Redis, or in-memory for tests — zero OrderService changes class MySQLOrderRepository implements OrderRepository { ... } class MongoOrderRepository implements OrderRepository { ... } class InMemoryOrderRepository implements OrderRepository { ... } // for tests
Dependency Inversion is the foundation of Spring's Dependency Injection. Every @Autowired, @Inject, or constructor injection is DIP in action.

Interview Q&A

What is the difference between IS-A and HAS-A relationships?
IS-A (inheritance): A Dog IS-A Animal. Use when the subclass truly is a specialized form of the superclass and all behavior of the parent applies. Over-used inheritance is a code smell.

HAS-A (composition): A Car HAS-A Engine. Use when one class uses another's functionality. "Favor composition over inheritance" — it's more flexible, less coupled, and easier to test.

Rule of thumb: Ask "is this IS-A true in ALL scenarios and forever?" If any doubt, use composition. Example: Stack shouldn't extend Vector (it IS-A mistake in java.util) — it should compose a Vector.
Can you violate LSP while respecting all other SOLID principles?
Yes. You can have proper separation of responsibilities (SRP), use interfaces for extension (OCP), segregate interfaces (ISP), and inject dependencies (DIP) — but still violate LSP if your subclasses don't truly behave as substitutes for their base type.

LSP is often violated subtly: throwing exceptions the base doesn't, returning null where base returns empty collection, adding stronger preconditions. A good LSP check: write unit tests against the base type and run them on all subclasses — they should all pass.
As a Team Lead, how do you enforce SOLID principles in code reviews?
Practical checklist during review:
• SRP: "What does this class do?" — if answer has "and", flag it.
• OCP: "How would we add X feature?" — if answer is "modify this class", flag it.
• LSP: "Does this subclass truly substitute for the parent in all cases?"
• ISP: Any interface with more than 5-7 methods is a smell.
• DIP: Any 'new' keyword inside a service class for creating repositories/services — flag it.

I also run metrics tools (SonarQube, PMD) to catch violations automatically, and pair program with junior engineers on architectural decisions rather than just reviewing after the fact.
What is the difference between polymorphism and overloading?
Overloading (static/compile-time polymorphism): Same method name, different parameter lists. Resolved at compile time based on parameter types. Not true polymorphism in the OOP sense.

Overriding (runtime/dynamic polymorphism): Subclass provides specific implementation of inherited method. Resolved at runtime based on actual object type. This IS the foundation of OOP — enables writing code against abstractions, not implementations.

Example: Collections.sort(list) doesn't need to know whether list contains Strings, Integers, or custom objects — the compareTo() method resolves at runtime.
