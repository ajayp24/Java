Architecture

Microservice Architecture

Core

Microservices decompose a system into small, independently deployable services each owning a bounded context. The key architectural drivers are independent deployability (change one service without touching others), technology heterogeneity (each service picks its own stack), and organizational alignment (Conway's Law — your architecture mirrors your team structure). The tradeoffs are real: distributed systems introduce network failures, partial consistency, and operational overhead that a monolith simply doesn't have.

Monolith vs Microservices Monolith Microservices ┌──────────────────────┐ ┌───────────┐ ┌───────────┐ │ UI + API │ │ Order │ │ Inventory│ │ Order logic │ │ Service │ │ Service │ │ Inventory logic │ → └─────┬─────┘ └─────┬─────┘ │ Payment logic │ │ async │ │ User logic │ ┌─────┴─────┐ ┌─────┴─────┐ │ [shared DB] │ │ Payment │ │ User │ └──────────────────────┘ │ Service │ │ Service │ └───────────┘ └───────────┘ [each service owns its own DB]
Design Principles
  • Single Responsibility: one service = one bounded context. When a service grows past what a single team can own, split it.
  • Own your data: no shared databases between services — shared schema creates deployment coupling.
  • Design for failure: any downstream call can fail. Services must degrade gracefully (fallback, circuit break, retry).
  • API versioning: services evolve independently — clients must not break when a service changes its contract.
  • Strangler Fig: migrate a monolith incrementally — route traffic for one feature at a time to the new service; don't big-bang rewrite.
Distributed Monolith Anti-Pattern
  • Services that share a database, call each other synchronously for every request, or deploy in lockstep are a distributed monolith — all the complexity, none of the benefits.
  • Team lead red flag in code review: service A's repository imports service B's entity classes.

API Gateway

Core

An API Gateway is the single entry point for all client traffic. It handles cross-cutting concerns so individual services don't have to: routing, authentication/authorization, SSL termination, rate limiting, request aggregation, and response transformation. Spring Cloud Gateway is the standard Java implementation, built on Project Reactor (non-blocking).

JAVAGlobal JWT auth filter in Spring Cloud Gateway
@Component
public class JwtAuthFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders()
            .getFirst(HttpHeaders.AUTHORIZATION);

        if (token == null || !token.startsWith("Bearer ")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        // Validate JWT, extract claims, forward downstream as header
        Claims claims = jwtUtil.parse(token.substring(7));
        ServerHttpRequest mutated = exchange.getRequest().mutate()
            .header("X-User-Id", claims.getSubject())
            .build();
        return chain.filter(exchange.mutate().request(mutated).build());
    }

    @Override public int getOrder() { return -1; } // run before routing
}

Service Discovery

Important

In a dynamic environment where service instances start and stop, you can't hardcode IPs. A service registry keeps track of live instances. Instances register themselves on startup and heartbeat continuously; on failure they are evicted. Clients (or the gateway) look up the registry before each call. Eureka (Netflix/Spring Cloud) and Consul are the two most common choices; on Kubernetes, the cluster's DNS + Service objects serve the same role natively.

Communication

REST

Core

REST is the dominant synchronous HTTP API style. Key constraints: stateless (server holds no client session), uniform interface (HTTP verbs + resource URIs), cacheable (responses declare their cacheability). In a microservices context, REST is appropriate for query-heavy, request-response flows where the client needs an immediate answer. For high-throughput or fire-and-forget scenarios, asynchronous messaging is usually better.

REST API Design Rules
  • Resources, not verbs: /orders/{id} not /getOrder?id=. The HTTP method is the verb.
  • HTTP semantics: GET (idempotent read), POST (create/non-idempotent), PUT (idempotent full replace), PATCH (partial update), DELETE (idempotent delete).
  • Status codes matter: 200 OK, 201 Created (POST), 204 No Content (DELETE), 400 Bad Request, 401 Unauthenticated, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests, 503 Service Unavailable.
  • Versioning: URI versioning (/v1/orders) is most visible; header versioning (Accept: application/vnd.acme.v1+json) is more REST-pure but harder to debug.
  • HATEOAS: responses include links to related actions — useful for hypermedia APIs, overkill for internal service-to-service calls.
JAVAREST controller with ProblemDetail (RFC 7807) error responses
@RestController
@RequestMapping("/v1/orders")
public class OrderController {

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public OrderResponse create(@RequestBody @Valid CreateOrderRequest req) {
        return service.create(req);
    }

    @GetMapping("/{id}")
    public ResponseEntity<OrderResponse> get(@PathVariable Long id) {
        return service.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }
}

@RestControllerAdvice
public class ProblemDetailAdvice {
    // Spring 6 ProblemDetail — RFC 7807 structured error body
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail
            .forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, "Validation failed");
        pd.setProperty("errors", ex.getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage())
            .toList());
        return pd;
    }
}

gRPC

Important

gRPC is a high-performance RPC framework using Protocol Buffers for serialization and HTTP/2 for transport. Compared to REST+JSON: ~5–10× smaller payload (binary), multiplexed connections (no head-of-line blocking), and strict contract-first design via .proto files. Ideal for internal service-to-service calls, especially high-throughput data streams. Less suitable for browser clients without gRPC-Web proxying.

JAVAgRPC server impl (grpc-spring-boot-starter)
@GrpcService
public class OrderGrpcService extends OrderServiceGrpc.OrderServiceImplBase {

    @Override
    public void getOrder(GetOrderRequest req, StreamObserver<OrderResponse> resp) {
        orderRepo.findById(req.getId())
            .ifPresentOrElse(
                o -> { resp.onNext(toProto(o)); resp.onCompleted(); },
                () -> resp.onError(Status.NOT_FOUND.asRuntimeException())
            );
    }

    @Override
    public void listOrders(ListOrdersRequest req, StreamObserver<OrderResponse> resp) {
        orderRepo.findByCustomerId(req.getCustomerId())
            .forEach(o -> resp.onNext(toProto(o)));   // streams each row
        resp.onCompleted();
    }
}
Messaging

Apache Kafka

Important

Kafka is a distributed, durable, high-throughput event log. Messages are appended to partitions (ordered within a partition) and retained for a configurable period — consumers replay from any offset. This makes Kafka fundamentally different from a queue: messages are not deleted on consumption, and multiple consumer groups can read the same data independently. It excels at event streaming, audit logs, and decoupling high-volume producers from consumers.

Kafka Concepts
  • Topic: named log, divided into partitions. More partitions = more parallelism.
  • Partition: ordered, immutable sequence. Messages with the same key go to the same partition — ordering guaranteed per key.
  • Consumer Group: each partition assigned to one consumer in the group. Scale consumers up to partition count.
  • Offset: position in a partition. Consumer commits offset after processing — on restart, it resumes from the committed offset.
  • at-least-once delivery: default. Commit after processing, never before — if processing fails before commit, message is redelivered. Idempotent consumers required.
  • exactly-once: achievable with Kafka transactions (enable.idempotence=true + transactional producer). More complex, avoid unless strictly needed.
JAVASpring Kafka producer + consumer with manual offset commit
// Producer — publish order event
@Service
public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderEvent> kafka;

    public void publish(OrderEvent event) {
        kafka.send("orders", event.getOrderId(), event)  // key → same partition
             .whenComplete((result, ex) -> {
                 if (ex != null) log.error("Publish failed", ex);
             });
    }
}

// Consumer — at-least-once, manual commit after processing
@KafkaListener(topics = "orders", groupId = "inventory-group",
               containerFactory = "manualAckFactory")
public void handle(ConsumerRecord<String, OrderEvent> record,
                    Acknowledgment ack) {
    try {
        inventory.reserve(record.value());
        ack.acknowledge();                 // commit only after success
    } catch (Exception e) {
        log.error("Failed to process {}", record.offset(), e);
        // do NOT ack → Kafka redelivers; or forward to DLQ
    }
}
Messaging

RabbitMQ

Important

RabbitMQ is a traditional message broker: producers publish to exchanges, exchanges route messages to queues via binding rules, consumers pull from queues. Messages are consumed and removed — no replay. RabbitMQ excels at task distribution, work queues, and complex routing (topic, fanout, direct, headers exchanges). Choose Kafka for event streaming / replay; choose RabbitMQ for task queues, routing, and RPC-style messaging.

    throws IOException {
    try {

        channel.basicAck(tag, false);
    } catch (Exception e) {
        channel.basicNack(tag, false, false); // requeue=false → DLQ
    }
}

Event-Driven Architecture

Advanced

In event-driven architecture (EDA), services communicate by publishing and subscribing to domain events — immutable facts about things that happened. Producers don't know who listens; consumers don't know who produced. This achieves temporal decoupling (consumer can be offline) and spatial decoupling (no hardcoded endpoint). The cost is eventual consistency and harder debugging.

Event Design Rules
  • Events are facts, not commands: OrderPlaced (happened) vs PlaceOrder (request). A fact cannot be rejected; a command can.
  • Include enough data: events should be self-contained — consumers shouldn't need to call back to the producer to enrich them (avoids temporal coupling).
  • Event schema versioning: add fields, never remove or rename. Use a schema registry (Confluent Schema Registry + Avro/Protobuf) to enforce compatibility.
  • Consumer idempotency: at-least-once delivery means events may arrive twice — consumers must handle duplicates gracefully (deduplication by event ID).

Saga Pattern

Pattern

A Saga manages a multi-step business transaction across services where each step has a corresponding compensating transaction. If step N fails, steps N-1 through 1 are compensated (rolled back) in reverse. There are two implementations: Choreography (services emit events, react to others' events — no central coordinator) and Orchestration (a central Saga orchestrator sends commands and waits for replies — easier to reason about, avoids cyclic event dependencies).

ChoreographyOrchestration
ControlDistributed — each service reacts to eventsCentralized — orchestrator drives the flow
CouplingServices know about each other's eventsOnly orchestrator knows the full flow
DebuggingHard — trace events across servicesEasier — single orchestrator tracks state
ToolsAny event brokerAxon Framework, Temporal, Conductor
JAVAChoreography-based Saga — OrderService step + compensating event
// Step 1: Order service publishes OrderPlaced
@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    Order order = repo.save(new Order(cmd, OrderStatus.PENDING));
    outbox.publish(new OrderPlaced(order));  // Outbox pattern (see next section)
    return order;
}

// Step 2: Inventory service listens, reserves stock, publishes result
@KafkaListener(topics = "orders")
public void onOrderPlaced(OrderPlaced event) {
    try {
        inventory.reserve(event.items());
        outbox.publish(new StockReserved(event.orderId()));
    } catch (InsufficientStockException e) {
        // Compensate: tell order service to cancel
        outbox.publish(new StockReservationFailed(event.orderId(), e.getMessage()));
    }
}

// Step 3: Order service compensates on failure
@KafkaListener(topics = "inventory")
public void onStockFailed(StockReservationFailed event) {
    orderService.cancelOrder(event.orderId(), event.getReason());
}

Outbox Pattern

Pattern

The Outbox pattern solves the dual-write problem: you can't atomically write to a database and publish to Kafka in the same transaction — if the publish fails, you have a committed DB record with no event, or vice versa. The fix: write the event to an outbox table in the same DB transaction as the business data, then a separate relay process reads unpublished outbox rows and publishes them to Kafka. Atomicity is guaranteed by the local DB transaction.

Outbox Pattern Flow Application (one DB transaction) Relay Process Kafka ┌────────────────────────────────┐ ┌───────────┐ ┌────────┐ │ INSERT INTO orders … │ │ │ │ │ │ INSERT INTO outbox │ │ poll │ │ │ │ (event_type, payload, │──────────────► unpublished───►│ orders │ │ published_at = NULL) │ │ outbox │ │ topic │ │ COMMIT │ │ rows │ │ │ └────────────────────────────────┘ │ mark │ └────────┘ │ published│ └───────────┘ Atomicity guaranteed by local DB TX Relay may publish twice → consumers must be idempotent
SQL + JAVAOutbox table + transactional write + relay
-- Outbox table
CREATE TABLE outbox (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_id VARCHAR(36) NOT NULL,
    event_type   VARCHAR(100) NOT NULL,
    payload      JSONB NOT NULL,

JAVAAtomic write + scheduled relay
@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    Order order = orderRepo.save(new Order(cmd));
    // Same TX — if commit fails, outbox row also not saved
    outboxRepo.save(OutboxEvent.of("OrderPlaced", order.getId(), order));
    return order;
}

// Relay — runs every 1s, publishes unpublished rows
@Scheduled(fixedDelay = 1000)
@Transactional
public void relay() {
    outboxRepo.findTop100ByPublishedAtIsNull().forEach(event -> {
        kafka.send(event.getEventType(), event.getAggregateId(), event.getPayload());
        event.setPublishedAt(Instant.now());   // mark published
    });
}

CQRS

Pattern

CQRS (Command Query Responsibility Segregation) separates the write model (commands that change state) from the read model (queries that return data). The read model can be a denormalized, query-optimized projection — a separate table, Elasticsearch index, or Redis cache — updated asynchronously from the write side. This removes the contention between heavy reads and writes sharing the same data model, at the cost of eventual consistency between write and read models.

CQRS with Event Sourcing Commands Events Client ──────────► Command Handler ──────────► Event Store ─────────► Event Bus (validates, applies) (append-only) │ │ Queries ▼ Client ◄────────── Query Handler ◄────────── Read Model ◄──────── Projector (thin read layer) (denormalized, (updates Postgres/ES/Redis) read DB)
JAVALightweight CQRS — separate read projection updated by event consumer
// Write model — normalized, command-optimized
@Entity
public class Order { /* normalized domain entity */ }

// Read model — denormalized, query-optimized (separate table)
@Entity
@Table(name = "order_summary_view")
public class OrderSummaryView {
    @Id private Long orderId;
    private String  customerName;  // denormalized from customer service
    private int     lineCount;
    private BigDecimal total;
    private String  statusLabel;
}

// Projector — updates read model when events arrive
@KafkaListener(topics = {"orders", "customers"})
public void project(DomainEvent event) {
    switch (event) {
        case OrderPlaced   e -> summaryRepo.create(e);
        case OrderUpdated  e -> summaryRepo.update(e);
        case CustomerRenamed e -> summaryRepo.updateCustomerName(e);
        default -> {}
    }
}

// Query handler — reads from optimized read model (no JOIN, no lock)
@GetMapping("/orders")
public Page<OrderSummaryView> list(Pageable p) {
    return summaryRepo.findAll(p);
}
Resilience

Circuit Breaker

Resilience

A circuit breaker wraps remote calls and monitors for failures. When failure rate exceeds a threshold, the circuit opens — subsequent calls immediately return a fallback without hitting the downstream service, allowing it time to recover. After a wait period, the circuit enters half-open: a probe request is allowed through. If it succeeds, the circuit closes; if it fails, it opens again. Resilience4j is the standard Java library (replacing the deprecated Hystrix).

Circuit Breaker State Machine failure rate > threshold probe succeeds CLOSED ────────────────────────────► OPEN ──────────────────► HALF-OPEN (normal) all calls fail fast (wait) probe sent (test) ▲ │ │ probe fails │ └────────────────────────────────────────────────────────────────┘ re-opens
JAVAResilience4j circuit breaker + fallback
// application.yml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        slidingWindowSize: 10           # evaluate last 10 calls
        failureRateThreshold: 50         # open if 50% fail
        waitDurationInOpenState: 10000   # wait 10s before half-open
        permittedNumberOfCallsInHalfOpenState: 3
        slowCallDurationThreshold: 2000  # 2s = slow call
        slowCallRateThreshold: 50
JAVA@CircuitBreaker with fallback method
@Service
public class OrderService {

    @CircuitBreaker(name = "inventory", fallbackMethod = "stockFallback")
    @Retry(name = "inventory")
    public StockLevel checkStock(String sku) {
        return inventoryClient.getStock(sku);
    }

    // Fallback: return cached/default value when circuit is open
    private StockLevel stockFallback(String sku, Throwable t) {
        log.warn("Stock check failed for {}: {}", sku, t.getMessage());
        return StockLevel.unknown(sku);   // degrade gracefully
    }
}
Resilience

Retry

Resilience

Retries handle transient failures — network hiccups, brief service restarts, momentary DB lock timeouts. The key constraints: retry only idempotent operations (safe to execute multiple times), use exponential backoff with jitter (prevent thundering herd when many clients retry simultaneously), and always set a max attempts limit. Never retry indefinitely and never retry without backoff — uncontrolled retries amplify failure.

Retry Design Rules
  • Only retry transient errors: retry ConnectTimeout, ServiceUnavailable (503). Never retry 400 Bad Request or 404 — those won't change.
  • Exponential backoff: wait = base * 2^attempt. Without backoff, all retrying clients hit the recovering service simultaneously.
  • Jitter: add random variance to backoff to spread retries in time (AWS: full jitter = random(0, base * 2^attempt)).
  • Retry budget: track retries as a percentage of total calls. If >10% of calls are retries, it signals a deeper problem — alert on it.
JAVAResilience4j retry with exponential backoff + Spring @Retryable
// application.yml — Resilience4j retry
resilience4j:
  retry:
    instances:
      inventory:
        maxAttempts: 3
        waitDuration: 500ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2   # 500ms → 1s → 2s
        randomizedWaitFactor: 0.3         # ±30% jitter
        retryExceptions:
          - feign.RetryableException
          - java.net.ConnectException
        ignoreExceptions:
          - com.acme.BadRequestException   # don't retry 4xx

// Spring @Retryable alternative (spring-retry)
@Retryable(
    retryFor = { ConnectException.class, ServiceUnavailableException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 500, multiplier = 2, random = true)
)
public StockLevel checkStock(String sku) { ... }

@Recover
public StockLevel stockRecover(ServiceUnavailableException e, String sku) {
    return StockLevel.unknown(sku);   // called after all retries exhausted
}

Rate Limiting

Resilience

Rate limiting protects a service from being overwhelmed by too many requests — from a single misbehaving client, a traffic spike, or a DDoS. Applied at the gateway for external clients; also applied within services to throttle downstream calls. Common algorithms: Token Bucket (burst allowed up to bucket size), Fixed Window Counter (count requests per minute, simple but allows burst at window boundary), Sliding Window (smoother, no boundary burst), Leaky Bucket (output at fixed rate, smooths bursts).

            .header("Retry-After", "60")
            .build();
    }
    return ResponseEntity.ok(service.process(req));
}

Idempotency

Resilience

An operation is idempotent if executing it multiple times has the same effect as executing it once. Critical in distributed systems where retries are inevitable — a payment charged twice is catastrophic. HTTP GET, PUT, DELETE are semantically idempotent. POST is not — but can be made idempotent with an Idempotency-Key header: the server stores the result of the first call and returns the cached result on duplicates.

JAVAIdempotency key pattern — store first result, return cached on replay
-- Idempotency key table
CREATE TABLE idempotency_keys (

    status_code INT NOT NULL,
    response    JSONB NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_idem_created ON idempotency_keys (created_at);
-- Expire keys after 24h via scheduled job or TTL trigger
JAVAIdempotency filter — intercepts before controller, returns cached response
@Component
public class IdempotencyFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                      HttpServletResponse res,
                                      FilterChain chain)
            throws IOException, ServletException {

        String key = req.getHeader("Idempotency-Key");
        if (key == null || !req.getMethod().equals("POST")) {
            chain.doFilter(req, res); return;
        }

        Optional<IdempotencyRecord> cached = idemRepo.findById(key);
        if (cached.isPresent()) {
            IdempotencyRecord r = cached.get();
            res.setStatus(r.getStatusCode());
            res.setContentType("application/json");
            res.getWriter().write(r.getResponse());  // replay cached response
            return;
        }

        CachedBodyResponseWrapper wrapper = new CachedBodyResponseWrapper(res);
        chain.doFilter(req, wrapper);

        // Store result for future replays
        idemRepo.save(new IdempotencyRecord(key, wrapper.getStatus(), wrapper.getBody()));
    }
}
Consumer Idempotency (Kafka / RabbitMQ)
  • At-least-once delivery means duplicate messages are expected. Consumers must deduplicate by a stable message ID before processing.
  • Pattern: INSERT INTO processed_events (event_id) ON CONFLICT DO NOTHING — if insert succeeds, process; if conflict, skip.
Consistency

Distributed Transactions

Advanced

True distributed transactions (2PC / XA) are largely abandoned in microservices — they require all participants to be available simultaneously, create long-held locks, and are operationally fragile. Instead, the industry uses patterns that accept eventual consistency: the Saga pattern, Outbox, and idempotent retry. If you need strong consistency across services, you may need to rethink your service boundaries — shared data may belong in the same service.

CAP Theorem in Interviews
  • A distributed system can only guarantee two of: Consistency, Availability, Partition Tolerance. Partition tolerance is non-negotiable in a real network — so the real choice is CP (consistent, may be unavailable during partition) vs AP (available, may return stale data during partition).
  • Most microservice systems choose AP — they accept eventual consistency in exchange for availability. Say this explicitly in an interview when asked about distributed data.

Distributed Tracing

Advanced

A single user request may touch 10 services. Distributed tracing correlates all spans across services into one trace, giving you end-to-end latency, identifying which service is slow, and showing the causal relationship between operations. The industry standard is OpenTelemetry (OTel): one API, pluggable exporters (Jaeger, Zipkin, Grafana Tempo, AWS X-Ray). Spring Boot 3 integrates OTel via Micrometer Tracing.

Observability Stack — The Three Pillars
  • Metrics: Micrometer → Prometheus → Grafana. What is happening at aggregate level (error rate, latency p99, queue depth).
  • Logs: structured JSON via Logback/Log4j2 → Loki or Elasticsearch. What happened for a specific request. Include traceId in every log line.
  • Traces: OpenTelemetry → Grafana Tempo / Jaeger. How a request flowed across services and where time was spent.
  • Team lead tip: correlate all three by traceId. A Grafana alert fires on high error rate → click to trace → trace links to logs. That's the loop.
