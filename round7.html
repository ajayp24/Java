Cloud & DevOps

Cloud and DevOps questions test whether you understand not just what services exist, but when to use each one, what the trade-offs are, and how to integrate them with Java/Spring Boot applications. Focus on the why behind each choice — interviewers want to know if you've actually operated systems in production, not just read the docs.

Compute

EC2

Core

EC2 provides virtual servers you control fully. You manage OS, runtime, and software. Use it when you need full control, a specific OS configuration, or when your workload doesn't fit the container/serverless model (e.g., GPU instances, bare-metal needs, licensed software).

Pricing ModelDiscountUse Case
On-Demand0%Variable/unpredictable load, short-term
Reserved (1yr)~40%Steady-state production workloads
Reserved (3yr)~60%Long-term baseline compute
Spot~70-90%Fault-tolerant batch jobs, Kafka consumers
Savings Plans~40-66%Flexible commitment (any region/instance family)
Key Concepts
  • Instance types: t3 (burstable, cheap, dev/test), m5 (general-purpose, production), c5 (compute-optimized, CPU-intensive apps), r5 (memory-optimized, in-memory DBs).
  • Auto Scaling Groups: maintain N instances, scale on CPU/custom metrics. Use min/desired/max capacity. ALB distributes traffic; health checks replace failed instances automatically.
  • Launch Template: defines AMI, instance type, security groups, user-data script (bootstrapping). Prefer Launch Templates over Launch Configurations (deprecated).
  • User data: runs as root on first boot. Install Java, pull your JAR from S3, start the service. Use Systems Manager Parameter Store for secrets in user-data — never hardcode.
  • EC2 vs containers: EC2 = you manage everything. Containers (ECS/EKS) = you manage apps, AWS manages compute placement. For Spring Boot, containers are almost always better than raw EC2 today.
Compute

ECS — Elastic Container Service

Core

ECS is AWS's managed container orchestrator. You define tasks (container specs) and services (desired count, load balancer, auto-scaling). ECS handles scheduling containers onto infrastructure — either EC2 instances you manage, or Fargate (fully managed). ECS is simpler than Kubernetes and tightly integrated with the AWS ecosystem.

ECS Hierarchy Cluster (logical grouping of resources) └── Service (maintains desired count, links to ALB target group) └── Task (one running instance of a Task Definition) └── Container(s) (Docker containers, share network/storage namespace) Task Definition (like a docker-compose file): { image: "myapp:1.2", cpu: 512, memory: 1024, portMappings: [{containerPort: 8080}], environment: [{name: "SPRING_PROFILES_ACTIVE", value: "prod"}], secrets: [{name: "DB_PASSWORD", valueFrom: "arn:aws:ssm:..."}] }
Spring Boot on ECS
  • Health checks: configure ALB health check on /actuator/health. ECS replaces unhealthy tasks automatically — Spring Actuator makes this trivial.
  • Secrets: inject from AWS Secrets Manager or SSM Parameter Store as environment variables via the Task Definition secrets field. Never bake secrets into your Docker image.
  • Rolling deployments: ECS replaces tasks one at a time by default. Configure minimumHealthyPercent: 100 and maximumPercent: 200 for zero-downtime deploys.
  • Service Auto Scaling: scale based on ALB Request Count per Target or CPU/memory metrics. Works well for Spring Boot services with predictable per-request CPU usage.
  • ECS vs EKS: ECS is simpler, AWS-native, lower operational overhead. EKS is Kubernetes — more portable, richer ecosystem, more complex. Use ECS unless you need Kubernetes-specific features or multi-cloud portability.
Compute

EKS — Elastic Kubernetes Service

Important

EKS runs managed Kubernetes control plane. AWS handles etcd, API server, and control plane HA — you manage worker nodes (or use Fargate for fully serverless). Use EKS when you need Kubernetes-native features: Helm charts, CRDs, advanced scheduling, or when moving workloads across AWS/GCP/Azure.

Key Kubernetes Concepts for Java TL
  • Pod: smallest deployable unit. One JVM = one container = one pod (typically). Resources: requests (scheduling), limits (enforcement). Set JVM heap < container memory limit or you'll get OOMKilled.
  • Deployment: declares desired pod count and rolling update strategy. Manages ReplicaSet under the hood. kubectl rollout undo rolls back to previous ReplicaSet.
  • Service: stable virtual IP for a set of pods. Types: ClusterIP (internal), NodePort (debug), LoadBalancer (creates AWS NLB). Use ALB Ingress Controller for HTTP routing instead.
  • ConfigMap / Secret: inject config without rebuilding images. spring.config.import=configtree:/etc/config/ reads a ConfigMap volume as Spring properties.
  • HPA (Horizontal Pod Autoscaler): scales pod count based on CPU, memory, or custom metrics (Kafka consumer lag via KEDA is common for Java consumers).
  • Node groups: mix On-Demand nodes for baseline + Spot nodes for bursty workloads. Use taints and tolerations to control which pods land where.
JVM on Kubernetes — Common Mistakes
  • JVM reads host CPU count, not container CPU. Add -XX:ActiveProcessorCount=N or use JDK 17+ which is container-aware.
  • JVM default heap is 1/4 of host RAM. Set -Xmx to ~75% of the container memory limit, not the node's total RAM.
  • Use -XX:+UseContainerSupport (default in JDK 10+) to respect cgroup limits.

Fargate

Important

Fargate is serverless compute for containers — no EC2 instances to manage. You define CPU and memory per task; AWS provisions the underlying infrastructure invisibly. Works with both ECS and EKS. Pay per vCPU-second and GB-second used, not per idle instance.

Compute

Lambda

Core

Lambda runs code in response to events with no server management. You provide a function; AWS handles scaling to thousands of concurrent executions. The execution model is stateless, ephemeral (15 min max), and billed per 100ms. Not suitable for long-running connections (WebSocket servers, Kafka consumers) but excellent for event-driven glue code.

TriggerUse Case
API Gateway / ALBServerless HTTP API (Spring Cloud Function)
S3 eventImage processing, virus scan on upload
SQSMessage processing with auto-scaling
EventBridgeScheduled jobs (cron), cross-service events
DynamoDB StreamsReact to DB changes, fan-out to other services
Kafka / MSKBatch consumer (small events, not high-throughput)
Java Lambda Best Practices
  • Cold start: JVM cold start is 1-3s. Mitigate with: SnapStart (Firecracker memory snapshot on publish), Provisioned Concurrency (pre-warmed instances, extra cost), or GraalVM native image (via Spring Native).
  • Handler class: implement RequestHandler<I,O>. Keep the handler thin — delegate to a service class that can be tested without AWS SDK. Static initialization happens once per container lifetime (reused across warm invocations).
  • Memory setting: Lambda allocates CPU proportional to memory. Counterintuitively, giving Java 1024MB instead of 512MB often makes functions faster AND cheaper (lower duration). Test both.
  • Lambda vs ECS/EC2: Lambda excels at event-driven, stateless, infrequent invocations. Persistent connections (DB connection pooling, WebSockets, Kafka consumers) belong on ECS/EC2 — Lambda can't hold them efficiently.
Data

S3 — Simple Storage Service

Core

S3 is object storage — immutable blobs addressed by bucket + key. 11 nines durability, essentially unlimited scale. The mental model: S3 is a global key-value store where values are arbitrary binary data. It is not a file system (no random-access writes, no append, no true directories).

Interview Must-Knows
  • Storage classes: Standard (frequent access, high availability) → Standard-IA (infrequent, 30-day minimum) → Glacier Instant (millisecond retrieval, archival) → Glacier Deep Archive (12h retrieval, cheapest). Use Lifecycle Policies to auto-transition objects.
  • Presigned URLs: generate a time-limited, signed URL that lets a client upload or download directly without going through your servers. Expires in 15 min–7 days. Essential for large file uploads — never proxy large files through your app.
  • Versioning: once enabled, overwriting a key creates a new version rather than deleting the old one. Enables rollback and protects against accidental deletion. Required before enabling MFA Delete.
  • Event notifications: trigger SQS, SNS, or Lambda on PutObject/DeleteObject. Primary pattern for file-upload processing pipelines.
  • Java SDK: S3Client (sync) or S3AsyncClient. Spring's ResourceLoader supports s3://bucket/key URIs via spring-cloud-aws.
  • Cross-region replication: auto-replicate objects to another region. Used for DR or bringing content closer to users. Works with versioning enabled on both buckets.

RDS — Relational Database Service

Core

RDS is managed relational databases: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server. AWS handles backups, patching, replication, and failover. You pick instance size, storage type, Multi-AZ, and read replicas. Aurora is AWS's optimized cloud-native engine (compatible with MySQL/Postgres) with higher throughput and automatic storage scaling.

Spring Boot + RDS
  • Connection string: use RDS Proxy between your app and RDS. Proxy pools connections at the AWS layer — critical for Lambda (which can't maintain persistent connections) and helps prevent connection storms on ECS restart bursts.
  • Credentials: use IAM database authentication (no password, short-lived token) or rotate credentials via Secrets Manager auto-rotation. Spring Cloud AWS can fetch DB credentials from Secrets Manager automatically.
  • Read replicas: point your Spring DataSource read-only transactions to the replica endpoint. Spring's @Transactional(readOnly=true) routes to replica with AbstractRoutingDataSource.
  • Parameter Groups: tune PostgreSQL parameters (max_connections, shared_buffers, log_min_duration_statement) without SSH access to the instance.
Data

DynamoDB

Important

DynamoDB is a fully managed NoSQL key-value + document database with single-digit millisecond latency at any scale. The entire data model is designed around access patterns known upfront — unlike relational DBs where you add indexes later. Getting the partition key wrong kills your throughput and is expensive to fix in production.

Data Modeling Principles
  • Primary key: partition key (PK) alone, or PK + sort key (SK). All queries must specify PK exactly. SK enables range queries within a partition. Design PK to distribute load evenly — no hot partitions.
  • Single-table design: store multiple entity types in one table. PK = "USER#123", SK = "PROFILE". PK = "USER#123", SK = "ORDER#2024-01". GSIs (Global Secondary Indexes) provide alternate access patterns. Reduces costs and complexity vs multiple tables.
  • GSI: Global Secondary Index — project attributes into an index with a different PK/SK. Enables "query by email" when your table is keyed by userId. GSIs have eventual consistency and separate capacity.
  • Capacity modes: On-Demand (pay per request, auto-scales, ~6x more expensive at steady state) vs Provisioned (set RCU/WCU, cheaper, can burst to 2x for 300s). Use On-Demand for variable/new workloads; switch to Provisioned once traffic is predictable.
  • DynamoDB Streams: ordered stream of item changes (like CDC). Trigger Lambda for event-driven patterns. Each shard → one Lambda concurrent invocation; processing is in order within a partition.
  • Java SDK: use DynamoDB Enhanced Client (DynamoDB Mapper replacement). Annotate POJOs with @DynamoDbBean, @DynamoDbPartitionKey. Works well with Spring Boot.
Messaging

SQS — Simple Queue Service

Core

SQS is a managed message queue (point-to-point). Producers enqueue messages; consumers poll and delete them. SQS handles durability, at-least-once delivery, and visibility timeout (message is hidden while being processed; requeued if not deleted in time). No message ordering by default — use FIFO queues when order matters.

Standard QueueFIFO Queue
ThroughputUnlimited (effectively)3,000 messages/sec with batching
OrderingBest-effort (not guaranteed)Exactly-once delivery within a group
DeduplicationConsumer must handle duplicates5-minute deduplication window
Use caseFan-out, high throughput, idempotent consumersFinancial transactions, ordered workflows
Key Patterns
  • Visibility timeout: when a consumer receives a message, it's hidden for N seconds. Consumer must process and delete before timeout, or SQS makes it visible again for retry. Set timeout to 2× your expected processing time.
  • Dead-letter queue (DLQ): after N failed processing attempts, message moves to DLQ. Monitor DLQ depth as an alarm — non-zero DLQ means your consumer has a bug. Use DLQ to inspect and replay failed messages.
  • Spring Integration: @SqsListener (spring-cloud-aws). Annotate a method and Spring creates a polling listener. Processes batches, handles ack/nack automatically.
  • Lambda trigger: SQS → Lambda auto-scales Lambda concurrency proportional to queue depth. Lambda polled by the service, not by your code. Each Lambda invocation receives up to 10 messages (batch size).
Messaging

SNS — Simple Notification Service

Core

SNS is a pub/sub service — one message to a topic is delivered to all subscribers simultaneously. Subscribers can be SQS queues, Lambda functions, HTTP endpoints, email, or SMS. The classic pattern is SNS → multiple SQS queues (fan-out): decouple producer from consumers, each consumer processes at its own pace.

SNS Fan-out Pattern Producer ──► SNS Topic: order.placed │ ┌───────┼────────────┬────────────────┐ ▼ ▼ ▼ ▼ SQS SQS SQS Email Inventory Shipping Notification Ops alert Service Service Service (SNS → email) consumer consumer consumer Each SQS queue can scale its consumer independently. Inventory slowness doesn't affect Shipping consumer.
SNS vs SQS vs Kafka
  • SNS: push to multiple subscribers now. No message retention. Subscriber must be online (SQS buffers if not). Best for fan-out notification patterns.
  • SQS: queue for one consumer group. Messages retained up to 14 days. Consumer polls at its own pace. Best for work queues and decoupling.
  • Kafka/MSK: distributed log. Multiple independent consumer groups each maintain their own offset. Messages retained for days/weeks. Replay from any point. Best for event streaming, audit logs, multiple independent consumers of the same events.
Messaging

Kafka / MSK

Important

Amazon MSK is managed Apache Kafka. Use MSK/Kafka when you need: multiple independent consumer groups reading the same events, long-term event retention (replay from days/weeks ago), strict ordering within a partition, or very high throughput (>100K messages/sec). MSK removes the Kafka broker management overhead.

Spring Boot + Kafka
  • Producer: KafkaTemplate<K,V>.send(topic, key, value). Use JSON serialization via JsonSerializer. Always set a message key when ordering matters — same key → same partition.
  • Consumer: @KafkaListener(topics="orders", groupId="shipping-svc"). Each consumer group gets its own cursor (offset). Two services with different groupIds both receive every message.
  • Partitions: parallelism = number of partitions. Max concurrent consumers per group = partition count. Set partitions at topic creation (adding partitions later breaks key-based ordering). Rule of thumb: start with 3× expected peak consumer count.
  • Offset management: default auto-commit risks losing in-flight messages on crash. Use manual ack with AckMode.MANUAL_IMMEDIATE and commit only after successful processing.
  • MSK-specific: IAM-based auth (no plaintext password). Use MSK Serverless for variable workloads; Provisioned for predictable high-throughput. Integrate via the MSK Bootstrap Server addresses from the AWS console.
Networking

VPC — Virtual Private Cloud

Core

A VPC is your private network in AWS. All compute resources launch inside a VPC. You define IP ranges (CIDR blocks), divide into subnets across AZs, and control traffic with Security Groups (stateful, instance-level) and NACLs (stateless, subnet-level).

Standard VPC Layout (3-tier) VPC: 10.0.0.0/16 │ ├── Public Subnets (one per AZ, /24) ← ALB, NAT Gateway, Bastion │ 10.0.1.0/24 (us-east-1a) │ 10.0.2.0/24 (us-east-1b) Route: 0.0.0.0/0 → Internet Gateway │ ├── Private Subnets (one per AZ, /24) ← ECS tasks, EC2, EKS nodes │ 10.0.11.0/24 (us-east-1a) │ 10.0.12.0/24 (us-east-1b) Route: 0.0.0.0/0 → NAT Gateway │ └── Data Subnets (one per AZ, /24) ← RDS, ElastiCache, MSK brokers 10.0.21.0/24 (us-east-1a) No route to internet (isolated) 10.0.22.0/24 (us-east-1b)
Security Model
  • Security Groups: stateful firewall attached to ENI (elastic network interface). Define inbound/outbound rules by port + source SG or CIDR. Best practice: allow traffic FROM a security group, not a CIDR. E.g., ECS task SG allows 5432 FROM RDS proxy SG.
  • NAT Gateway: allows private subnet resources to initiate outbound internet connections (Maven dependency downloads, Docker pulls, API calls) without accepting inbound connections. Place one per AZ for HA.
  • VPC Endpoints: private connections to AWS services (S3, DynamoDB, SQS) without leaving the AWS network. Eliminates NAT Gateway data transfer charges and reduces exposure. Critical for security-sensitive environments.
  • VPC Peering / Transit Gateway: connect two VPCs. Peering = 1:1 connection; Transit Gateway = hub for many-to-many VPC connections across accounts and regions.
Networking

ALB — Application Load Balancer

Core

ALB operates at Layer 7 (HTTP/HTTPS/WebSocket) and routes requests to target groups based on host header, path, query string, or HTTP method. It's the primary entry point for web applications on AWS — placed in public subnets, routing to private-subnet targets.

Key Features
  • Path-based routing: /api/users/* → User Service TG, /api/products/* → Product Service TG. One ALB can front multiple microservices without a separate API Gateway layer.
  • Target groups: can target EC2 instances, ECS tasks, Lambda functions, or IP addresses. Health check on each target — unhealthy targets removed from rotation automatically.
  • TLS termination: ALB handles HTTPS (certificate via ACM — free), forwards HTTP to internal targets. Never expose HTTP to the internet; always redirect 80 → 443 with an ALB listener rule.
  • WebSocket support: ALB supports WebSocket connections natively. Enable stickiness on the target group if your WS server is stateful (not recommended — prefer Redis for shared WS state).
  • WAF integration: attach AWS WAF to ALB to block OWASP Top 10, rate limit by IP, or allow-list specific user agents. First line of defense for public-facing APIs.
  • Access logs: enable ALB access logs to S3. Contains every request: timestamp, source IP, latency, target response. Essential for debugging production issues and capacity planning.
Networking

CloudFront

Important

CloudFront is AWS's CDN — 450+ edge locations cache content close to users. It reduces latency for static assets, images, and cacheable API responses. Also works as a security boundary: you can block all direct traffic to your ALB/S3 and only allow CloudFront IPs.

Key Patterns
  • Cache behaviors: different TTL per path. /static/* (immutable assets with content hash in filename) → TTL 1 year. /api/* → TTL 0 (no cache, pass-through). /images/* → TTL 24h with S3 origin.
  • Origins: S3 bucket (static hosting), ALB, API Gateway, or any HTTP endpoint. Use Origin Access Control (OAC) for S3: CloudFront signs requests to S3; S3 bucket policy denies all other origins.
  • Cache invalidation: on deploy, invalidate changed paths (/index.html). For versioned assets (hash in filename), no invalidation needed — old CDN URL simply isn't used anymore. Invalidations cost $0.005/path.
  • Lambda@Edge / CloudFront Functions: run code at edge nodes. Use for: auth token validation, request/response header manipulation, A/B testing, URL rewriting.
  • Signed URLs/Cookies: protect private content (behind-login images, premium video). CloudFront verifies a signature before serving. Generate signed URLs from your Spring Boot backend using CloudFront SDK.
Operations

CloudWatch

Core

CloudWatch is AWS's integrated observability service — metrics, logs, alarms, and dashboards. Every AWS service publishes metrics to CloudWatch automatically. You add application metrics and structured logs. CloudWatch Alarms trigger auto-scaling, SNS notifications, or Lambda functions when thresholds are breached.

Spring Boot Observability on AWS
  • Custom metrics: use Micrometer (Spring Boot Actuator's metric facade) with the CloudWatch registry (micrometer-registry-cloudwatch2). Metrics published as CloudWatch Custom Metrics every 60s. Create alarms on these for auto-scaling or pages.
  • Structured logging: log in JSON with a requestId / traceId field. CloudWatch Logs Insights queries JSON fields natively: filter level="ERROR" | stats count() by service.
  • Log groups + retention: set log group retention (30-90 days). Logs older than retention are deleted automatically — important for cost and compliance.
  • Composite Alarms: combine multiple metric alarms with AND/OR logic. Alert only when error rate is high AND latency is high (not just one) — reduces false positives.
  • CloudWatch Container Insights: automatic ECS/EKS metrics (CPU, memory, network per container) without any code changes. Enable in cluster settings. Replaces the need for node-level Prometheus for basic container metrics.
  • X-Ray integration: CloudWatch ServiceMap and traces powered by AWS X-Ray. Add the X-Ray Spring Boot starter for automatic trace instrumentation of HTTP calls, DynamoDB, SQS, etc.
Operations

IAM — Identity and Access Management

Core

IAM controls who (identity) can do what (action) on which AWS resources (resource). Critical principle: least privilege — grant only the exact permissions needed, nothing more. IAM mistakes are the #1 cause of AWS data breaches.

Key Concepts
  • IAM Roles vs Users: Users have long-lived credentials (access key ID + secret). Roles are assumed — short-lived STS credentials (1h default). Your ECS tasks, Lambda functions, and EC2 instances should always run with a Role, never with an IAM User's access key hardcoded.
  • IAM Role for ECS/Lambda: attach a task execution role to your ECS task or Lambda function. The AWS SDK automatically fetches credentials from the instance metadata endpoint — no configuration needed in your Spring Boot app. Works with spring-cloud-aws and standard AWS SDK.
  • Policy structure: { Effect: Allow, Action: ["s3:GetObject","s3:PutObject"], Resource: "arn:aws:s3:::my-bucket/*" }. Always scope Resource to the specific bucket/table — never use "*" in production.
  • Service Control Policies (SCPs): org-level guardrails that cap what any account or user can do, regardless of their own IAM permissions. E.g., prevent any account from disabling CloudTrail or creating resources outside approved regions.
  • OIDC-based CI/CD: GitHub Actions and other CI systems can assume IAM Roles via OIDC — no access keys stored in CI secrets. The CI system presents a token; AWS validates it against the registered OIDC provider and issues short-lived credentials. Best practice for all CI/CD pipelines in 2024.
Containers

Docker

Core

Docker packages an application and its runtime dependencies into a portable container image. Every container starts from an image; images are built via a Dockerfile. The container runtime (Docker/containerd) isolates processes via Linux cgroups and namespaces. Images are stored in registries (ECR, Docker Hub).

DOCKERFILESpring Boot multi-stage build
# Stage 1: extract layers from fat JAR
FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY target/myapp.jar myapp.jar
RUN java -Djarmode=layertools -jar myapp.jar extract

# Stage 2: lean runtime image
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
# Copy layers in order of how often they change
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./
# Non-root user
RUN addgroup -S app && adduser -S app -G app
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-XX:+UseContainerSupport", "-XX:MaxRAMPercentage=75", "org.springframework.boot.loader.JarLauncher"]
Best Practices
  • Layer caching: put rarely-changing layers (dependencies) before frequently-changing ones (application code). Spring Boot layered JARs exploit this optimally — dependency layer is cache-hit on 95% of builds.
  • Minimal base image: use JRE (not JDK) Alpine variants for smallest attack surface. JDK 21 allows custom JRE via jlink for even smaller images (30-50MB vs 200MB+).
  • Non-root user: always run the container as a non-root user. Containers that run as root can escalate privileges if the container runtime is misconfigured.
  • ECR lifecycle policies: auto-expire old image tags. Keep last 10 releases; delete everything older. Prevents unbounded ECR storage growth.
  • .dockerignore: exclude target/, .git/, *.md. Prevents sending large build context to the daemon.
Containers

Kubernetes

Important

Kubernetes orchestrates containerized workloads across a cluster of nodes. The control plane (API server, scheduler, etcd, controller manager) manages state; worker nodes run pods. You describe desired state in YAML manifests; Kubernetes continuously reconciles actual state toward desired state.

YAMLSpring Boot Deployment with resource limits
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:
    spec:
      containers:
      - name: user-service
        image: 123456789.dkr.ecr.us-east-1.amazonaws.com/user-service:1.2.3
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "250m", memory: "512Mi" }   # scheduling baseline
          limits:   { cpu: "1000m", memory: "1Gi" }   # enforcement ceiling
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
          initialDelaySeconds: 30
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8080 }
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: prod
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: db-secret, key: password }
Probes — Critical Distinction
  • Liveness probe: "Is the process alive?" If it fails, Kubernetes kills and restarts the pod. Use /actuator/health/liveness. Should only fail on unrecoverable states (deadlock, corrupt state). Never check DB connectivity here — a DB outage shouldn't restart all your pods.
  • Readiness probe: "Is this pod ready to receive traffic?" If it fails, Kubernetes removes the pod from the Service endpoints (no traffic sent) but does NOT restart it. Use /actuator/health/readiness. Check DB connection, cache availability here.
  • Startup probe: for slow-starting apps (JVM warm-up). Kubernetes waits for startup probe to succeed before starting liveness checks. Prevents killing a JVM that's still initializing Spring context.
CI/CD

Jenkins

Core

Jenkins is the most widely deployed open-source CI/CD server. Self-hosted, highly configurable via plugins, with a large ecosystem. Pipelines are defined in Jenkinsfile (Groovy DSL). Requires operational investment — Jenkins itself needs maintenance, scaling, and security patching. Suitable when you need maximum control or work in air-gapped environments.

GROOVYJenkinsfile — standard Java pipeline
pipeline {
  agent { docker { image 'eclipse-temurin:21' } }
  stages {
    stage('Test') {
      steps { sh 'mvn test -Dmaven.test.failure.ignore=false' }
      post { always { junit 'target/surefire-reports/*.xml' } }
    }
    stage('Build') {
      steps { sh 'mvn package -DskipTests' }
    }
    stage('Docker Push') {
      steps {
        withCredentials([usernamePassword(credentialsId: 'ecr-creds', ...)]) {
          sh 'docker build -t $IMAGE_NAME .'
          sh 'docker push $IMAGE_NAME'
        }
      }
    }
    stage('Deploy') {
      when { branch 'main' }
      steps { sh 'kubectl set image deployment/app app=$IMAGE_NAME' }
    }
  }
}
Jenkins vs Alternatives
  • Use Jenkins when: on-prem or air-gapped environment, existing large Jenkins investment, complex custom pipeline logic, need enterprise plugins (LDAP, SAML, RBAC).
  • Drawbacks: operational overhead (master HA, agent fleet management), Groovy DSL verbosity, plugin compatibility matrix, slow to adopt new features.
  • Jenkins on Kubernetes: use the Kubernetes plugin to spin up ephemeral pods as build agents. No need to maintain a static agent fleet — agents start fresh per build, scale to zero between builds.
CI/CD

GitHub Actions

Core

GitHub Actions is a cloud-native CI/CD platform integrated directly into GitHub. Workflows are YAML files in .github/workflows/. GitHub-hosted runners start fresh for each job — no maintenance. OIDC federation with AWS allows secure deployments without storing long-lived credentials.

YAML.github/workflows/deploy.yml
on:
  push: { branches: [main] }

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write    # required for OIDC
      contents: read
    steps:

SonarQube

Core

SonarQube is a continuous code quality and security analysis platform. It scans source code for bugs, code smells, vulnerabilities, and test coverage gaps. Integrated into CI — a Quality Gate blocks merges when quality metrics fall below defined thresholds. This is how you enforce code standards at scale without manual review checklists.

Key Concepts
  • Quality Gate: a set of conditions that must pass before code can merge or deploy. Typical gate: coverage on new code >80%, no new critical bugs, no new security hotspots unreviewed, new code duplication <3%.
  • Issue types: Bug (likely error in code, definite fix needed), Vulnerability (security flaw, exploitable), Code Smell (maintainability issue, technical debt), Security Hotspot (needs human review to determine if risky).
  • Maven integration: mvn sonar:sonar -Dsonar.projectKey=my-project -Dsonar.host.url=http://sonar:9000 -Dsonar.token=$SONAR_TOKEN. Runs after test phase — Sonar reads JaCoCo coverage reports.
  • PR decoration: SonarQube posts analysis results as comments on GitHub/GitLab PRs. Developers see issues inline in the PR review interface — no need to navigate to the SonarQube dashboard.
  • As a Team Lead: configure Quality Gates to match your team's standards. Start lenient (Coverage >60% on new code) and tighten over time. Don't block PRs with existing legacy debt — use the "new code" period concept so only changes are gated, not the entire codebase at once.
