Foundation

OOP Principles

Core

Java is built on four pillars: Encapsulation, Abstraction, Inheritance, and Polymorphism. As a Team Lead, you must not only define them but demonstrate how they reduce coupling, improve testability, and guide architectural decisions.

Key Points
  • Encapsulation — bundle data + behavior; expose only what's necessary via access modifiers (private, protected, public).
  • Abstraction — hide implementation details. Express what not how. Achieved via interfaces and abstract classes.
  • Inheritance — reuse and extend behavior. Java supports single class inheritance, multiple interface implementation.
  • Polymorphism — one interface, many forms. Compile-time (overloading) and runtime (overriding) variants.
  • SOLID principles extend these four into design guidance. Interviewers often move from "define OOP" to "explain SOLID" immediately.
JAVA Four Pillars — compact illustration 
// Encapsulation: private state, public contract
public class BankAccount {
    private BigDecimal balance;   // hidden

    public BigDecimal getBalance() { return balance; }
    public void deposit(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("Positive only");
        balance = balance.add(amount);
    }
}

// Abstraction: define the contract, hide the how
public interface PaymentGateway {
    PaymentResult charge(BigDecimal amount, String currency);
}

// Inheritance + Polymorphism: runtime dispatch
public class StripeGateway implements PaymentGateway {
    @Override
    public PaymentResult charge(BigDecimal amount, String currency) { /* ... */ }
}

PaymentGateway gw = new StripeGateway(); // polymorphism at work
gw.charge(BigDecimal.TEN, "USD");
Interview Focus — Team Lead Level
  • Be ready to connect each pillar to a real design decision you made.
  • "Favour composition over inheritance" — explain when inheritance breaks encapsulation.
  • Know SOLID cold: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
Foundation

Classes & Objects

Core

A class is a blueprint; an object is a heap-allocated instance. Understanding memory layout, constructor chaining, and the difference between static and instance context is essential for debugging subtle bugs in large codebases.

Key Points
  • Constructors are not inherited. this() chains to another constructor in the same class; super() calls the parent. Either must be the first statement.
  • Static members belong to the class (one copy), not instances. Static methods cannot access instance fields.
  • Initialization order: static blocks → static fields → instance blocks → constructor.
  • Inner classes: static nested (no outer reference), inner (holds outer ref), local (in method), anonymous (implements interface inline).
  • Object lifecycle: allocation → initialization → use → GC (when no more strong references).
JAVA Constructor chaining & initialization order 
public class Server {
    private static final int DEFAULT_PORT = 8080;
    private final int port;
    private final String host;

    // delegating constructor
    public Server() {
        this("localhost", DEFAULT_PORT); // must be first
    }

    public Server(String host, int port) {
        this.host = host;
        this.port = port;
    }

    // static factory — preferred over new in APIs
    public static Server localhost() { return new Server(); }
    public static Server at(String host, int port) { return new Server(host, port); }
}
Interview Focus
  • Prefer static factory methods over constructors — they have names, can return cached instances, and can return subtypes.
  • Explain when you'd use a Builder pattern vs telescoping constructors.

Interfaces & Abstract Classes

Core

This is one of the most common Team Lead interview questions. The distinction is deeper than syntax — it's about contractual capability (interface) vs partial implementation sharing (abstract class). Java 8+ blurred the line with default methods, so you need to articulate the remaining differences clearly.

AspectInterfaceAbstract Class
PurposeDefine capability/contractShare partial implementation
StateNo instance fields (only public static final)Instance fields allowed
ConstructorsNoneYes (called via super())
Multiple inheritanceYes — a class can implement manyNo — single parent class
Default methodsYes (Java 8+) — but prefer sparse useRegular methods with body

JAVA Interface default methods & abstract class 
public interface Auditable {
    String getCreatedBy();
    Instant getCreatedAt();

    // Default method — adds behaviour without breaking existing impls
    default String auditSummary() {
        return "Created by " + getCreatedBy() + " at " + getCreatedAt();
    }
}

// Abstract class: state + partial behaviour
public abstract class BaseEntity implements Auditable {
    private final UUID id = UUID.randomUUID();
    private final Instant createdAt = Instant.now();

    @Override public Instant getCreatedAt() { return createdAt; }
    // getCreatedBy() left abstract — subclass must provide
    public abstract String getCreatedBy();
}
Interview Focus
  • "Use interfaces to define what a type can do; use abstract classes to share how related types do it."
  • Know the diamond problem with default methods: when two interfaces define the same default, the implementing class must override it.
  • Marker interfaces (Serializable, Cloneable) vs annotation-based markers — discuss trade-offs.

Inheritance & Polymorphism

Core

Polymorphism in Java is primarily runtime (dynamic dispatch on overridden methods) vs compile-time (overloading resolved by the compiler). The JVM uses a virtual method table (vtable) for dispatch — overriding replaces the vtable entry; overloading creates a new entry.

Key Points
  • Overriding: same signature in subclass. Must have same or covariant return type, same or broader access, same or narrower checked exceptions.
  • Overloading: same name, different parameter types/count. Resolved at compile time by the declared type — not runtime type.
  • Liskov Substitution Principle: if B extends A, you must be able to use B wherever A is expected without breaking behaviour.
  • final class/method prevents overriding — useful for security and performance (JIT can inline).
  • Covariant return types: overriding method may return a subtype of the parent return type (since Java 5).
JAVA Dynamic dispatch vs compile-time overload resolution 
class Animal {
    public String speak() { return "..."; }
}

class Dog extends Animal {
    @Override
    public String speak() { return "Woof"; } // vtable entry replaced
}

Animal a = new Dog();
a.speak(); // "Woof" — runtime type (Dog) determines dispatch

// ── Overloading — compile-time, based on declared type ──
class Printer {
    void print(Object o)  { System.out.println("Object: " + o); }
    void print(String s)  { System.out.println("String: " + s); }
}

Object str = "hello";
new Printer().print(str); // "Object: hello" — declared type Object, not String!
Common Trap
  • Overload resolution uses declared type, not runtime type. This trips up even senior engineers.
  • Never override equals() in a class that allows subclassing with state — violates symmetry or transitivity.

equals() / hashCode()

Important

The equals()/hashCode() contract is one of the most commonly broken rules in Java codebases. If you override one, you must override both. Violating the contract causes silent, data-corrupting bugs in HashMap, HashSet, and any hash-based structure.

equals() Contract
  • Reflexive: x.equals(x) is always true.
  • Symmetric: if x.equals(y) then y.equals(x).
  • Transitive: if x.equals(y) and y.equals(z) then x.equals(z).
  • Consistent: multiple calls return same result if no state changed.
  • Null-safe: x.equals(null) always returns false.
  • hashCode contract: equal objects must have equal hash codes. Unequal objects should (but don't have to) have different hash codes.
JAVA Correct equals/hashCode implementation 
public class OrderId {
    private final String value;

    public OrderId(String value) { this.value = Objects.requireNonNull(value); }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;           // identity shortcut
        if (!(o instanceof OrderId)) return false; // null-safe + type check
        OrderId other = (OrderId) o;
        return Objects.equals(this.value, other.value);
    }

    @Override
    public int hashCode() {
        return Objects.hash(value); // consistent with equals fields
    }
}

// Pattern matching instanceof (Java 16+) — cleaner
@Override
public boolean equals(Object o) {
    return o instanceof OrderId other && Objects.equals(value, other.value);
}
Interview Focus
  • Explain what happens when you add a mutable object to a HashSet then mutate it — it becomes "lost" in the set.
  • Use Objects.hash(f1, f2) — simpler and avoids common 31-prime manual mistakes.
  • Records auto-generate correct equals/hashCode — mention this as a modern alternative.
Core Types

String / StringBuilder / StringBuffer

Core

String is immutable — every modification allocates a new object. The JVM maintains a String Pool in the heap (not PermGen since Java 7) for interning literals. StringBuilder is mutable and not thread-safe. StringBuffer is mutable and thread-safe via synchronized methods — but rarely needed since Java 5's concurrent tools.

TypeMutableThread-safeUse when
StringNoYes (immutable)Fixed text, keys, constants
StringBuilderYesNoBuilding strings in a single thread
StringBufferYesYesRare: shared mutable buffer (prefer other concurrency tools)
JAVA String pool & performance 
// String pool: literals share references
String a = "hello";
String b = "hello";
String c = new String("hello");

a == b;         // true — same pool reference
a == c;         // false — c is a heap object outside pool
a.equals(c);   // true — same content
c.intern() == a; // true — intern() returns pool reference

// Concatenation in loops: avoid String +
StringBuilder sb = new StringBuilder();
for (String item : items) {
    sb.append(item).append(','); // single buffer, no temp objects
}
String result = sb.toString();

// Modern: String.join / collectors often cleaner
String joined = String.join(",", items);
String joined2 = items.stream().collect(Collectors.joining(","));
Interview Focus
  • Java compiler converts simple + concatenation to StringBuilder in non-loop contexts — but not in loops. Be precise about this.
  • Text Blocks (Java 15+): """...""" — multiline strings with automatic indent stripping.
  • String.format vs formatted() (Java 15+) vs String interpolation in future Java versions.

Exception Handling

Core

Checked exceptions must be declared or caught — they represent recoverable conditions callers should handle (IOException, SQLException). Unchecked exceptions (RuntimeException subclasses) signal programming errors or unrecoverable states. Errors (OutOfMemoryError) are JVM-level — never catch them unless you have a very specific reason.

Key Points
  • try-with-resources (Java 7+): any AutoCloseable declared in try() is closed in reverse order, even on exception.
  • Multi-catch: catch (IOException | SQLException e) — reduces duplication, but caught exceptions must be unrelated types.
  • Exception chaining: preserve root cause via new RuntimeException("msg", cause).
  • Don't swallow exceptions: empty catch blocks are a team lead red flag. At minimum, log the exception.
  • Custom exceptions: extend RuntimeException for domain errors; add context fields (orderId, userId) rather than stuffing everything in the message string.
JAVA try-with-resources, multi-catch, exception chaining 
// try-with-resources: closes conn and stmt automatically
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {
    // use stmt...
} // both closed here, even if exception thrown

// Multi-catch — log same way but re-throw as domain exception
try {
    repository.save(order);
} catch (IOException | SQLException e) {
    throw new OrderPersistenceException("Failed to save order: " + order.getId(), e);
}

// Custom domain exception with context
public class OrderPersistenceException extends RuntimeException {
    public OrderPersistenceException(String message, Throwable cause) {
        super(message, cause); // chain: root cause preserved
    }
}
Anti-patterns to call out in code review
  • catch (Exception e) {} — silently swallowing all exceptions.
  • Using exceptions for flow control — expensive (stack trace creation), confusing.
  • Losing the cause: throw new RuntimeException(e.getMessage()) drops the original stack trace.

JAVA HashMap internals & computeIfAbsent 
// HashMap: array of buckets, each bucket a linked list (or tree if >8 entries)
// Key.hashCode() → spread via (h ^ h>>>16) → bucket index = hash & (n-1)
// Java 8+: bucket treeifies at threshold 8 → O(log n) worst case

Map<String, List<Order>> byCustomer = new HashMap<>();

// Old way — verbose
if (!byCustomer.containsKey(customerId)) {
    byCustomer.put(customerId, new ArrayList<>());
}
byCustomer.get(customerId).add(order);

// Modern — atomic & clean
byCustomer.computeIfAbsent(customerId, k -> new ArrayList<>()).add(order);

// Immutable collections (Java 9+)
List<String> roles = List.of("ADMIN", "USER");      // fast, null-hostile
Map<String, Integer> codes = Map.of("OK", 200, "NOT_FOUND", 404);
Interview Focus
  • Explain HashMap resizing (load factor 0.75, doubles capacity) and why initial capacity matters for large maps.
  • ConcurrentHashMap uses segment-level locking in Java 7, per-bucket CAS+synchronized in Java 8+. Not a drop-in for Hashtable.
  • When iterating and modifying: use Iterator.remove(), or collect to remove list, or use stream filter. ConcurrentModificationException otherwise.
Data Structures

Generics

Important

Generics provide compile-time type safety without runtime overhead. Type information is erased at compile time (type erasure) — the JVM sees raw types at runtime. This explains why you can't do new T(), instanceof T, or create generic arrays.

Wildcards & PECS
  • Unbounded <?>: unknown type — read-only safe.
  • Upper bounded <? extends T>: Producer — you can read T from it, but not write.
  • Lower bounded <? super T>: Consumer — you can write T into it, but reading yields Object.
  • PECS: Producer Extends, Consumer Super — the rule for choosing wildcard direction.
  • Type erasure: List<String> and List<Integer> are the same class at runtime. Bridge methods handle polymorphism.
JAVA PECS, bounded type parameters, generic methods 
// PECS — Producer Extends, Consumer Super
public static <T> void copy(List<? super T> dest,     // consumer
                              List<? extends T> src) {  // producer
    for (T item : src) dest.add(item);
}

// Bounded type parameter
public static <T extends Comparable<T>> T max(List<T> list) {
    return list.stream().max(Comparator.naturalOrder())
               .orElseThrow(NoSuchElementException::new);
}

// Type erasure: both are List.class at runtime
List<String> strings = new ArrayList<>();
List<Integer> ints   = new ArrayList<>();
strings.getClass() == ints.getClass(); // true!
Interview Focus
  • Why can't you create new T[10]? — Type erasure means T is Object at runtime; array creation needs exact type. Use List<T> instead.
  • Explain bridge methods: compiler generates them to maintain polymorphism after erasure.

Functional Interfaces

Important

A functional interface has exactly one abstract method (SAM — Single Abstract Method). @FunctionalInterface annotation enforces this at compile time. They are the target type for lambda expressions and method references.

InterfaceSignatureUse
Function<T,R>T → RTransform input to output
Predicate<T>T → booleanTest/filter condition
Consumer<T>T → voidSide effect on input
Supplier<T>() → TLazy value provider
BiFunction<T,U,R>(T,U) → RTwo inputs, one output
UnaryOperator<T>T → TTransform same type
BinaryOperator<T>(T,T) → TCombine two of same type
JAVA Function composition 
Function<String, String> trim   = String::trim;
Function<String, String> upper  = String::toUpperCase;
Function<String, Integer> length = String::length;

// andThen: compose left-to-right
Function<String, Integer> pipeline = trim.andThen(upper).andThen(length);
pipeline.apply("  hello  "); // → 5

// Predicate combination
Predicate<String> notEmpty = s -> !s.isEmpty();
Predicate<String> longEnough = s -> s.length() >= 3;
Predicate<String> valid = notEmpty.and(longEnough);

// Custom functional interface
@FunctionalInterface
public interface Transformer<T> {
    T transform(T input);
    default Transformer<T> andThen(Transformer<T> after) {
        return input -> after.transform(this.transform(input));
    }
}
Modern Java 8+

Lambda Expressions

Important

Lambdas are anonymous functions that implement a functional interface. They are not just syntactic sugar — the JVM uses invokedynamic and LambdaMetafactory to create them at runtime, which is more efficient than anonymous inner classes (no extra .class file, no outer this capture by default).

Key Points
  • Variable capture: lambdas can capture local variables only if they are effectively final (not necessarily declared final).
  • No this rebinding: inside a lambda, this refers to the enclosing class — unlike anonymous inner classes.
  • Syntax forms: (params) -> expression, (params) -> { statements; }, () -> expr, param -> expr
  • Lambdas are instances of functional interfaces — they can be stored, passed, and returned.
JAVA Lambda syntax forms & capture rules 
// All equivalent for Comparator<String>
Comparator<String> c1 = (a, b) -> a.compareTo(b);
Comparator<String> c2 = String::compareTo; // method reference
Comparator<String> c3 = Comparator.naturalOrder();

// Effectively final capture
String prefix = "ORDER-"; // effectively final
Function<String, String> addPrefix = id -> prefix + id; // ok
// prefix = "X"; would make this a compile error

// this inside lambda = enclosing instance
class OrderService {
    private String name = "OrderService";
    Runnable r = () -> System.out.println(this.name); // "OrderService"
}
Modern Java 8+

Method References

Important

Method references are a shorthand for a lambda that only calls an existing method. There are exactly four kinds — interviewers often ask you to enumerate and contrast them.

JAVA All four method reference types 
// 1. Static method: ClassName::staticMethod
Function<String, Integer> parser = Integer::parseInt;
//  equivalent lambda: s -> Integer.parseInt(s)

// 2. Instance method on a specific object: instance::method
String greeting = "Hello";
Supplier<String> upper = greeting::toUpperCase;
//  equivalent lambda: () -> greeting.toUpperCase()

// 3. Instance method on an arbitrary instance of type: ClassName::method
Function<String, String> trim = String::trim;
//  equivalent lambda: s -> s.trim()  (s is the first arg, becomes receiver)

// 4. Constructor: ClassName::new
Supplier<ArrayList<String>> listFactory = ArrayList::new;
Function<Integer, ArrayList<String>> sizedList = ArrayList::new;
//  picks the right constructor by arity from the functional interface

// Practical: Comparator.comparing with method reference
orders.sort(Comparator.comparing(Order::getCreatedAt)
                       .thenComparing(Order::getTotalAmount).reversed());
Modern Java 8+

Stream API

Important

Streams are a lazy, declarative way to process sequences of data. They do not store data — they pipeline operations over a source. Intermediate operations are lazy (not executed until a terminal is reached). Terminal operations trigger the pipeline and may consume the stream.

Intermediate vs Terminal
  • Intermediate (lazy): filter, map, flatMap, distinct, sorted, peek, limit, skip.
  • Terminal (eager): collect, reduce, forEach, count, findFirst, anyMatch, toList (Java 16+).
  • Streams are single-use: once a terminal operation runs, the stream is closed.
  • flatMap: map each element to a stream, then flatten — for one-to-many transformations.
  • parallel(): uses ForkJoinPool. Only beneficial for CPU-intensive, stateless, large-data operations. Wrong use causes worse performance.
JAVA Common Stream patterns 
List<Order> orders = /* ... */;

// Group by status, count each
Map<Status, Long> byStatus = orders.stream()
    .collect(Collectors.groupingBy(Order::getStatus, Collectors.counting()));

// flatMap: order → order lines
List<OrderLine> allLines = orders.stream()
    .flatMap(o -> o.getLines().stream())
    .collect(Collectors.toList());

// reduce: sum all amounts
BigDecimal total = orders.stream()
    .map(Order::getAmount)
    .reduce(BigDecimal.ZERO, BigDecimal::add);

// Collecting to immutable list (Java 16+)
List<String> ids = orders.stream()
    .filter(Order::isActive)
    .map(Order::getId)
    .toList(); // unmodifiable list

// Lazy: only processes until first match found
Optional<Order> firstLarge = orders.stream()
    .filter(o -> o.getAmount().compareTo(BigDecimal.valueOf(1000)) > 0)
    .findFirst(); // terminates as soon as first match found
Team Lead Code Review Flags
  • Using peek() for side effects in production — it's for debugging only; behaviour with short-circuit ops is undefined.
  • parallel() on small collections or IO-bound work — overhead outweighs benefit.
  • Stateful lambdas in map() — breaks parallel correctness and reasoning.
Modern Java 8+

Optional

Important

Optional<T> is a container that may or may not hold a value. Its purpose is to make the possibility of absence explicit in method signatures — it is not a replacement for null everywhere. Misuse is common; a Team Lead should guide the team on its proper scope.

JAVA Creation, consumption, and chaining 
// Creation
Optional<User> user = Optional.of(u);          // throws NPE if u is null
Optional<User> user = Optional.ofNullable(u);  // safe — wraps null as empty
Optional<User> empty = Optional.empty();

// Consumption — prefer functional style
user.ifPresent(u -> log.info("Found: {}", u.getName()));
String name = user.map(User::getName).orElse("anonymous");
String name = user.map(User::getName).orElseGet(() -> fetchDefault()); // lazy
User u = user.orElseThrow(() -> new UserNotFoundException(id));

// flatMap for nested optionals
Optional<String> zip = user
    .flatMap(User::getAddress)    // returns Optional<Address>
    .map(Address::getZipCode);    // returns Optional<String>
Anti-patterns — Flag in Code Review
  • optional.get() without isPresent() check — defeats the purpose, throws NoSuchElementException.
  • Optional as a field type or parameter — it's for return types only. Serialization also breaks.
  • Optional.isPresent() + get() pattern — use ifPresent(), map(), or orElse() instead.
  • orElse(expensiveCall()) always evaluates — use orElseGet(() -> expensiveCall()) for lazy evaluation.

Important

The java.time package (Java 8) replaced the broken java.util.Date and Calendar. All types are immutable and thread-safe. The design separates date, time, timezone, and machine-readable instants into distinct classes.

Instant now = Instant.now();                    // UTC timestamp — use for DB
LocalDate today = LocalDate.now();
ZonedDateTime userTime = ZonedDateTime.now(ZoneId.of("America/New_York"));

// Immutable modification — returns new instance
LocalDate nextWeek = today.plusWeeks(1);

  • LocalDateTime does not account for DST — can cause double-counting or missing hours at clock changes.
  • Legacy interop: Date.from(instant) and date.toInstant() bridge old APIs.
Java 14–21

Records

Advanced

Records (Java 16, preview since 14) are a concise way to declare immutable data carriers. The compiler auto-generates a canonical constructor, equals(), hashCode(), toString(), and accessor methods from the record components. They replace the classic value class boilerplate.

Capabilities & Limitations
  • Components are implicitly private final. Accessor methods match component names (id() not getId()).
  • Compact constructor: validate/normalize without repeating assignment — compiler adds assignments after.
  • Can implement interfaces; cannot extend a class (records extend java.lang.Record implicitly).
  • Can have static fields, static methods, instance methods. Cannot have instance fields beyond components.
  • Not suitable for entities with identity (use @Entity classes) or mutable state.
JAVA Record definition, compact constructor, interface impl 
// Simple record — replaces ~40 lines of boilerplate
public record Money(BigDecimal amount, String currency) {

    // Compact constructor — validate, then compiler assigns fields
    public Money {
        Objects.requireNonNull(amount, "amount");
        Objects.requireNonNull(currency, "currency");
        if (amount.signum() < 0) throw new IllegalArgumentException("Negative");
        currency = currency.toUpperCase(); // normalize
    }

    // Additional methods fine
    public Money add(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException();
        return new Money(amount.add(other.amount), currency);
    }
}

Money price = new Money(BigDecimal.valueOf(9.99), "usd");
price.amount();   // accessor — not getAmount()
price.currency(); // → "USD" (normalized)
Java 14–21

Sealed Classes

Advanced

Sealed classes (Java 17) restrict which classes can extend or implement them. The compiler knows all permitted subtypes at compile time — enabling exhaustive switch expressions with pattern matching (Java 21). This models closed algebraic data types.

JAVA Sealed hierarchy with pattern matching switch 
// Sealed interface — only these three can implement it
public sealed interface PaymentResult
    permits PaymentResult.Success, PaymentResult.Declined, PaymentResult.Error {

    record Success(String transactionId) implements PaymentResult {}
    record Declined(String reason)      implements PaymentResult {}
    record Error(Exception cause)       implements PaymentResult {}
}

// Pattern matching switch — exhaustive, no default needed (Java 21)
String message = switch (result) {
    case PaymentResult.Success(var txId) -> "Charged: " + txId;
    case PaymentResult.Declined(var reason) -> "Declined: " + reason;
    case PaymentResult.Error(var ex) -> "Error: " + ex.getMessage();
}; // compiler verifies all cases covered
Interview Focus
  • Sealed classes model domains where the type hierarchy is fixed and known — payment states, HTTP responses, AST nodes.
  • Permitted subtypes must be in the same package (or module). They must be final, sealed, or non-sealed.
  • Works powerfully with records — sealed interface + record permits = concise, safe ADT.
Metaprogramming

Annotations

Important

Annotations are metadata attached to code elements. They have no direct effect on runtime by themselves — a framework or annotation processor reads and acts on them. Understanding meta-annotations is key to writing custom annotations correctly.

Meta-annotations
  • @Target: where the annotation can be applied — TYPE, METHOD, FIELD, PARAMETER, CONSTRUCTOR, etc.
  • @Retention: how long it lives — SOURCE (discarded after compile), CLASS (in .class but not runtime), RUNTIME (available via reflection).
  • @Documented: include in Javadoc.
  • @Inherited: subclasses inherit the annotation from their parent class.
  • @Repeatable: allows the same annotation multiple times on one element.
JAVA Custom annotation with runtime retention 
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface Audited {
    String action() default "UNKNOWN";
    boolean logResult() default false;
}

// Usage
@Audited(action = "CREATE_ORDER", logResult = true)
public Order createOrder(OrderRequest req) { /* ... */ }

// Reading at runtime via reflection

Metaprogramming

Reflection

Advanced

Reflection lets code inspect and manipulate class structure at runtime — bypassing compile-time type checking. It powers frameworks like Spring, Hibernate, and JUnit. As a Team Lead, you should know when it's justified and understand its costs.

Key Points
  • Class<?> object is the entry point — get via obj.getClass(), MyClass.class, or Class.forName("com.example.Foo").
  • getDeclaredMethods() returns all methods (including private); getMethods() returns public methods including inherited.
  • setAccessible(true) bypasses access control — requires appropriate module permissions in Java 9+.
  • Performance cost: reflection is ~10–100× slower than direct calls. Cache Method/Field references if called frequently.
  • Java 9 modules (module-info.java) restrict reflective access to non-open packages — opens directive needed.
JAVA Inspecting & invoking at runtime 
Class<?> clazz = OrderService.class;

// List all declared methods
Arrays.stream(clazz.getDeclaredMethods())
      .forEach(m -> System.out.println(m.getName()));

// Read a private field (use sparingly — breaks encapsulation)
Field field = clazz.getDeclaredField("repository");
field.setAccessible(true);
Object repo = field.get(serviceInstance);

// Invoke method dynamically
Method method = clazz.getDeclaredMethod("validateOrder", Order.class);
method.setAccessible(true);
Boolean valid = (Boolean) method.invoke(serviceInstance, order);

// Find all methods annotated with @Audited
Arrays.stream(clazz.getDeclaredMethods())
      .filter(m -> m.isAnnotationPresent(Audited.class))
      .forEach(m -> System.out.println("Audited: " + m.getName()));
Team Lead Perspective
  • Reflection is a last resort in application code. Use it in framework/library code, not business logic.
  • Java 16+ MethodHandles are faster and module-safe — prefer them over raw reflection when performance matters.
  • In Java 17+ strong encapsulation: --add-opens JVM args are a warning sign that something needs rethinking.
