1. Entity Mapping

@Entity @Table(name = "orders", indexes = { @Index(name = "idx_customer_status", columnList = "customer_id, status") }) public class Order { @Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq") @SequenceGenerator(name = "order_seq", sequenceName = "order_sequence", allocationSize = 50) // batches 50 IDs — reduces DB round trips private Long id; @Column(nullable = false) private Long customerId; @Enumerated(EnumType.STRING) // store as "PENDING", not 0/1/2 private OrderStatus status; @Column(precision = 15, scale = 2) private BigDecimal total; @Column(updatable = false) @CreationTimestamp private Instant createdAt; @Version // optimistic locking — prevents lost updates private int version; }
Prefer GenerationType.SEQUENCE with allocationSize over IDENTITY. IDENTITY disables JDBC batch inserts because each insert needs the auto-generated ID immediately.

2. Relationships

// One-to-Many — Order has many OrderItems @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, fetch = FetchType.LAZY, orphanRemoval = true) private List<OrderItem> items = new ArrayList<>(); // Many-to-One — OrderItem belongs to Order @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id", nullable = false) private Order order; // Many-to-Many — use @JoinTable on owning side @ManyToMany(cascade = { CascadeType.PERSIST, CascadeType.MERGE }) @JoinTable(name = "product_tags", joinColumns = @JoinColumn(name = "product_id"), inverseJoinColumns = @JoinColumn(name = "tag_id")) private Set<Tag> tags = new HashSet<>();
EAGER fetch type on collections is dangerous — it loads all related data even when you don't need it, and combined with multiple EAGER collections causes Cartesian product queries. Always use LAZY for @OneToMany and @ManyToMany.

3. N+1 Problem & Fixes

The N+1 problem: loading N entities and then issuing 1 additional query per entity to load a related collection = N+1 total queries.

// N+1 problem — 1 query for orders, N queries for order.getItems() List<Order> orders = orderRepo.findAll(); // SELECT * FROM orders orders.forEach(o -> o.getItems().size()); // SELECT * FROM order_items WHERE order_id=? × N // Fix 1: JOIN FETCH — loads everything in one query (use for single relationship) @Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items WHERE o.status = :status") List<Order> findWithItems(@Param("status") OrderStatus status); // Fix 2: @EntityGraph — declarative alternative to JOIN FETCH @EntityGraph(attributePaths = { "items", "items.product" }) List<Order> findByCustomerId(Long customerId); // Fix 3: @BatchSize — issues IN() query for collection instead of 1-by-1 @OneToMany(mappedBy = "order", fetch = FetchType.LAZY) @BatchSize(size = 100) // loads items for up to 100 orders in one IN() query private List<OrderItem> items; // Fix 4: Projections / DTOs — avoid entity entirely when you need a subset @Query("SELECT new com.example.dto.OrderSummaryDto(o.id, o.status, o.total) FROM Order o") List<OrderSummaryDto> findOrderSummaries(); // No lazy-load issue — DTO has no persistent collections
JOIN FETCH with pagination (@PageRequest) causes HHH90003004 warning and incorrect results — Hibernate loads all data in memory and paginates in Java. Use @BatchSize or a two-query approach (paginate IDs first, then fetch full entities by those IDs).

8. Interview Q&A

What is the N+1 query problem and how do you detect and fix it?
Problem: Loading a collection of N entities triggers 1 additional SQL per entity to load a lazy association = N+1 queries total. 100 orders → 101 queries.

Detection:
1. Enable SQL logging (hibernate.show_sql) and count queries
2. Use Hibernate Statistics API in tests
3. P6Spy or datasource-proxy library to log and count queries
4. Look for repeated queries with different IDs in logs

Fixes:
- JOIN FETCH: single query, loads association in memory — avoid with pagination
- @EntityGraph: same as JOIN FETCH but declarative
- @BatchSize: IN() queries (e.g., WHERE order_id IN (1,2,...,100))
- DTO projections: avoid entity entirely, no lazy-load issue
- Two-query approach for paginated results: fetch IDs first, then entities by ID
Explain the difference between optimistic and pessimistic locking.
Optimistic locking assumes conflicts are rare. No DB-level lock is acquired. When updating, checks that a @Version counter hasn't changed since read. If another transaction committed first, throws OptimisticLockException. Best for read-heavy, low-contention scenarios.

Pessimistic locking acquires a DB-level row lock (SELECT FOR UPDATE) for the duration of the transaction. Other transactions trying to read/write that row are blocked. Best for high-contention scenarios where conflicts are frequent and costly (e.g., inventory deduction).

Trade-offs: Optimistic — better throughput, worse UX on conflict (retry needed). Pessimistic — serializes access, lower throughput, risk of deadlock, potential timeout if lock held too long.
What is the difference between FetchType.LAZY and EAGER, and when would you use each?
EAGER — association is always loaded with the parent entity, in the same query (or additional queries). @ManyToOne and @OneToOne default to EAGER.

LAZY — association loaded only when accessed for the first time. Requires an active session. @OneToMany and @ManyToMany default to LAZY.

Use LAZY almost always — EAGER on collections causes unnecessary data loading and can produce Cartesian products. Exception: small, always-needed associations (@ManyToOne to a reference table) where EAGER is reasonable.

Common trap: calling a lazy association after the EntityManager is closed → LazyInitializationException. Fix: use @Transactional on the service method, or use JOIN FETCH/DTO in the query.
