Multithreading & JVM

The hardest area to master in Java — concurrency bugs are silent, non-deterministic, and production-only. A Team Lead must not only understand the primitives but know when to reach for each one and where the traps are.

Thread Basics

Thread

Core

A Thread is the smallest unit of execution scheduled by the OS. Java threads map 1:1 to OS threads (platform threads). Java 21 introduces Virtual Threads (Project Loom) — lightweight, JVM-managed threads that don't consume an OS thread while blocked.

Thread Lifecycle
  • NEW: created but not yet started.
  • RUNNABLE: executing or ready to execute (OS decides).
  • BLOCKED: waiting to acquire a monitor lock.
  • WAITING: waiting indefinitely — Object.wait(), Thread.join().
  • TIMED_WAITING: waiting with timeout — Thread.sleep(ms), LockSupport.parkNanos().
  • TERMINATED: run() completed or exception thrown.
  • Virtual Threads (Java 21): created via Thread.ofVirtual().start(task) or Executors.newVirtualThreadPerTaskExecutor().
JAVAThread creation, daemon, interruption
// Extend Thread (rarely correct — prefer Runnable)
class WorkerThread extends Thread {
    @Override public void run() { /* work */ }
}

// Preferred: pass Runnable, name the thread (critical for debugging)
Thread t = Thread.ofPlatform()
    .name("order-processor")
    .daemon(true)              // daemon: JVM exits without waiting for it
    .start(() -> processOrders());

// Cooperative interruption — the correct way to stop a thread
class Processor implements Runnable {
    @Override public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                doWork();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt(); // restore flag!
                break;
            }
        }
    }
}

// Java 21 Virtual Thread
Thread vt = Thread.ofVirtual().name("vt-1").start(() -> doWork());
Team Lead Flags
  • Never use Thread.stop() — deprecated and unsafe; it releases all monitors, leaving state corrupted.
  • Always restore the interrupted flag after catching InterruptedException — callers higher up the call stack need to see it.
  • Name your threads — unnamed threads make thread dumps unreadable in production.
Thread Basics

Runnable / Callable

Core

Runnable has no return value and cannot throw checked exceptions. Callable<V> returns a value and can throw checked exceptions — it is used with ExecutorService.submit(), which wraps the result in a Future<V>.

AspectRunnableCallable<V>
Methodvoid run()V call() throws Exception
ReturnNoneGeneric value V
ExceptionsUnchecked onlyAny checked exception
Used withThread, execute()submit() → Future<V>
Java versionJava 1.0Java 5 (java.util.concurrent)
JAVACallable + Future pattern
ExecutorService pool = Executors.newFixedThreadPool(4);

Callable<PricingResult> task = () -> {
    // can throw checked exception
    return pricingService.calculate(orderId); // throws IOException
};

Future<PricingResult> future = pool.submit(task);

// ... do other work ...

try {
    PricingResult result = future.get(5, TimeUnit.SECONDS); // blocks with timeout
} catch (ExecutionException e) {
    // e.getCause() holds the actual exception thrown in the task
    throw new PricingException("Pricing failed", e.getCause());
} catch (TimeoutException e) {
    future.cancel(true); // interrupt the task
    throw new PricingException("Timeout");
}
Async Execution

ExecutorService

Important

ExecutorService decouples task submission from execution mechanics. You submit tasks; the service decides threading. Always shut it down explicitly — unreferenced executors are not GC'd because their threads hold a reference back to the executor.

Key Methods
  • execute(Runnable) — fire-and-forget; no return, exceptions are swallowed by UncaughtExceptionHandler.
  • submit(Callable) — returns Future<V>; exceptions are wrapped in ExecutionException from future.get().
  • invokeAll(Collection<Callable>) — submits all, blocks until all complete, returns list of Futures.
  • invokeAny(Collection<Callable>) — returns result of first to complete, cancels the rest.
  • shutdown() — stop accepting new tasks; allow running tasks to finish.
  • shutdownNow() — attempts to interrupt running tasks; returns list of queued tasks that never started.
JAVALifecycle-safe executor usage
ExecutorService executor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors()
);

try {
    List<Future<Report>> futures = executor.invokeAll(reportTasks);
    for (Future<Report> f : futures) {
        reports.add(f.get()); // already done; get() won't block long
    }
} finally {
    // Graceful shutdown pattern
    executor.shutdown();
    if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
        executor.shutdownNow();
    }
}
Interview Focus
  • Difference between shutdown() and shutdownNow() — this is a common question.
  • Executors factory methods hide important queue behavior — prefer ThreadPoolExecutor directly in production for control over queue type and rejection policy.
  • Avoid Executors.newCachedThreadPool() for untrusted workloads — unbounded thread creation under load.
Async Execution

CompletableFuture

Important

CompletableFuture<T> (Java 8) enables non-blocking async pipelines with explicit completion control. Unlike Future, it can be chained, combined, and manually completed — making it the backbone of modern reactive Java without a reactive framework.

Key Operations
  • thenApply: transform result — like map(). Runs in same thread or common pool.
  • thenCompose: chain async ops that return another CF — like flatMap().
  • thenCombine: combine two independent CFs when both complete.
  • allOf / anyOf: wait for all / first-one-done out of N futures.
  • exceptionally: recover from failure; handle: inspect result or exception.
  • Default executor: ForkJoinPool.commonPool() — consider supplying your own for isolation.
JAVAAsync pipeline & parallel combination
CompletableFuture<Order> orderFuture = CompletableFuture
    .supplyAsync(() -> orderRepo.findById(id), executor)
    .thenApply(Order::validate)          // transform
    .thenCompose(o ->                       // async chain
        CompletableFuture.supplyAsync(() -> enricher.enrich(o), executor))
    .exceptionally(ex -> Order.fallback(id)); // recover

// Run two tasks in parallel, combine when both done
CompletableFuture<Price> priceFuture = CompletableFuture
    .supplyAsync(() -> pricing.get(sku), executor);
CompletableFuture<Stock> stockFuture = CompletableFuture
    .supplyAsync(() -> inventory.check(sku), executor);

CompletableFuture<ProductInfo> combined = priceFuture
    .thenCombine(stockFuture, ProductInfo::new);

// Wait for all N — allOf returns CF<Void>, extract manually
CompletableFuture<Void> all = CompletableFuture.allOf(
    futures.toArray(new CompletableFuture[0]));
all.thenRun(() -> futures.stream().map(CompletableFuture::join).forEach(this::process));
Traps
  • join() throws unchecked; get() throws checked — use get(timeout, unit) in production to avoid blocking forever.
  • Exceptions in async stages are swallowed unless you attach exceptionally() or handle().
  • Using ForkJoinPool.commonPool() with blocking IO contaminates the pool — always supply a dedicated executor.

Thread Pools

Important

All Executors factory methods delegate to ThreadPoolExecutor. Understanding its parameters directly is essential for sizing pools correctly and avoiding OOM or thread starvation in production.

JAVACustom ThreadPoolExecutor with bounded queue
// Production-safe: bounded queue + explicit rejection policy
ExecutorService executor = new ThreadPoolExecutor(
    4,                                  // corePoolSize
    8,                                  // maximumPoolSize
    60L, TimeUnit.SECONDS,             // keepAliveTime for idle threads > core
    new ArrayBlockingQueue<>(100),     // bounded queue — prevents OOM
    new ThreadFactoryBuilder()          // named threads (Guava or custom)
        .setNameFormat("order-worker-%d")
        .build(),
    new ThreadPoolExecutor.CallerRunsPolicy() // back-pressure: caller runs task
);
Sizing Rule of Thumb
  • CPU-bound: threads ≈ Runtime.getRuntime().availableProcessors() (or +1).
  • IO-bound: threads ≈ N_cpu × (1 + wait_time / cpu_time) — often much larger; or use Virtual Threads.
  • Rejection policies: AbortPolicy (throws), CallerRunsPolicy (back-pressure), DiscardPolicy (silently drops), DiscardOldestPolicy (evicts head).
Synchronization

Synchronization

Core

The synchronized keyword acquires the intrinsic monitor lock (mutex) of an object before entering a block or method. It provides both mutual exclusion (atomicity) and visibility (happens-before relationship — all writes before unlock are visible after lock).

Key Points
  • synchronized method: locks on this (instance method) or ClassName.class (static method).
  • synchronized block: locks on any specified object — prefer a private dedicated lock object over this.
  • Reentrant: the same thread can acquire the same lock again (nested calls don't deadlock on themselves).
  • wait() / notify() / notifyAll(): must be called while holding the lock on the object.
  • Contended synchronized is expensive — JVM escalates from biased → thin → fat lock as contention increases.
JAVABlock vs method sync, private lock object
public class OrderQueue {
    // Private lock — callers can't accidentally lock on 'this'
    private final Object lock = new Object();
    private final Queue<Order> queue = new ArrayDeque<>();

    public void enqueue(Order o) {
        synchronized (lock) {
            queue.add(o);
            lock.notifyAll(); // signal waiting consumers
        }
    }

    public Order dequeue() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty()) { // loop — guard against spurious wakeups
                lock.wait();
            }
            return queue.poll();
        }
    }
}
Common Mistake
  • Using if instead of while around wait() — spurious wakeups (OS can wake a thread without notify) make while mandatory.
  • Synchronizing on a non-final field — if the reference changes, different threads lock on different objects.
Synchronization

Locks (java.util.concurrent.locks)

Important

ReentrantLock offers everything synchronized does plus: tryLock (non-blocking), timed lock, interruptible lock acquisition, and fairness. ReadWriteLock allows multiple concurrent readers but exclusive writers — ideal for read-heavy caches.

JAVAReentrantLock & ReadWriteLock patterns
// ReentrantLock — always unlock in finally
private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account from, Account to, BigDecimal amount) {
    lock.lock();
    try {
        from.debit(amount);
        to.credit(amount);
    } finally {
        lock.unlock(); // ALWAYS in finally
    }
}

// tryLock — avoid deadlock by not blocking
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try { /* critical section */ }
    finally { lock.unlock(); }
} else {
    /* could not acquire — back off or retry */
}

// ReadWriteLock — concurrent reads, exclusive writes
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
private final Lock readLock  = rwLock.readLock();
private final Lock writeLock = rwLock.writeLock();
private Map<String, Config> cache = new HashMap<>();

public Config get(String key) {
    readLock.lock();
    try { return cache.get(key); } finally { readLock.unlock(); }
}
public void put(String key, Config val) {
    writeLock.lock();
    try { cache.put(key, val); } finally { writeLock.unlock(); }
}
Interview Focus
  • StampedLock (Java 8): optimistic read — check if write happened since read; much faster for read-heavy scenarios.
  • Fair ReentrantLock(true): threads acquire in FIFO order — prevents starvation but reduces throughput.
  • Condition (from lock) replaces wait()/notify() — supports multiple named wait sets on one lock.
Synchronization

volatile

Important

volatile guarantees visibility (writes are immediately visible to all threads) and prevents instruction reordering around the field — but does not guarantee atomicity of compound operations (read-modify-write). It inserts memory barrier instructions.

What volatile Does and Doesn't Do
  • Guarantees: a write to a volatile field happens-before every subsequent read of that field.
  • Does not guarantee: atomicity of count++ (read + increment + write = 3 ops). Use AtomicLong or synchronized.
  • Classic use: a running flag observed by multiple threads.
  • Double-checked locking: requires volatile on the instance field to prevent broken reads of partially-constructed objects.
JAVAvolatile flag & correct double-checked locking
// Correct: volatile flag for stop signal
private volatile boolean running = true;

public void stop() { running = false; } // visible to all threads immediately

public void run() {
    while (running) { doWork(); } // without volatile, may loop forever (cached)
}

// Double-checked locking — volatile on instance field is REQUIRED
private volatile ServiceConnection instance;

public ServiceConnection getConnection() {
    if (instance == null) {                  // first check (no lock)
        synchronized (this) {
            if (instance == null) {           // second check (with lock)
                instance = new ServiceConnection(); // volatile ensures full construction visible
            }
        }
    }
    return instance;
}
Synchronization

Atomic Classes

Important

The java.util.concurrent.atomic package provides lock-free, thread-safe primitives using Compare-And-Swap (CAS) — a single hardware instruction. CAS atomically: read the current value, compare to expected, write new value only if equal. No lock, no context switch.

JAVAAtomicLong, AtomicReference, AtomicStampedReference
// AtomicLong: lock-free counter
private final AtomicLong requestCount = new AtomicLong(0);

public long nextId()    { return requestCount.incrementAndGet(); }
public long snapshot()  { return requestCount.get(); }

// AtomicReference: CAS on an object reference
private final AtomicReference<Config> current = new AtomicReference<>(defaultConfig);

public void updateConfig(Config newConfig) {
    Config old;
    do {
        old = current.get();                          // read
    } while (!current.compareAndSet(old, newConfig)); // retry until CAS wins
}

// LongAdder: better than AtomicLong under HIGH contention
// Stripes internally across multiple cells, sums on read
private final LongAdder hits = new LongAdder();
hits.increment();
long total = hits.sum(); // sum() is not atomic with increment() — for metrics only

// ABA problem: AtomicStampedReference adds a version number
AtomicStampedReference<Node> ref = new AtomicStampedReference<>(node, 0);
int[] stamp = new int[1];
Node current = ref.get(stamp);
ref.compareAndSet(current, newNode, stamp[0], stamp[0] + 1);
Interview Focus
  • Explain the ABA problem: value changes A→B→A; CAS sees A and thinks nothing changed. AtomicStampedReference adds a version to detect it.
  • LongAdder vs AtomicLong: use LongAdder for high-contention counters (metrics), AtomicLong when you need the latest value atomically with updates.

JAVAConcurrentHashMap compute patterns
ConcurrentHashMap<String, AtomicLong> metrics = new ConcurrentHashMap<>();

// Atomic compute — entire block is atomic on that key
metrics.compute(eventName, (key, existing) -> {
    if (existing == null) return new AtomicLong(1);
    existing.incrementAndGet(); return existing;
});

// merge: if key absent insert value; else apply function
metrics.merge(eventName, new AtomicLong(1),
    (existing, one) -> { existing.incrementAndGet(); return existing; });

// BlockingQueue: classic producer-consumer
BlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000);

// Producer
queue.put(task);  // blocks if full — back-pressure

// Consumer
Task t = queue.poll(1, TimeUnit.SECONDS); // null if no task within 1s
Failure Modes

Deadlocks

Advanced

A deadlock occurs when two or more threads each hold a lock the other needs, and none can proceed. All four Coffman conditions must hold: mutual exclusion, hold-and-wait, no preemption, circular wait. Eliminating any one breaks the deadlock.

Prevention Strategies
  • Lock ordering: always acquire locks in the same global order — breaks circular wait.
  • tryLock with timeout: if you can't acquire all locks, release what you have and retry.
  • Single lock: coarser locking (reduce number of locks in play).
  • Lock-free data structures: eliminate locks entirely with CAS.
  • Detect in production: jstack <pid> or ThreadMXBean.findDeadlockedThreads().
JAVADeadlock + fix via lock ordering
// DEADLOCK: Thread 1 locks A then B; Thread 2 locks B then A
// Thread 1                  Thread 2
// lock(accountA)            lock(accountB)
// lock(accountB) ← WAITS   lock(accountA) ← WAITS   → DEADLOCK

// FIX: always lock the lower-id account first
public void transfer(Account a, Account b, BigDecimal amount) {
    Account first  = a.getId() < b.getId() ? a : b;
    Account second = a.getId() < b.getId() ? b : a;

    synchronized (first) {
        synchronized (second) {
            first.debit(amount);
            second.credit(amount);
        }
    }
}

// Programmatic detection
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads();
if (deadlocked != null) {
    Arrays.stream(bean.getThreadInfo(deadlocked))
          .forEach(info -> log.error("Deadlocked: {}", info));
}
Failure Modes

Race Conditions

Advanced

A race condition occurs when program behavior depends on the timing of thread scheduling. Types: check-then-act (stale read between check and action), read-modify-write (non-atomic compound update), and memory visibility (stale cached reads). Java Memory Model (JMM) defines when writes are guaranteed visible — only through happens-before relationships.

JAVARace condition examples & fixes
// RACE: check-then-act (both threads see balance OK, both debit)
if (account.getBalance() >= amount) {   // Thread 1 checks → true
    account.debit(amount);              // Thread 2 also checks → true, both debit!
}

// FIX: make check+act atomic
synchronized (account) {
    if (account.getBalance().compareTo(amount) >= 0) {
        account.debit(amount);
    }
}

// RACE: read-modify-write
private int counter = 0;
public void increment() { counter++; } // NOT atomic: read, increment, write

// FIX option 1: atomic
private final AtomicInteger counter = new AtomicInteger();
public void increment() { counter.incrementAndGet(); }

// FIX option 2: synchronized
public synchronized void increment() { counter++; }
Java Memory Model — Happens-Before Relationships
  • Unlock on monitor M → lock on M (synchronization).
  • Write to volatile field → subsequent read of that field.
  • Thread.start() → all actions in the started thread.
  • All actions in a thread → Thread.join() returns in joining thread.
JVM Internals

JVM Architecture

JVM

The JVM provides a platform-independent execution environment. It loads, verifies, and executes Java bytecode. Understanding its architecture allows you to reason about startup time, memory pressure, JIT warm-up, and profiling.

┌──────────────────────────────────────────────────────────────┐ │ CLASS LOADER SUBSYSTEM │ │ Bootstrap → Extension/Platform → Application → Custom │ └──────────────────────────┬───────────────────────────────────┘ │ .class bytecode ┌──────────────────────────▼───────────────────────────────────┐ │ RUNTIME DATA AREAS │ │ │ │ ┌─────────────┐ ┌──────────────────────┐ ┌────────────┐ │ │ │ Method │ │ HEAP │ │ Thread │ │ │ │ Area │ │ Young Gen│ Old Gen │ │ Stack │ │ │ │ (classes, │ │ Eden│S0│S1│ Tenured │ │ (frames, │ │ │ │ static, │ └──────────────────────┘ │ locals, │ │ │ │ bytecode) │ │ operands) │ │ │ └─────────────┘ ┌──────────┐ ┌────────┐ └────────────┘ │ │ │ PC Reg │ │ Native │ │ │ │ per-thd │ │ Method │ │ │ └──────────┘ │ Stack │ │ │ └────────┘ │ └──────────────────────────────────────────────────────────────┘ │ ┌──────────────────────────▼───────────────────────────────────┐ │ EXECUTION ENGINE │ │ Interpreter → JIT Compiler (C1 tiered → C2 server) │ │ GC (G1 / ZGC / Shenandoah) │ └──────────────────────────────────────────────────────────────┘
Key Areas
  • Method Area (Metaspace since Java 8): class metadata, static fields, bytecode. OOM here means too many classes loaded.
  • Heap: all object instances. Subject to GC. Shared across threads.
  • Stack: per-thread, per-method frame. Local variables and operand stack. StackOverflowError = too deep recursion.
  • PC Register: per-thread program counter — address of current instruction.
JVM Internals

Heap / Stack

JVM

The heap stores all object instances and arrays, shared across threads. The stack stores each method invocation's frame: local variables, return address, operand stack. Stack memory is auto-released when the method returns; heap requires GC.

AspectStackHeap
StoresPrimitives, references, method framesObjects, arrays
ScopePer-thread (private)Shared across all threads
LifetimeMethod invocation durationUntil GC collects (no strong refs)
SizeSmall (~512KB–1MB per thread)Configurable: -Xms / -Xmx
AllocationAutomatic (LIFO)GC managed
ErrorStackOverflowErrorOutOfMemoryError: Java heap space
Heap Generations (G1 / traditional)
  • Young Gen: Eden + Survivor spaces (S0/S1). New objects allocated in Eden. Minor GC is frequent but fast.
  • Old Gen (Tenured): objects that survived multiple minor GCs. Major/Full GC is expensive.
  • Escape Analysis: JVM can allocate objects on the stack if it proves they don't escape the method — avoids heap pressure.
  • TLAB: Thread-Local Allocation Buffer — each thread has its own Eden slice; allocation is pointer-bump without locking.

Garbage Collection

JVM

The GC automatically reclaims unreachable heap objects. Modern collectors aim for low-pause and high-throughput. Stop-the-world (STW) pauses halt all application threads — the main latency concern. Modern collectors (ZGC, Shenandoah) push STW to sub-millisecond.

Interview Focus
  • Explain GC roots: static fields, stack local variables, JNI references — objects reachable from roots are kept.
  • Generational hypothesis: most objects die young — why Eden and young gen make GC efficient.
  • Full GC triggers: promotion failure, Metaspace OOM, explicit System.gc() (avoidable with -XX:+DisableExplicitGC).
JVM Internals

Class Loading

JVM

Classes are loaded on demand (lazy), linked, and initialized before first use. The parent delegation model ensures security: a class loader checks its parent before loading a class itself — Bootstrap → Platform → Application. This prevents user code from shadowing java.lang.*.

Loading Phases
  • Loading: find .class file, read bytecode into memory, create Class<?> object in method area.
  • Linking — Verification: validate bytecode is structurally correct (safety guarantee).
  • Linking — Preparation: allocate memory for static fields, set default values (0, null, false).
  • Linking — Resolution: replace symbolic references (class names) with direct memory references.
  • Initialization: run static initializers and static field assignments in textual order.
JAVACustom ClassLoader & class loading pitfalls
// Dynamic class loading — used by plugin systems, OSGi, Spring DevTools
ClassLoader loader = new URLClassLoader(
    new URL[]{ pluginJar.toURI().toURL() },
    Thread.currentThread().getContextClassLoader()
);
Class<?> plugin = loader.loadClass("com.acme.Plugin");
Object instance = plugin.getDeclaredConstructor().newInstance();

// ClassLoader leak: custom loader held by loaded class → entire class hierarchy stays alive
// Fix: close URLClassLoader when done (implements Closeable)
try (URLClassLoader ucl = new URLClassLoader(urls)) {
    /* load and use classes */
} // closed → classes become eligible for GC

// Static initializer order matters
class Config {
    static {
        System.out.println("Config initialized"); // runs once, at first use
    }
}
JVM Internals

JIT Compiler

JVM

The JIT (Just-In-Time) compiler converts frequently-executed bytecode into native machine code at runtime. HotSpot uses tiered compilation: interpreted → C1 (fast, low-opt) → C2 (slow, high-opt). Methods become "hot" after ~10,000 invocations and are compiled by C2.

Key Optimizations
  • Inlining: replaces method call with method body — enables further optimization. Most impactful. Small methods inline eagerly.
  • Loop unrolling: replicates loop body to reduce branch overhead.
  • Dead code elimination: removes unreachable or provably unused branches.
  • Escape analysis: if object doesn't escape method, allocate on stack or eliminate entirely.
  • Deoptimization: JIT assumptions can be invalidated (e.g., new subclass loaded) — code reverts to interpreter, then re-optimizes.
  • GraalVM Native Image: AOT compilation — no JIT warmup, instant start, lower memory. Trade-off: no dynamic class loading.
SHELLJIT diagnostic flags
# Print compilation decisions
-XX:+PrintCompilation          # log each method compiled
-XX:+UnlockDiagnosticVMOptions
-XX:+PrintInlining             # show what's inlined

# Tiered compilation (default since Java 8)
-XX:+TieredCompilation
-XX:CompileThreshold=10000     # invocations before C2 compilation

# Force AOT with GraalVM
native-image -jar app.jar      # produces native executable
Interview Focus
  • JIT warmup matters in benchmarks — always use JMH (Java Microbenchmark Harness) to avoid measuring interpreter performance.
  • Why does Java sometimes get faster over time? JIT gathers profiling data and re-optimizes hot paths as more of the program runs.
Performance

Memory Leaks

Advanced

Java memory leaks occur when objects are no longer needed but remain reachable through a strong reference — preventing GC. Unlike C/C++, the leak is logical (stale references), not a missing free().

Common Leak Patterns
  • Static collections: objects added to a static Map/List and never removed grow forever.
  • Unclosed resources: Connection, InputStream, FileChannel not closed → resource leak (not always heap, but FD/socket leak).
  • Listeners not deregistered: event listeners / callbacks holding outer class reference.
  • ThreadLocal: values not removed after thread pool reuse — thread holds strong ref to old values.
  • ClassLoader leak: see Class Loading section — especially in hot-reload scenarios.
  • Inner class references: anonymous inner classes implicitly hold outer class this.
JAVAThreadLocal leak & fix; WeakReference cache
// LEAK: ThreadLocal in thread pool — thread reused, old value retained
private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

public void handleRequest(UserContext ctx) {
    CTX.set(ctx);
    try {
        process();
    } finally {
        CTX.remove(); // REQUIRED — else pooled thread holds ctx forever
    }
}

// WeakReference for soft caches — GC can collect if memory pressure
Map<String, WeakReference<HeavyObject>> cache = new WeakHashMap<>();

// Listener deregistration pattern
public class EventConsumer implements AutoCloseable {
    private final EventBus bus;

    public EventConsumer(EventBus bus) {
        this.bus = bus;
        bus.register(this);
    }

    @Override
    public void close() {
        bus.unregister(this); // prevent leak — use try-with-resources
    }
}

Performance

JVM Performance Tuning

Advanced

Performance tuning is a measurement discipline — never change JVM flags without profiling first. The typical process: measure baseline → profile (CPU/heap/GC) → identify bottleneck → change one thing → re-measure.

Key Flags by Category
  • Heap sizing: -Xms (initial), -Xmx (max). Set equal in production to avoid resize GC pauses. Containers: -XX:+UseContainerSupport (default Java 10+).
  • GC: -XX:+UseG1GC + -XX:MaxGCPauseMillis=200. Switch to -XX:+UseZGC for latency-critical services.
  • Metaspace: -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m — bounds class metadata growth.
  • Thread stack: -Xss512k — reduce per-thread stack if creating many threads.
  • JIT: -XX:+TieredCompilation (default). -server flag for C2-first on small apps.

Team Lead Profiling Workflow
  • CPU bottleneck: async-profiler → flame graph → find hot methods → optimize algorithm or add cache.
  • GC pressure: GC log analysis (GCEasy / GCViewer) → allocation rate → reduce object churn (reuse, pooling).
  • Heap leak: heap dump → MAT dominator tree → find unexpected retainers.
  • Lock contention: async-profiler lock profile or JFR → find hot monitors → reduce scope or switch to lock-free.
