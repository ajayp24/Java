Autoboxing & Unboxing

Java automatically converts between primitives and their wrapper classes. This can lead to subtle bugs:

Integer a = 127; Integer b = 127; System.out.println(a == b); // true — cached range -128 to 127 Integer x = 128; Integer y = 128; System.out.println(x == y); // false — new objects outside cache System.out.println(x.equals(y)); // true — always use .equals() for wrappers // Unboxing null throws NullPointerException Integer val = null; int result = val; // NullPointerException!
Integer caches values from -128 to 127 by default. Never compare wrapper objects with == unless you're certain about the range.

2. String Internals

String is immutable in Java. All string literals are stored in the String Pool (part of the heap since Java 7).

String Pool & intern()

String s1 = "hello"; // String pool String s2 = "hello"; // same reference from pool String s3 = new String("hello"); // new heap object s1 == s2; // true s1 == s3; // false s1.equals(s3); // true s1 == s3.intern(); // true — intern() returns pool reference

String vs StringBuilder vs StringBuffer

StringNoYes (immutable)Slow for concatenationFixed/constant values
StringBuilderYesNoFastestSingle-threaded string building

// Bad — creates N string objects in loop String result = ""; for (int i = 0; i < 1000; i++) result += i; // Good — single StringBuilder, much faster StringBuilder sb = new StringBuilder(); for (int i = 0; i < 1000; i++) sb.append(i); String result = sb.toString();
Java compiler optimizes string concatenation with + in a single expression to use StringBuilder, but NOT in loops.

Key String Methods (Interview Favorites)

3. Exception Handling

Exception Hierarchy

Throwable ├── Error // JVM errors — don't catch (OutOfMemoryError, StackOverflowError) └── Exception ├── RuntimeException // Unchecked — NullPointerException, IllegalArgumentException │ ├── NullPointerException │ ├── ArrayIndexOutOfBoundsException │ ├── ClassCastException │ └── ArithmeticException └── Checked Exceptions // Must be caught or declared ├── IOException ├── SQLException └── ClassNotFoundException

Best Practices

// 1. Multi-catch (Java 7+) try { // code } catch (IOException | SQLException e) { log.error("Data error", e); } // 2. Try-with-resources (Java 7+) — AutoCloseable try (Connection conn = ds.getConnection(); PreparedStatement ps = conn.prepareStatement(sql)) { // resources auto-closed even on exception } // 3. Custom exception with cause chain public class PaymentException extends RuntimeException { public PaymentException(String message, Throwable cause) { super(message, cause); } } // 4. Re-throw with context try { processPayment(orderId); } catch (SQLException e) { throw new PaymentException("Failed for order: " + orderId, e); }
Never catch Exception or Throwable generically without re-throwing. Never swallow exceptions with empty catch blocks. Always preserve the original cause when wrapping.

Finally Block Behavior

try { return "try"; // finally still executes! } finally { return "finally"; // overrides the try return — AVOID this pattern } // result: "finally" // Exception in finally suppresses original exception — AVOID try { throw new RuntimeException("original"); } finally { throw new RuntimeException("finally"); // "original" is lost! }

4. Generics

Generics provide compile-time type safety and eliminate the need for casting. They are erased at runtime (type erasure).

// Generic class public class Box<T> { private T value; public void set(T value) { this.value = value; } public T get() { return value; } } // Bounded type parameters public <T extends Comparable<T>> T max(T a, T b) { return a.compareTo(b) > 0 ? a : b; } // Wildcards void printList(List<?> list) { ... } // unbounded void sum(List<? extends Number> list) { ... } // upper bounded (read) void add(List<? super Integer> list) { ... } // lower bounded (write)

PECS Principle — Producer Extends, Consumer Super

// Producer: you READ from it → use extends public static double sumList(List<? extends Number> list) { return list.stream().mapToDouble(Number::doubleValue).sum(); } // Consumer: you WRITE to it → use super public static void addNumbers(List<? super Integer> list) { list.add(1); list.add(2); list.add(3); }

Type Erasure

// At runtime, generics are erased — cannot do: new T(); // COMPILE ERROR new T[10]; // COMPILE ERROR T instanceof List<String>; // COMPILE ERROR // What actually exists at runtime: List<String> strList = new ArrayList<>(); List<Integer> intList = new ArrayList<>(); strList.getClass() == intList.getClass(); // true! Both are ArrayList.class

6. Immutability

Immutable objects are inherently thread-safe and make code easier to reason about.

Creating an Immutable Class

public final class Money { // final — no subclassing private final long amount; // final fields private final Currency currency; public Money(long amount, Currency currency) { this.amount = amount; this.currency = Objects.requireNonNull(currency); } public long getAmount() { return amount; } public Currency getCurrency() { return currency; } // Return new instance instead of mutating public Money add(Money other) { if (!this.currency.equals(other.currency)) throw new IllegalArgumentException("Currency mismatch"); return new Money(this.amount + other.amount, this.currency); } } // Java 16+ Records — automatically immutable public record Point(double x, double y) {}

Rules for Immutability

  • Declare class as final
  • All fields private and final
  • No setters — return new instances on modification
  • Deep copy mutable objects in constructor and getters
  • Never share references to mutable internal state

7. Java Memory Model (JMM)

The JMM defines how threads interact through memory. It specifies when writes by one thread are visible to other threads.

// Happens-Before relationships guarantee visibility // 1. volatile — writes visible to all threads immediately private volatile boolean stopped = false; // 2. synchronized — exit of monitor happens-before entry by another thread synchronized (this) { counter++; } // 3. Thread.start() happens-before any action in the started thread // 4. Thread.join() — all actions in joined thread happen-before join returns // 5. static initializer happens-before first use of the class

8. Interview Q&A

What is the difference between == and .equals() in Java?
== compares references (memory addresses) for objects, or values for primitives.

.equals() compares content/logical equality as defined by the class implementation.

For String: s1 == s2 may be false for two strings with same content (unless pooled), while s1.equals(s2) is true if content matches. Always use .equals() for object comparison. When overriding .equals(), always override .hashCode() too — objects that are equal must have the same hash code.
Explain checked vs unchecked exceptions. When would you use each?
Checked exceptions extend Exception (not RuntimeException). The compiler requires them to be caught or declared with throws. Use for recoverable conditions where the caller can meaningfully handle it (e.g., FileNotFoundException — caller might show file picker).

Unchecked exceptions extend RuntimeException. No compiler enforcement. Use for programming errors (NullPointerException, IllegalArgumentException) or situations where recovery is impossible or impractical.

Team Lead view: Modern Java APIs (and Spring) favor unchecked exceptions to avoid checked exception pollution up the call stack. Checked exceptions break lambdas and stream operations. I prefer custom unchecked exceptions with clear names, documented in Javadoc.
Why is String immutable in Java?
Several reasons: (1) String pool — multiple references can share the same literal safely because no one can change it; (2) Thread safety — immutable objects are inherently thread-safe with no synchronization needed; (3) Security — class loading, network connections, file operations use String parameters; mutable strings could be changed after security checks; (4) Hashcode caching — String caches its hashCode, making it efficient as HashMap keys.

This is why changing a String always creates a new object.
What is the difference between final, finally, and finalize?
final — keyword. On variables: value can't be reassigned. On methods: can't be overridden. On classes: can't be subclassed.

finally — block that always executes after try/catch (except System.exit() or JVM crash). Used for cleanup code.

finalize() — deprecated method called by GC before object is collected. Unreliable timing, don't use it. Use AutoCloseable and try-with-resources instead.

Note: finalize() was deprecated in Java 9 and removed in Java 18.
What are the rules for overriding hashCode() and equals()?
equals() contract: reflexive (x.equals(x)=true), symmetric (x.equals(y) ↔ y.equals(x)), transitive, consistent, and x.equals(null)=false.

hashCode() contract: If x.equals(y) is true, then x.hashCode() must equal y.hashCode(). The reverse is not required (hash collisions are allowed).

Consequence: If you put an object in a HashMap and then change the fields used in hashCode(), you'll lose the object in the map — can't find it anymore. Keep hashCode fields immutable or don't mutate after adding to collections.
What is type erasure and how does it affect generics?
Type erasure means generic type parameters are removed at compile time. The bytecode has no information about the generic type. This enables backward compatibility with pre-Java-5 code.

Consequences: You can't do new T(), instanceof List<String>, create generic arrays. All List<String> and List<Integer> instances have the same runtime class (ArrayList.class). Cast warnings happen when interoperating with raw types.

Workaround: Pass Class<T> type as a parameter when you need the type at runtime (used in frameworks like Jackson).
