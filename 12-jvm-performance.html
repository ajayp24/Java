1JVM Architecture

The JVM is a stack-based virtual machine that executes bytecode. It provides platform independence, memory management, and runtime optimization via JIT compilation.

ComponentResponsibility
Class Loader SubsystemLoads, links, and initializes .class files
Runtime Data AreasHeap, Stack, Method Area, PC Registers, Native Stack
Execution EngineInterpreter + JIT Compiler + GC
JIT CompilerC1 (client, fast startup) + C2 (server, peak throughput)
Native Interface (JNI)Calls native C/C++ libraries

JIT Compilation Tiers

// Tiered compilation (default since Java 8): // Level 0 — Interpreter // Level 1 — C1 no profiling (simple methods) // Level 2 — C1 limited profiling // Level 3 — C1 full profiling (method invocation & branch counters) // Level 4 — C2 (aggressive optimizations: inlining, loop unrolling, escape analysis) // Enable/disable JIT (for debugging only) // -XX:+TieredCompilation (default: enabled) // -XX:-TieredCompilation (disable — pure interpreter) // -XX:CompileThreshold=10000 (invocation count before C2 kicks in)
Escape Analysis The JIT's escape analysis determines if an object is confined to a single thread or method. If it doesn't "escape", the JVM can allocate it on the stack (scalar replacement) instead of the heap, eliminating GC pressure entirely.

2Class Loading

Class loading is hierarchical and lazy — a class is loaded only when first used (not at startup). The delegation model prevents core classes from being overridden by application code.

LoaderLoadsNotes
Bootstraprt.jar / java.* (JDK core)Native C++ code, parent of all
Extension / Platformjre/lib/ext or --patch-moduleJava 9+: Platform ClassLoader
Application / SystemClasspath / modulepathMost app classes loaded here
Custom ClassLoaderPlugins, hot-deploy, OSGiChild of Application loader

Loading Phases

// 1. Loading — read .class bytes, create Class object in Method Area // 2. Linking // a. Verification — bytecode is valid, type-safe // b. Preparation — static fields allocated, set to defaults (null/0) // c. Resolution — symbolic refs resolved to actual memory refs // 3. Initialization — static initializers and static blocks execute public class ClassLoadingDemo { static { System.out.println("Initialized!"); // runs once at first use } public static void main(String[] args) { // Check which classloader loaded a class System.out.println(String.class.getClassLoader()); // null = Bootstrap System.out.println(ClassLoadingDemo.class.getClassLoader()); // AppClassLoader } }
ClassLoader Leaks Hot-deploy (e.g., Tomcat redeployment) creates a new ClassLoader. If old references remain (via static ThreadLocal, JDBC drivers, logging frameworks), the old ClassLoader can't be GC'd, causing PermGen / Metaspace exhaustion over time.

G1 GC Deep Dive

// G1 divides heap into equal-sized regions (~2048 regions by default) // Regions are dynamically assigned as: Eden, Survivor, Old, or Humongous // Humongous = object > 50% of region size // Key JVM flags for G1: // -XX:+UseG1GC // -XX:MaxGCPauseMillis=200 // pause target (G1 tries to meet it) // -XX:G1HeapRegionSize=16m // region size (1MB-32MB, power of 2) // -XX:G1NewSizePercent=20 // min young gen % // -XX:G1MaxNewSizePercent=60 // max young gen % // -XX:InitiatingHeapOccupancyPercent=45 // start concurrent cycle at 45% old gen // G1 GC phases: // 1. Young GC (minor) — STW, evacuates Eden+Survivor to new Survivor/Old // 2. Concurrent Mark — concurrent with app threads, finds live objects // 3. Remark — STW, finalizes marking (SATB algorithm) // 4. Cleanup — STW (brief), reclaims empty regions // 5. Mixed GC — STW, collects young + some old regions

GC Logging (Java 9+)

# Unified GC logging -Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=20m # Key things to look for: # - Pause time > MaxGCPauseMillis (G1 can't always meet target) # - Full GC (should be rare — indicates promotion failure or heap too small) # - Humongous object allocation (tune G1HeapRegionSize) # - "To-space exhausted" (survivor/old gen full during evacuation)

5Heap Tuning & JVM Flags

Production JVM Startup Template

# Container-aware sizing (Java 10+) -XX:+UseContainerSupport # reads cgroup limits (enabled by default Java 11+) -XX:MaxRAMPercentage=75.0 # heap = 75% of container RAM -XX:InitialRAMPercentage=50.0 # start heap at 50% to avoid resize pauses # Or explicit sizes -Xms2g -Xmx2g # fix min==max to prevent heap resize # GC selection -XX:+UseG1GC -XX:MaxGCPauseMillis=200 # Metaspace -XX:MetaspaceSize=256m # initial (avoids early resizes) -XX:MaxMetaspaceSize=512m # cap it to detect leaks # Thread stacks -Xss512k # reduce from default 1MB for high thread count # OOM diagnostics -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/ -XX:+ExitOnOutOfMemoryError # fail fast, let orchestrator restart # Performance -XX:+UseStringDeduplication # G1 only: dedup identical String objects -XX:+OptimizeStringConcat # optimize string concatenation

GC Tuning Decision Tree

Which GC to choose?
• Latency < 200ms, heap < 32GB → G1 with MaxGCPauseMillis=100-200
• Latency < 10ms, large heap → ZGC (-XX:+UseZGC)
• Max throughput, batch jobs → Parallel GC (-XX:+UseParallelGC)
• Microservices in containers, fast startup → GraalVM Native Image (no GC tuning needed)

Thread Dump Analysis

# Take thread dump jcmd <PID> Thread.print # or kill -3 <PID> # sends SIGQUIT, dumps to stdout # Key thread states to look for: # BLOCKED — thread waiting to acquire a monitor (lock contention) # WAITING — thread in Object.wait() or LockSupport.park() # TIMED_WAITING — Thread.sleep, wait with timeout # Deadlock example (JVM will report it in thread dump) java.lang.Thread.State: BLOCKED (on object monitor) - waiting to lock <0x0000000780001234> (a java.lang.Object) - locked <0x0000000780005678> (a java.lang.Object)

7Memory Leaks

Java memory leaks occur when objects are unintentionally reachable (held by references) even after they're no longer needed. The GC cannot collect reachable objects.

Common Leak Patterns

// 1. Static collections growing unbounded public class MetricsRegistry { private static final Map<String, Object> cache = new HashMap<>(); public static void register(String key, Object val) { cache.put(key, val); // leak: never evicted } // Fix: use WeakHashMap, Caffeine with expiry, or explicit eviction } // 2. ThreadLocal not removed private static final ThreadLocal<Connection> CONN = new ThreadLocal<>(); public void process() { CONN.set(getConnection()); try { // ... work ... } finally { CONN.remove(); // ALWAYS remove in finally — thread pool reuses threads } } // 3. Listeners / callbacks never unregistered public class EventBus { private final List<Listener> listeners = new ArrayList<>(); public void subscribe(Listener l) { listeners.add(l); } // Fix: add unsubscribe(), or use WeakReference list public void unsubscribe(Listener l) { listeners.remove(l); } } // 4. Inner class holding outer class reference public class OuterService { private byte[] largeBuffer = new byte[10_000_000]; public Runnable createTask() { return new Runnable() { // anonymous inner class holds OuterService ref! public void run() { System.out.println("running"); } }; // Fix: use lambda (no implicit this capture) or static nested class } }

Reference Types for Cache-Friendly Memory

// Strong reference — never GC'd while reachable (default) Object obj = new Object(); // Soft reference — GC'd only under memory pressure (good for caches) SoftReference<byte[]> softCache = new SoftReference<>(new byte[1024]); // Weak reference — GC'd at next collection (good for canonical maps) WeakReference<Widget> weakWidget = new WeakReference<>(widget); WeakHashMap<Key, Value> map = new WeakHashMap<>(); // keys are weak refs // Phantom reference — used for cleanup actions post-GC (Cleaner API Java 9+) Cleaner cleaner = Cleaner.create(); cleaner.register(resource, () -> cleanup()); // runs when resource unreachable

QInterview Q&A

Q1: What's the difference between Minor GC, Major GC, and Full GC?

Minor GC collects the young generation (Eden + Survivors). It's fast because it only scans a small area and uses the card table to find old→young references without scanning all of old gen. Happens frequently.

Major GC collects the old generation. May or may not also collect young gen depending on the collector. More expensive than minor GC.

Full GC collects the entire heap (young + old + Metaspace) in a single stop-the-world pause. Caused by: promotion failure (old gen full), explicit System.gc() calls, Metaspace exhaustion. Should be rare in production — frequent Full GCs indicate heap sizing problems.

Q2: Your application has increasing heap usage that never comes down. How do you diagnose and fix it?

Diagnose: 1) Monitor heap with jstat -gcutil every few seconds to confirm growing old gen. 2) Enable GC logging (-Xlog:gc*) to see GC frequency and effectiveness. 3) Take heap dump when heap is near max: jcmd <pid> GC.heap_dump /tmp/heap.hprof. 4) Analyze with Eclipse MAT — check dominator tree, leak suspects, and find which classes are unexpectedly retaining large retained heaps.

Common causes: Static collections growing unbounded, ThreadLocal not removed (in thread pools), event listeners never unregistered, classloader leaks on hot-redeploy, connection pool objects kept in long-lived caches.

Fix: Add eviction/TTL to caches, always remove() ThreadLocals in finally blocks, use weak references for listeners, ensure unsubscribe paths exist, use bounded collections.

Q3: How does the JVM's JIT compiler optimize code, and what's escape analysis?

JIT optimizations: Method inlining (replaces method call with body — eliminates call overhead), loop unrolling (reduces branch overhead), dead code elimination, constant folding (evaluate constant expressions at compile time), branch prediction hints, and vectorization (SIMD instructions).

Escape analysis: The JIT determines if an object "escapes" the method or thread. If an object is local and never passed outside, the JIT can: allocate it on the stack instead of heap (scalar replacement), avoiding GC pressure entirely. Example: a temporary StringBuilder created and used within a single method often gets stack-allocated. Enable diagnostic output with -XX:+DoEscapeAnalysis -XX:+PrintEscapeAnalysis.

Q4: What tuning would you apply to a Java microservice running in a 2GB container?

# Container-aware settings -XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0 # 1.5GB heap, leaves 512MB for Metaspace/threads/off-heap -XX:InitialRAMPercentage=50.0 # start at 1GB, grow as needed -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=256m -Xss256k # reduce stack size if many threads -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/ -XX:+ExitOnOutOfMemoryError # let k8s restart the pod

For Spring Boot 3+ with virtual threads (Java 21): add -Dspring.threads.virtual.enabled=true — significantly reduces thread stack memory since virtual threads are cheap.
