2JWT Deep Dive

JSON Web Tokens are base64url-encoded JSON objects signed with HMAC or RSA/EC. Structure: header.payload.signature.

// JWT structure (decoded) // Header: {"alg":"RS256","typ":"JWT"} // Payload: {"sub":"user123","iss":"auth-service","aud":"api","iat":1700000000,"exp":1700003600,"roles":["USER"]} // Signature: RS256(base64url(header) + "." + base64url(payload), privateKey) // Spring Security JWT validation (spring-security-oauth2-resource-server) @Configuration public class SecurityConfig { @Bean public SecurityFilterChain filterChain(HttpSecurity http) throws Exception { http .sessionManagement(s -> s.sessionCreationPolicy(STATELESS)) .oauth2ResourceServer(oauth2 -> oauth2 .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter())) ) .authorizeHttpRequests(auth -> auth .requestMatchers("/public/**").permitAll() .requestMatchers("/admin/**").hasRole("ADMIN") .anyRequest().authenticated() ); return http.build(); } private JwtAuthenticationConverter jwtConverter() { JwtGrantedAuthoritiesConverter gac = new JwtGrantedAuthoritiesConverter(); gac.setAuthoritiesClaimName("roles"); // custom claim name gac.setAuthorityPrefix("ROLE_"); // Spring expects ROLE_ prefix JwtAuthenticationConverter converter = new JwtAuthenticationConverter(); converter.setJwtGrantedAuthoritiesConverter(gac); return converter; } @Bean public JwtDecoder jwtDecoder() { // Validates signature using public key from JWKS endpoint return NimbusJwtDecoder.withJwkSetUri("https://auth.example.com/.well-known/jwks.json").build(); } }
JWT Security Pitfalls 1. alg:none attack — attacker sets algorithm to "none", removing signature. Always explicitly specify allowed algorithms, never accept "none".
2. RS256 vs HS256 confusion — if server expects RS256 but also accepts HS256, attacker can sign with the public key as HMAC secret. Explicitly whitelist algorithm.
3. No expiry check — always validate "exp" claim and keep access tokens short-lived (15 min). Use refresh tokens for longer sessions.
4. Sensitive data in payload — JWT payload is base64url encoded, NOT encrypted. Don't store PII, passwords, or secrets in claims.

Token Refresh Strategy

// Short-lived access token + long-lived refresh token pattern: // Access token: 15 minutes, stateless JWT // Refresh token: 7 days, opaque token stored in DB (allows revocation) @PostMapping("/auth/refresh") public TokenResponse refresh(@RequestBody RefreshRequest request) { RefreshToken stored = refreshTokenRepo.findByToken(request.getRefreshToken()) .orElseThrow(() -> new UnauthorizedException("Invalid refresh token")); if (stored.isExpired()) { refreshTokenRepo.delete(stored); throw new UnauthorizedException("Refresh token expired"); } refreshTokenRepo.delete(stored); // rotate: single-use refresh token String newAccess = jwtService.generate(stored.getUserId()); RefreshToken newRefresh = refreshTokenRepo.save(createRefreshToken(stored.getUserId())); return new TokenResponse(newAccess, newRefresh.getToken()); }

Symmetric Encryption

// AES-256-GCM: authenticated encryption (provides confidentiality + integrity) public class AesGcmEncryptor { private static final int GCM_IV_LENGTH = 12; private static final int GCM_TAG_LENGTH = 128; public byte[] encrypt(byte[] plaintext, SecretKey key) throws Exception { byte[] iv = new byte[GCM_IV_LENGTH]; new SecureRandom().nextBytes(iv); // random IV, never reuse Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding"); cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(GCM_TAG_LENGTH, iv)); byte[] ciphertext = cipher.doFinal(plaintext); // Prepend IV to ciphertext (IV is not secret, needed for decryption) byte[] result = new byte[iv.length + ciphertext.length]; System.arraycopy(iv, 0, result, 0, iv.length); System.arraycopy(ciphertext, 0, result, iv.length, ciphertext.length); return result; } } // Secret key generation KeyGenerator keyGen = KeyGenerator.getInstance("AES"); keyGen.init(256, new SecureRandom()); SecretKey key = keyGen.generateKey(); // Store keys in: AWS KMS, HashiCorp Vault, Azure Key Vault — NEVER in code/config

QInterview Q&A

Q1: How would you implement stateless authentication in a Spring Boot microservices environment?

Architecture: Centralized Auth Service issues JWTs (short-lived access tokens, 15 min). Each microservice validates the JWT independently using the auth service's public key (JWKS endpoint — no network call per request once keys are cached). API Gateway can also validate JWTs before forwarding requests.

Implementation: Auth Service uses spring-authorization-server or integrates with Keycloak/Auth0. Resource services use spring-security-oauth2-resource-server with NimbusJwtDecoder pointing to the JWKS URI. Extract claims (user ID, roles) from the SecurityContext.

Revocation challenge: Stateless JWTs can't be revoked before expiry. Mitigations: keep access tokens short-lived (15 min), use opaque refresh tokens stored in DB (revocable), maintain a small bloom filter / denylist for immediately-revoked tokens (logout, compromised), or use token introspection endpoint.

Q2: What's the difference between authentication and authorization, and how does Spring Security model them?

Authentication (AuthN) answers "who are you?" — Spring Security represents the authenticated principal as an Authentication object stored in SecurityContextHolder. The AuthenticationManager (backed by AuthenticationProvider) handles the verification process.

Authorization (AuthZ) answers "what can you do?" — Spring Security uses GrantedAuthority objects (typically roles like "ROLE_ADMIN") attached to the Authentication. The AccessDecisionManager (or the newer AuthorizationManager in Spring Security 6) evaluates these against security rules defined in SecurityFilterChain (URL-based) or @PreAuthorize annotations (method-level).

Key classes: SecurityContextHolder → Authentication → Collection<GrantedAuthority>. For JWT: JwtAuthenticationConverter maps JWT claims to GrantedAuthority instances.

Q3: How do you prevent SSRF (Server-Side Request Forgery) in a Java application?

SSRF occurs when an attacker tricks your server into making requests to internal services by providing a URL your application fetches (e.g., an image URL field, webhook URL, report generation endpoint).

Prevention: 1) Allowlist approach — only permit requests to explicitly approved domains/IPs; reject everything else. 2) Validate URLs before fetching: resolve DNS and check if the resolved IP is in private ranges (10.x, 172.16-31.x, 192.168.x, 127.x, 169.254.x — AWS metadata). 3) Use an egress proxy that enforces allowlists. 4) Disable redirects, or validate redirect destinations. 5) Apply network-level controls: microservices should only have outbound access to what they need (network policies in k8s).

// URL validation example public void validateUrl(String userUrl) { URL url = new URL(userUrl); if (!ALLOWED_SCHEMES.contains(url.getProtocol())) { throw new SecurityException("Scheme not allowed"); } InetAddress addr = InetAddress.getByName(url.getHost()); if (addr.isLoopbackAddress() || addr.isSiteLocalAddress() || addr.isLinkLocalAddress()) { throw new SecurityException("Access to private network not allowed"); } }

Q4: How do you securely store and rotate secrets in a Spring Boot application?

Never store secrets in: code (hardcoded strings), VCS/git (even in private repos — git history persists), application.properties in source control, environment variables in Dockerfiles or k8s manifests committed to git.

Correct approach: Use a secrets manager. Spring Cloud Vault (HashiCorp Vault), AWS Secrets Manager via Spring Cloud AWS, or Kubernetes Secrets (base64 is not encryption — use sealed-secrets or external-secrets-operator). At runtime, secrets are injected as environment variables or resolved via @ConfigurationProperties / @Value from a secrets backend, not files.

Rotation: Use Spring Cloud Vault with lease renewal — Spring Boot auto-refreshes @RefreshScope beans when secrets rotate. For DB credentials, use Vault's dynamic secrets (Vault generates a short-lived DB user, renews the lease, then revokes it — no rotation ceremony needed).
