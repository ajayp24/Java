System Design

System design interviews test your ability to translate vague requirements into a concrete, scalable architecture — live, in 45 minutes. The frameworks here follow the standard flow: clarify → estimate → design → deep-dive. For each system, focus on the one or two design decisions that interviewers actually care about. Don't memorize diagrams — practice explaining trade-offs.

E-Commerce

E-Commerce Platform

Core

Users browse products, add items to a cart, and complete a checkout with payment. The system must handle product catalog search, session-based carts, and order processing — each with very different data and latency requirements.

10K concurrent users
100M products
50K orders/day
10M page views/day
<200ms product page
99.95% checkout uptime
Functional
  • Browse / search products by keyword, category, filters
  • Add / remove items from cart; cart persists across sessions
  • Checkout with address, payment method selection
  • Order confirmation; order history and tracking
  • Product reviews and ratings
Non-Functional
  • Product pages: p99 < 200ms (CDN-cached)
  • Search: p99 < 300ms (Elasticsearch)
  • Cart: always available (Redis, AP system)
  • Checkout: strongly consistent, no double charges
  • Images: served from CDN, not origin servers
High-Level Architecture Browser ──► CDN (images, static JS/CSS, cached catalog pages) │ └──► API Gateway (auth, rate limit, routing) │ ┌──────────┼──────────┬──────────────┬────────────┐ ▼ ▼ ▼ ▼ ▼ Product Search Cart Order Payment Service Service Service Service Service (Postgres) (Elastic- (Redis TTL (Postgres (async, + S3 imgs search) session-key) state m/c) idempotent) │ │ Kafka topic: orders │ │ │ Inventory Ship Notification Service Svc Service
Key Component Decisions
  • Product catalog: PostgreSQL for writes; Elasticsearch for full-text search. Sync via Debezium CDC on the products table.
  • Cart: Redis with HSET cart:{userId} — O(1) add/remove, TTL expiry for abandoned carts. Store SKU + quantity; hydrate prices at checkout (never store price in cart — prices change).
  • Product images: upload to S3, serve via CloudFront with immutable URL caching. Thumbnails generated by Lambda on S3 event.
  • Checkout flow: reserve inventory → charge payment → confirm order. If payment fails, release inventory reservation immediately.
  • Sessions: JWT for auth; guest carts use a cookie-based cart ID merged into user cart on login.
  • Read scaling: PostgreSQL read replicas for order history; Redis cache for product detail pages (TTL 5 min).
Interview Talk Track
  • First thing to say: "I'd separate the read path (catalog, search) from the write path (checkout, orders) — they have very different consistency requirements." This immediately shows architectural maturity.
  • Follow up: "Search is the hardest part to scale — I'd use Elasticsearch with sharding by category, and sync it asynchronously from Postgres via CDC rather than dual-writing."
  • Deep dive they'll ask: "How do you handle inventory overselling?" → optimistic locking with a reserved_quantity column + DB check constraint, or Redis DECR with floor check for hot items.

Payment System

Core

A payment system processes money movement: authorization, capture, settlement, and refunds. The two hardest problems are exactly-once processing (never charge twice) and auditability (immutable record of every state change). You don't build a card network — you integrate with a PSP (Stripe, Adyen) and build the ledger, idempotency, and fraud layers around it.

10K TPS peak
<500ms authorization
0 double charges tolerated
7 years audit retention
Payment Flow Client ──► Payment API │ ├── 1. Check Idempotency Store (Redis, key = client's idempotencyKey) │ └── if found: return cached response (prevent double charge) │ ├── 2. Fraud Detection (ML score, velocity checks, geo-mismatch) │ └── if score > threshold: decline or challenge (3DS) │ ├── 3. Call PSP (Stripe/Adyen) → authorize card │ ├── 4. Write to Ledger DB (append-only, double-entry) │ ORDER_CHARGED: debit customer_wallet, credit merchant_wallet │ └── 5. Publish to Kafka: payment.completed └── Notification Service: receipt email └── Order Service: advance order state
Critical Design Points
  • Idempotency key: client generates a UUID per payment attempt and sends it as a header. Server stores result keyed by this UUID. On retry, returns cached result without re-charging. Key expires after 24h.
  • Double-entry ledger: every transaction creates two rows (debit + credit). Balance = sum of all credits - sum of all debits. Append-only — never UPDATE or DELETE a ledger row.
  • PSP timeout handling: if PSP call times out, you don't know if it succeeded. Query PSP for the payment status before deciding to retry or void.
  • Reconciliation: daily job compares your ledger totals against PSP settlement reports. Discrepancies trigger alerts.
  • Fraud detection: run as a synchronous pre-auth check. Features: same card used on multiple accounts, unusual geo, high velocity. Decline if risk score > threshold.
Never Say This in an Interview
  • "I'd use a distributed transaction (2PC) to atomically charge the card and update the DB" — PSPs don't support 2PC. You can't wrap a third-party API call in a local transaction. The correct answer is idempotency + reconciliation.

Order Management System

Core

An OMS orchestrates the lifecycle of an order from placement through delivery. The core complexity is a multi-step distributed workflow across inventory, payment, warehouse, and shipping systems — any of which can fail. The Saga pattern manages this; the state machine makes the order's position in that workflow explicit.

Order State Machine + Saga CREATED ──► PAYMENT_PENDING ──► PAID ──► WAREHOUSE_ASSIGNED │ │ │ payment failed │ picking started ▼ ▼ PAYMENT_FAILED PICKING ──► PACKED ──► SHIPPED ──► DELIVERED │ │ out of stock ▼ CANCELLED (compensate: refund payment) Compensating Transactions: PAID → CANCELLED : trigger refund via Payment Service WAREHOUSE_ASSIGNED → CANCELLED : release warehouse slot PICKING → CANCELLED : restock items, refund
Design Decisions
  • State machine: store current state as an enum column. Transitions validated in code (and optionally with DB check constraints). Log every transition with timestamp + actor.
  • Saga orchestration: an Order Orchestrator service sends commands (ReserveInventory, ChargePayment) and waits for replies via Kafka. Easier to trace and debug than choreography for a complex flow.
  • Idempotent steps: each saga step must be idempotent — the orchestrator may resend a command if it doesn't receive a reply within a timeout. Steps check if they've already processed the command by event ID.
  • Order history: append-only event log per order (event sourcing light). Every state change is an event with timestamp; the UI renders the full timeline from these events.
  • Customer cancellation window: orders in PAID or WAREHOUSE_ASSIGNED state can be cancelled by the customer; PICKING or later require customer support intervention.

Inventory System

Important

Inventory tracks physical stock: quantities on hand, reserved, and available. The core challenge is concurrent reservation — when 100 users try to buy the last unit simultaneously, exactly one should succeed. At large scale this becomes a hot-key problem in the database.

1M SKUs
100K reservations/min peak
0 oversells
hot SKUs flash sale problem
Concurrency StrategyMechanismTrade-offWhen to Use
DB Optimistic LockUPDATE SET qty=qty-1 WHERE qty>0 AND version=?Retry storm under contentionLow-to-medium concurrency per SKU
DB Pessimistic LockSELECT FOR UPDATESerialized throughput, deadlock riskLow concurrency, short transactions
Redis DECRLua script: DECR + floor check atomicallyCache/DB sync complexityHot SKUs, flash sales, very high QPS
Pre-allocationAssign stock buckets to instancesUneven depletion between bucketsVery large flash sales (millions of units)
Stock Model
  • quantity_on_hand: physical count in warehouse
  • quantity_reserved: held for pending orders (released after 30 min if not paid)
  • quantity_available = on_hand − reserved. This is what's shown to customers.
  • Reservation TTL: on checkout start, reserve stock with a 30-min TTL (Redis sorted set for expiry). Confirmed on payment; released on timeout or cancellation.
  • Threshold alerts: Kafka events when available quantity drops below reorder point → triggers supplier reorder workflow.

Notification System

Important

A notification system delivers messages across multiple channels — email, SMS, push, in-app — triggered by events from any service. The design must handle high throughput, user preferences, retries for failed deliveries, and channel routing logic without coupling producer services to delivery details.

10M notifications/day
4 channels (email/SMS/push/in-app)
<5s delivery p99
retry on failure w/ backoff
Notification Architecture Any Service ──► Kafka: notification-requests topic │ Notification Router ├── lookup user preferences ├── render template (Handlebars/Freemarker) └── fan-out to channel queues │ ┌────────────┼────────────┬────────────┐ ▼ ▼ ▼ ▼ Email Queue SMS Queue Push Queue In-App Queue SES/SendGrid Twilio FCM/APNs WebSocket worker worker worker worker │ │ dead-letter dead-letter queue (DLQ) queue (DLQ) │ Retry after Alert after 3 failures → ops dashboard exp. backoff
Design Points
  • User preferences: per-user, per-event-type opt-in/opt-out stored in DB. Router checks preferences before dispatching to any channel. Respect unsubscribes within 10 seconds.
  • Templates: store versioned templates in DB. Router fetches template by notification type, renders with event payload data. Never hardcode content in code.
  • Rate limiting: per-user rate limit (max 5 SMS/hour) enforced in Redis. Prevents notification storms during bug or runaway event loop.
  • Deduplication: idempotency key per notification event. If the same event is published twice (Kafka at-least-once), the router skips duplicates using a Redis seen-set with 24h TTL.
  • Priority lanes: separate Kafka partitions for critical (OTP codes, fraud alerts) vs promotional. Critical lane is always processed; promotional can be throttled.

File Upload Service

Important

A file upload service accepts large files from clients, stores them durably, and makes them accessible via a CDN. The key insight: don't route large binary data through your application servers — use presigned URLs to let clients upload directly to S3. Your servers handle metadata and coordination only.

10M uploads/day
5GB max file size
resumable uploads required
virus scan before serving
Upload Flow (Presigned URL Pattern) Client Your API S3 Processing │ │ │ Pipeline │─ POST /upload/init ────►│ │ │ │◄─ presigned S3 URL ─────│ │ │ │ (signed, expires in 15min) │ │ │ │ │ │─── PUT binary data ────────────────────────►│ │ │◄── 200 OK (ETag) ──────────────────────────│ │ │ │ │ │─ POST /upload/complete ─►│ │ │ │ │─ S3 event ──────┤─ SQS/SNS ────────────►│ │ │ │ ┌────────┴──────┐ │ │ │ Virus scan Thumbnail gen │◄─ file metadata ─────────│◄─ update DB ────│ │ │ │ { id, url, status } │ │ quarantine S3 thumb if infected bucket → CDN
Key Decisions
  • Presigned URL: your API calls s3.generatePresignedUrl(PUT, bucket, key, 15min) and returns it to the client. Client uploads directly — your servers handle zero bytes of file content. This is the answer that impresses interviewers.
  • Chunked / resumable upload: for files >100MB, use S3 Multipart Upload. Client splits into 5MB+ chunks, uploads each part, then calls CompleteMultipartUpload. On network failure, resume by listing already-uploaded parts.
  • Virus scanning: scan in quarantine bucket (not public) before moving to production bucket. Use ClamAV or a managed service (AWS GuardDuty malware scanning). Never serve unscanned files.
  • File deduplication: hash file content (SHA-256) on upload. If hash already exists in DB, skip the upload and return the existing file URL. Saves storage and egress costs.
  • Access control: private files use short-lived presigned GET URLs (15 min). Public files use CloudFront URLs. Store access policy in DB per file.

URL Shortener

Core

A URL shortener maps a short code to a long URL and redirects with sub-10ms latency. It's the canonical "simple-looking but scale-interesting" system design problem. The two hard parts are unique code generation at scale and making redirects fast enough to not be perceptible.

500M URLs total
100K redirects/sec
10 write / sec (creates)
<10ms redirect p99
5 years retention
URL Shortener Architecture Write path: Client ──► POST /shorten ──► API Server ├── generate base62 code (7 chars = 62^7 = 3.5 trillion) │ Approach: auto-increment ID → base62 encode │ (avoids guessability of sequential; prefix with shard ID) ├── store: { code, long_url, user_id, created_at, expires_at } │ in PostgreSQL + write-through to Redis └── return: https://short.ly/{code} Read path (redirect — hot path): Client ──► GET /abc123 ──► CDN (cache-control: max-age=3600 for stable URLs) │ └──(miss)──► API Server ──► Redis cache (O(1) lookup) │ └──(miss)──► PostgreSQL └── return 301/302 └── async: Kafka → analytics
Code Generation — Critical Decision
  • Base62 encode auto-increment ID: simplest, no collision. DB auto-increment → convert to base62 (0-9, a-z, A-Z). 7 chars gives 3.5 trillion unique codes. The ID generation is the only thing needing coordination.
  • 301 vs 302: 301 (permanent) is cached by browsers — analytics will miss future clicks from cached redirects. 302 (temporary) hits your server every time — better for analytics, higher cost. Pick 302 for analytics products; 301 for pure shortening.
  • Custom aliases: check availability against the code namespace. Store in same table with is_custom = true; reserve a prefix range for user-defined codes.
  • Expiry: store expires_at as nullable timestamp. Scheduled job deletes expired URLs and invalidates CDN cache. Deleted codes can be recycled after 90 days.
  • Analytics: publish click events to Kafka asynchronously. Consumer writes to ClickHouse (OLAP) for time-series click aggregation. Never block the redirect for analytics.

Chat Application

Important

A real-time chat application delivers messages between users with low latency and guaranteed ordering. The core problems are: how do messages reach online users instantly (WebSocket push), how do offline users receive missed messages (pull on reconnect), and how do you guarantee ordering in group chats.

50M daily active users
10B messages/day
100ms delivery p99
group chats up to 1000 members
Chat Architecture User A (online) WebSocket Cluster Message Service DB │ ┌────────────────┐ │ ├─── connect ───────►│ WS Server A │ │ │ (long-lived) │ (Node/Netty) │ │ │ └────────┬───────┘ │ │ │ pub to Kafka │ User B (online, ┌────────┴───────┐ │ different server) │ WS Server B ├── subscribe │ ◄─── push msg ──────┤ │ from Kafka │ └────────────────┘ │ │ Online presence: Redis SET ws-server:{userId} = serverA (TTL 60s, heartbeat) Message storage: Cassandra (write-heavy, time-series, userId + chatId partition key) Offline delivery: on reconnect, client sends lastSeenMessageId → server fetches newer messages Push (mobile offline): APNs/FCM via Notification Service
Key Decisions
  • WebSocket fan-out: when User A sends to group, Message Service publishes to Kafka topic partitioned by chatId. Each WS server subscribes and pushes to connected members. This decouples WS servers — User A's server doesn't need to know which server User B is on.
  • Message ordering: use a monotonically increasing sequence_id per chat (Redis INCR per chatId). Messages stored and delivered in sequence order. Client reorders if gap detected.
  • Read receipts: client sends ACK (messageId, userId) when message is displayed. Stored in Redis bitmap or Cassandra counter. Delivered as a separate event back to sender's WS connection.
  • Cassandra schema: partition key = (chatId), clustering key = (sequenceId DESC). Efficient for "load last 50 messages" query.
  • Media: same presigned-URL S3 pattern as file upload. Message contains S3 URL, not binary data.

Banking System

Advanced

A core banking system manages accounts, processes transfers, and maintains a complete audit trail. Unlike e-commerce, a banking system prioritizes consistency over availability (CP not AP) — an incorrect balance is never acceptable. Every money movement must be atomic, auditable, and reversible through compensating entries, not deletions.

CP system (consistency first)
ACID transactions mandatory
7 years regulatory retention
immutable ledger
Banking Architecture Client ──► API Gateway ──► Account Service │ ┌──────┴────────┐ │ │ Balance Query Transaction Service (read replica) │ 1. Validate: sufficient funds, account active 2. Begin DB transaction 3. INSERT into ledger (debit + credit entries) 4. UPDATE account balances 5. Commit 6. Publish event to Kafka │ ┌──────┴──────┐ AML/Compliance Notification (async ML scan) (statement)
Ledger Design
  • Double-entry bookkeeping: every transfer = 2 ledger rows. Transfer $100 from A to B: DEBIT account_A $100 + CREDIT account_B $100. Ledger sum always = 0. This makes fraud and corruption detectable by simple sum checks.
  • Immutability: ledger rows are NEVER updated or deleted. Corrections are made via new compensating entries. This preserves complete audit trail.
  • Optimistic concurrency on accounts: accounts table has a version column. Transfer updates both accounts in a single transaction with WHERE version = ? check. Retry on conflict.
  • Event sourcing: treat ledger entries as the event store. Account balance is a projection (sum of ledger entries). Can rebuild balance at any point in history.
  • AML/compliance: async consumer on transaction events. Applies ML models to detect suspicious patterns. Does NOT block the transaction — files a SAR asynchronously if flagged.

Ride Sharing

Advanced

A ride-sharing platform matches riders to nearby available drivers in real time. The hardest problems are: efficiently finding nearby drivers (geospatial indexing), matching under contention (driver gets two requests simultaneously), and tracking continuously moving assets. Location data is extremely write-heavy — millions of GPS updates per second.

5M active drivers
500K location updates/sec
<5s match time
geospatial radius search
Ride Sharing Architecture Location Update (write-heavy): Driver App ──► Location Service ──► Redis GEOADD driver:{city} lon lat driverId (Redis GEO index, TTL-refreshed per update) └──► Kafka: location-updates (async DB persist, analytics) Ride Request: Rider App ──► Ride API ──► Matching Service │ 1. GEORADIUS drivers:{city} lng lat 3km ASC COUNT 20 2. Filter: available drivers only (status = AVAILABLE in Redis) 3. Offer to nearest driver (WebSocket push, 10s timeout) 4. If decline/timeout → offer to next driver in list 5. On accept: create Trip in PostgreSQL │ ┌──────────┴────────────────┐ Surge Pricing Notification (supply/demand (rider: driver ratio in Redis) details; driver: pickup location)
Key Decisions
  • Redis GEORADIUS: Redis stores driver locations as a geospatial sorted set (Haversine formula under the hood). GEORADIUS returns drivers within N km sorted by distance in O(N+log(M)) time. City-sharded: one key per city to avoid hot keys.
  • Driver state: Redis hash driver:{id} with status (AVAILABLE/ON_TRIP/OFFLINE) and TTL. If driver app goes offline, TTL expires and driver is removed from available pool automatically.
  • Match contention: two riders may simultaneously match the same driver. Use a Redis distributed lock (Redlock) when offering a trip to a driver. If lock fails, move to next candidate.
  • Surge pricing: calculate supply/demand ratio per geohash cell every 30 seconds. If demand > supply by threshold, apply surge multiplier. Store current multiplier in Redis; recalculate async.
  • ETA calculation: call routing service (OSRM, Google Maps API) with driver's current position and pickup coordinates. Update estimated arrival as driver moves.
Specialized

Large-scale REST API

Core

Designing a REST API for millions of requests per second requires layered caching, horizontal scaling, and robust cross-cutting concerns (auth, rate limiting, versioning). This is the horizontal concern underlying every other system in this round — the API layer is how all those systems are exposed.

1M RPS
10K clients
p99 <100ms
99.99% uptime
API Scaling Stack Request ──► DNS (GeoDNS → nearest region) ──► CDN (GET responses cached by URL+Vary:Authorization) ──► Load Balancer (L7, sticky sessions optional) ──► API Gateway ├── JWT validation (public key, no DB hit) ├── Rate limiting (Redis token bucket per clientId) ├── Request routing (path → service) └── Circuit breaker (downstream protection) ──► Service instances (stateless, horizontal scale) ├── L1 cache: in-process Caffeine (nanoseconds, per-instance) ├── L2 cache: Redis cluster (milliseconds, shared) └── DB: PostgreSQL with read replicas └── Connection pool: HikariCP (sized to CPU × 2)
Critical Design Points
  • Auth at gateway: validate JWT using cached public key (no DB call on every request). Downstream services trust the X-User-Id header injected by the gateway — they don't re-validate.
  • Cache hierarchy: CDN (minutes, shared globally) → API Gateway cache (seconds, by route) → Service L1 cache (milliseconds, per instance) → Redis L2 (milliseconds, shared) → DB. Most requests should never reach the DB.
  • Rate limiting strategy: per-client token bucket in Redis. Return 429 Too Many Requests with Retry-After and X-RateLimit-Remaining headers. Separate limits for authenticated vs anonymous clients.
  • API versioning: URL versioning (/v1/, /v2/) for breaking changes. Maintain N-1 versions; announce deprecation 6 months in advance with Sunset header on deprecated routes.
  • Observability: every response includes X-Request-Id (trace ID). Log request/response metadata (not body) at gateway level. Prometheus metrics: request rate, error rate, latency histograms per route.
  • Graceful degradation: non-critical downstream failures return cached stale data with a Warning header. Critical failures return 503 with Retry-After.
System Design Interview Framework
  • Step 1 — Clarify (5 min): functional requirements (what users do), scale numbers (users, QPS, data size), SLA (latency, availability), geographic scope.
  • Step 2 — Estimate (3 min): storage (bytes × records), bandwidth (bytes × QPS), cache hit ratio target. Say numbers out loud — interviewers want to hear you think.
  • Step 3 — High-level (10 min): draw the main components with data flows. Name the tech choices (Postgres not just "a database"). Justify every choice with one sentence.
  • Step 4 — Deep dive (20 min): pick the hardest problem and go deep. Concurrency, failure modes, bottlenecks. Interviewers drive this — listen to what they ask about.
  • Step 5 — Trade-offs (5 min): what would you change under different constraints? What are the current bottlenecks? Shows senior thinking.
