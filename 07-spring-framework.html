1. IoC Container & Dependency Injection

IoC (Inversion of Control): instead of classes creating their own dependencies, the container creates and injects them. Spring achieves this with the ApplicationContext (an IoC container).

DI Types

// Constructor injection (PREFERRED — immutable, testable, required deps clear) @Service public class OrderService { private final OrderRepository repo; private final PaymentService payment; // @Autowired optional when single constructor (Spring 4.3+) public OrderService(OrderRepository repo, PaymentService payment) { this.repo = repo; this.payment = payment; } } // Field injection (AVOID — not testable without Spring context, hides deps) @Autowired private OrderRepository repo; // bad practice // Qualifier — when multiple beans of same type @Bean("primaryDataSource") public DataSource primaryDataSource() { ... } @Bean("secondaryDataSource") public DataSource secondaryDataSource() { ... } @Autowired @Qualifier("primaryDataSource") private DataSource dataSource; // @Primary — default when no @Qualifier specified @Bean @Primary public DataSource mainDataSource() { ... }

2. Bean Lifecycle & Scopes

// Bean lifecycle hooks @Component public class CacheManager { @PostConstruct public void init() { // called after all dependencies injected — load cache, open connections } @PreDestroy public void cleanup() { // called before bean destroyed — close resources, flush cache } }
ScopeDescriptionUse Case
singleton (default)One instance per ApplicationContextServices, repositories, utilities
prototypeNew instance each time requestedStateful objects, command objects
requestOne per HTTP request (web only)Request-specific state
sessionOne per HTTP session (web only)User session state
applicationOne per ServletContext (web only)App-wide shared state in web apps
Injecting a prototype-scoped bean into a singleton bean means the singleton always gets the same prototype instance (at creation time). Fix: inject ApplicationContext and call getBean() each time, or use @Lookup methods.

3. Auto-Configuration

Spring Boot reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports to find autoconfiguration classes. Each uses @ConditionalOn* to decide whether to apply.

// How autoconfiguration works — simplified @AutoConfiguration @ConditionalOnClass(DataSource.class) // only if DataSource on classpath @ConditionalOnMissingBean(DataSource.class) // only if user hasn't defined one @EnableConfigurationProperties(DataSourceProperties.class) public class DataSourceAutoConfiguration { @Bean public DataSource dataSource(DataSourceProperties props) { return props.initializeDataSourceBuilder().build(); } } // @ConfigurationProperties — type-safe binding to application.yml @ConfigurationProperties(prefix = "app.cache") public record CacheProperties(int ttlSeconds, int maxSize, String type) {} // application.yml: // app.cache.ttl-seconds: 300 // app.cache.max-size: 1000 // app.cache.type: redis // Profile-specific configuration @Bean @Profile("production") public CacheService redisCacheService() { ... } @Bean @Profile("!production") // all non-production profiles public CacheService inMemoryCacheService() { ... }

4. Spring MVC Request Lifecycle

// Request flow: Browser → DispatcherServlet → HandlerMapping → Interceptor → Controller → ViewResolver @RestController @RequestMapping("/api/v1/orders") public class OrderController { @GetMapping("/{id}") public ResponseEntity<OrderDto> getOrder(@PathVariable Long id) { return service.findById(id) .map(ResponseEntity::ok) .orElseThrow(() -> new OrderNotFoundException(id)); } @PostMapping @ResponseStatus(HttpStatus.CREATED) public OrderDto createOrder(@Valid @RequestBody CreateOrderRequest req) { return service.create(req); } @GetMapping public Page<OrderDto> listOrders( @RequestParam(defaultValue = "0") int page, @RequestParam(defaultValue = "20") int size, @RequestParam(required = false) String status) { return service.findAll(PageRequest.of(page, size), status); } } // Global exception handler @RestControllerAdvice public class GlobalExceptionHandler { @ExceptionHandler(OrderNotFoundException.class) @ResponseStatus(HttpStatus.NOT_FOUND) public ErrorResponse handleNotFound(OrderNotFoundException ex) { return new ErrorResponse("ORDER_NOT_FOUND", ex.getMessage()); } @ExceptionHandler(MethodArgumentNotValidException.class) @ResponseStatus(HttpStatus.BAD_REQUEST) public ErrorResponse handleValidation(MethodArgumentNotValidException ex) { var errors = ex.getBindingResult().getFieldErrors().stream() .map(e -> e.getField() + ": " + e.getDefaultMessage()) .collect(Collectors.joining(", ")); return new ErrorResponse("VALIDATION_FAILED", errors); } }

5. AOP — Aspect-Oriented Programming

AOP allows cross-cutting concerns (logging, security, transactions) to be modularized. Spring AOP uses JDK dynamic proxies (for interfaces) or CGLIB proxies (for classes).

@Aspect @Component public class PerformanceAspect { // Pointcut expression — all public methods in service package @Pointcut("execution(public * com.example.service.*.*(..))") public void serviceMethods() {} // Around advice — wraps method execution (most powerful) @Around("serviceMethods()") public Object measureTime(ProceedingJoinPoint pjp) throws Throwable { long start = System.currentTimeMillis(); try { return pjp.proceed(); // MUST call proceed() to invoke real method } finally { long elapsed = System.currentTimeMillis() - start; log.info("{} took {}ms", pjp.getSignature().toShortString(), elapsed); } } // Annotation-based pointcut @Around("@annotation(com.example.annotation.Audited)") public Object audit(ProceedingJoinPoint pjp) throws Throwable { Audited annotation = getAnnotation(pjp, Audited.class); Object result = pjp.proceed(); auditLog.record(pjp, result, annotation.action()); return result; } } // AOP LIMITATION: self-invocation bypasses proxy! @Service class OrderService { public void placeOrder(Order o) { this.validate(o); // @Transactional on validate() BYPASSED — called on 'this', not proxy } @Transactional public void validate(Order o) { ... } // not called through proxy here }

9. Interview Q&A

What is the difference between @Component, @Service, @Repository, and @Controller?
All four are specializations of @Component and trigger Spring bean creation via component scanning. The differences are semantic and functional:

@Repository adds exception translation — Spring wraps persistence-related exceptions (SQLException, Hibernate exceptions) into Spring's DataAccessException hierarchy, so higher layers don't need to know about the DB technology.

@Controller marks a class to handle HTTP requests. @RestController combines @Controller + @ResponseBody.

@Service has no extra functionality currently — it serves as documentation that this is a business service layer.

@Component is generic — use it for anything that doesn't fit the above three.
How does Spring @Transactional work and what are its gotchas?
@Transactional works via AOP proxy. When a @Transactional method is called, the proxy intercepts the call, starts a transaction (or joins an existing one based on propagation), calls the real method, then commits or rolls back.

Key gotchas:
1. Self-invocation — calling @Transactional from within the same class bypasses the proxy entirely. Fix: inject self, or restructure.
2. Default rollback only on RuntimeException — checked exceptions don't trigger rollback by default. Use rollbackFor = Exception.class to change this.
3. @Transactional on private methods — ignored by Spring AOP (CGLIB can't proxy private methods). Must be public.
4. Propagation.REQUIRES_NEW — creates a new transaction even if one exists. Useful for audit logging that must succeed even if outer tx rolls back.
5. LazyInitializationException — accessing a lazy-loaded association after the transaction closes. Fix: fetch joins, @Transactional on service method, or use DTOs.
Explain Spring Boot auto-configuration and how you would debug it.
Auto-configuration reads classes listed in spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports on the classpath. Each auto-config class is conditional — it only applies if certain classes are present (@ConditionalOnClass), beans are missing (@ConditionalOnMissingBean), or properties match (@ConditionalOnProperty).

Debug steps:
1. --debug flag or debug=true in application.properties — prints a "Conditions Evaluation Report" showing every auto-config class and WHY it was applied or excluded.
2. Actuator /actuator/conditions endpoint shows the same at runtime.
3. Add @SpringBootTest(properties = "spring.autoconfigure.exclude=...") to exclude specific configs in tests.
How would you implement caching in a Spring Boot application?
Spring provides an abstraction via @EnableCaching and @Cacheable/@CacheEvict/@CachePut annotations. The backing store can be in-memory (ConcurrentHashMap), Caffeine, Redis, Hazelcast, etc.

Pattern:
1. Add @EnableCaching to a @Configuration class
2. Configure CacheManager bean (RedissonCacheManager, CaffeineCacheManager, etc.)
3. Annotate methods with @Cacheable(value = "users", key = "#id")
4. Use @CacheEvict(value = "users", key = "#user.id") on update/delete methods

For production: Use Redis for distributed caching. Define TTL per cache. Add cache statistics metrics. Handle cache stampede with probabilistic early expiration or locking.
