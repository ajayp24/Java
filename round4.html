Database & Persistence

The persistence layer is where most production incidents live — N+1 queries, missing indexes, lock contention, and connection pool exhaustion. This round covers the full stack from raw JDBC through JPA/Hibernate, transaction management, and the performance tuning a team lead must know to review PRs and lead incident post-mortems.

Foundation

JDBC

Core

JDBC (Java Database Connectivity) is the low-level API that all higher-level frameworks (JPA, Spring Data) sit on top of. Understanding it directly illuminates what those abstractions are doing. The core objects are Connection, PreparedStatement, and ResultSet. Always use PreparedStatement — never Statement with string concatenation — to prevent SQL injection and enable server-side query caching.

JDBC Fundamentals
  • Connection: physical link to the database — expensive to create, must always be closed.
  • PreparedStatement: pre-compiled, parameterized SQL — safe from injection, faster for repeated execution.
  • ResultSet: cursor over query results — forward-only by default; close it promptly.
  • Auto-commit: on by default — every statement is its own transaction. Disable for multi-statement transactions.
  • Batch updates: addBatch() / executeBatch() sends multiple statements in one round-trip — critical for bulk inserts.
JAVAJDBC best practices — try-with-resources, batch insert
// Always use try-with-resources — guarantees close() even on exception
public Optional<Order> findById(DataSource ds, long id) throws SQLException {
    String sql = "SELECT id, customer_id, total FROM orders WHERE id = ?";
    try (Connection conn = ds.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {

        ps.setLong(1, id);              // positional, 1-based
        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) {
                return Optional.of(new Order(
                    rs.getLong("id"),
                    rs.getString("customer_id"),
                    rs.getBigDecimal("total")
                ));
            }
            return Optional.empty();
        }
    }
}

// Batch insert — single round-trip for N rows
public void bulkInsert(DataSource ds, List<Order> orders) throws SQLException {
    String sql = "INSERT INTO orders (customer_id, total) VALUES (?, ?)";
    try (Connection conn = ds.getConnection()) {
        conn.setAutoCommit(false);           // manual transaction
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            for (Order o : orders) {
                ps.setString(1, o.getCustomerId());
                ps.setBigDecimal(2, o.getTotal());
                ps.addBatch();
            }
            ps.executeBatch();
            conn.commit();
        } catch (SQLException e) {
            conn.rollback();
            throw e;
        }
    }
}
SQL Injection — Never Concatenate
  • "SELECT * FROM users WHERE name = '" + input + "'" — classic injection vector. Always use PreparedStatement with ? placeholders.
  • ResultSet columns are 1-based by index but string-named access by column name is clearer and survives column reordering.

JPA

Core

JPA (Jakarta Persistence API) is a specification — a set of interfaces — for ORM in Java. It maps Java objects to database tables, manages an entity lifecycle, and provides JPQL (object-oriented query language). Hibernate is the most common JPA implementation. JPA's key abstraction is the EntityManager, which tracks entities in a persistence context (first-level cache).

JPA Layer Stack ┌─────────────────────────────────────────┐ │ Your Application Code │ │ Repository / Service / Controller │ ├─────────────────────────────────────────┤ │ Spring Data JPA │ ← generates implementations at runtime ├─────────────────────────────────────────┤ │ JPA API (specification) │ ← EntityManager, JPQL, @Entity, @Query ├─────────────────────────────────────────┤ │ Hibernate ORM (implementation) │ ← SQL generation, caching, proxies ├─────────────────────────────────────────┤ │ JDBC / DataSource │ ← PreparedStatement, ResultSet ├─────────────────────────────────────────┤ │ Database (Postgres, MySQL…) │ └─────────────────────────────────────────┘
JAVA@Entity mapping + Spring Data JPA repository
@Entity
@Table(name = "orders",
       indexes = @Index(name = "idx_orders_customer", columnList = "customer_id"))
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "customer_id", nullable = false, length = 36)
    private String customerId;

    @Column(precision = 10, scale = 2)
    private BigDecimal total;

    @Enumerated(EnumType.STRING)     // store as "PENDING", not 0
    private OrderStatus status;

    @Version                          // optimistic locking
    private Long version;

    @CreationTimestamp
    private Instant createdAt;
}

// Spring Data JPA — no implementation needed
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByCustomerIdAndStatus(String customerId, OrderStatus status);

    @Query("SELECT o FROM Order o WHERE o.total > :min ORDER BY o.createdAt DESC")
    Page<Order> findHighValueOrders(@Param("min") BigDecimal min, Pageable p);

    @Modifying
    @Query("UPDATE Order o SET o.status = :status WHERE o.id = :id")
    int updateStatus(@Param("id") Long id, @Param("status") OrderStatus status);
}
Persistence Context (First-Level Cache)
  • Within a transaction, loading the same entity twice returns the same Java object — Hibernate tracks it by primary key.
  • Changes to managed entities are auto-flushed to the DB at transaction commit — no explicit save() needed for updates.
  • @GeneratedValue(IDENTITY) disables JDBC batch inserts — use SEQUENCE strategy for bulk insert performance.
Foundation

Hibernate Internals

Important

Hibernate goes beyond the JPA spec with its own extensions: second-level cache (L2C), batch fetching, natural IDs, and StatelessSession. Understanding the dirty checking mechanism (Hibernate snapshots each loaded entity and compares at flush time) explains why loading thousands of entities is expensive even if you don't change them.

Hibernate Caching Layers
  • L1 Cache (Persistence Context): per-EntityManager, always on, cleared at transaction end. Prevents double-loading within one transaction.
  • L2 Cache: shared across EntityManagers / sessions. Requires explicit opt-in: @Cache(usage = CacheConcurrencyStrategy.READ_WRITE) + provider (Ehcache, Caffeine, Redis via Infinispan).
  • Query Cache: caches JPQL query result sets (IDs only) — useful for near-static lookup lists. Must be used with L2C.
  • StatelessSession: no persistence context, no dirty checking, no L1 cache — used for bulk ETL operations.
JAVAL2 cache + batch size + SQL logging
// application.yml — essential Hibernate settings
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50             # batch inserts/updates
          batch_versioned_data: true
          order_inserts: true         # group by type for batching
          order_updates: true
        cache:
          use_second_level_cache: true
          region:
            factory_class: JCacheRegionFactory
        format_sql: true
        generate_statistics: true    # expose via JMX / Actuator
    show-sql: false                  # use p6spy or datasource-proxy in dev instead
JAVAL2 cache on entity + StatelessSession bulk load
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)  // Hibernate annotation
public class Product { ... }

// StatelessSession — no dirty checking, no L1 cache, low memory for bulk reads
try (StatelessSession session = sessionFactory.openStatelessSession()) {
    ScrollableResults<Product> scroll = session
        .createQuery("FROM Product", Product.class)
        .setFetchSize(1000)
        .scroll(ScrollMode.FORWARD_ONLY);
    while (scroll.next()) {
        process(scroll.get());  // process one at a time, constant memory
    }
}

Entity Relationships

Core

JPA models four relationship types between entities. The owning side controls the foreign key column — always the side with the @JoinColumn. The inverse side uses mappedBy. Getting this wrong causes silent duplicate-insert bugs. For bidirectional associations, always maintain both sides in Java code.

AnnotationCardinalityDefault FetchNotes
@OneToOne1 : 1EAGERUse @MapsId for shared primary key. Prefer lazy.
@ManyToOneN : 1EAGEROwning side; always has @JoinColumn. Override to LAZY.
@OneToMany1 : NLAZYInverse side; use mappedBy. Avoid List + @OrderColumn unless needed.
@ManyToManyN : NLAZYUses join table. Prefer modeling as explicit entity with two @ManyToOne.
JAVABidirectional @OneToMany — both sides maintained
@Entity
public class Order {
    @Id @GeneratedValue private Long id;

    // Inverse side: mappedBy = field name on the owning OrderLine side
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL,
               orphanRemoval = true, fetch = FetchType.LAZY)
    private List<OrderLine> lines = new ArrayList<>();

    // Bidirectional helper — always maintain both sides
    public void addLine(OrderLine line) {
        lines.add(line);
        line.setOrder(this);
    }
    public void removeLine(OrderLine line) {
        lines.remove(line);
        line.setOrder(null);  // orphanRemoval will delete the row
    }
}

@Entity
public class OrderLine {
    @Id @GeneratedValue private Long id;

    // Owning side: holds the FK column
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;

    private String sku;
    private int quantity;
}
Cascade Traps
  • CascadeType.ALL includes REMOVE — cascading delete from a parent deletes all children. Verify this is intended.
  • Never use @ManyToMany without thinking twice — the join table has no natural place for extra columns (quantity, effective date). Model it as an explicit entity.
  • equals() / hashCode() on entities must be based on a stable business key or the database ID — never use the default reference-based equals in collections.

Lazy vs Eager Loading

Important

Fetch type controls when Hibernate issues the SQL for an association. LAZY: a proxy placeholder is returned; the real query fires on first access. EAGER: the association is loaded immediately in the same query (or a follow-up query). The defaults are: @ManyToOne / @OneToOne — EAGER (bad for performance); @OneToMany / @ManyToMany — LAZY. Always override @ManyToOne to LAZY and fetch explicitly when needed.

Rules of Thumb
  • Default everything to FetchType.LAZY — fetch eagerly at query time with JOIN FETCH or @EntityGraph.
  • EAGER on @ManyToOne triggers a JOIN (or extra query) for every parent load, even when the association is not needed.
  • LazyInitializationException: accessing a lazy association outside a transaction (after the session closes) — the proxy can't load. Fix by loading within the transaction or using DTOs/projections.
  • @Transactional on a service method keeps the session open for the method's duration — but not beyond.
JAVAFetch strategies — JOIN FETCH vs @EntityGraph
// JOIN FETCH in JPQL — loads association in same query
@Query("SELECT o FROM Order o JOIN FETCH o.lines WHERE o.customerId = :cid")
List<Order> findWithLines(@Param("cid") String cid);

// @EntityGraph — declarative, works on derived query methods too
@EntityGraph(attributePaths = {"lines", "lines.product"})
Optional<Order> findById(Long id);  // override: Spring Data default findById

// Projection DTO — select only what you need (best for read-only)
public record OrderSummary(Long id, String customerId, BigDecimal total) {}

@Query("SELECT new com.acme.OrderSummary(o.id, o.customerId, o.total) " +
       "FROM Order o WHERE o.status = :s")
List<OrderSummary> findSummariesByStatus(@Param("s") OrderStatus s);

// Interface projection — Spring Data generates implementation
public interface OrderView {
    Long getId();
    String getCustomerId();
}
List<OrderView> findByStatus(OrderStatus status);

N+1 Problem

Advanced

The N+1 problem is the single most common JPA performance bug. You load N parent entities (1 query), then access a lazy association on each — firing N more queries. With 1 000 orders, that's 1 001 database round-trips instead of 1. It's silent: the code looks correct, the tests pass (with small data sets), and it only becomes visible under production load.

JAVAN+1 — the problem and three solutions
// PROBLEM: loads 1000 orders, then fires 1000 more queries for lines
var orders = orderRepo.findAll();          // query 1
for (Order o : orders) {
    o.getLines().size();                    // query 2, 3, 4 … 1001
}

// ─── SOLUTION 1: JOIN FETCH in JPQL
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.lines")
List<Order> findAllWithLines();  // 1 query with JOIN

// ─── SOLUTION 2: @BatchSize — Hibernate fetches in IN(...) batches
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
@BatchSize(size = 50)              // loads lines for 50 orders per query
private List<OrderLine> lines;

// ─── SOLUTION 3: @EntityGraph on the repository method
@EntityGraph(attributePaths = "lines")
List<Order> findAll();  // Spring Data override with graph

// ─── DETECTION: datasource-proxy logs query count per request
// Or enable: hibernate.generate_statistics=true
// SessionFactory.getStatistics().getQueryExecutionCount()
JOIN FETCH + Pagination = Bug
  • Combining JOIN FETCH on a collection with Pageable causes Hibernate to load all rows in memory and paginate in Java — you see the warning HHH90003004: firstResult/maxResults specified with collection fetch.
  • Fix: use @BatchSize or a two-step approach — first page the IDs (SELECT o.id FROM Order o), then JOIN FETCH the full entities by the fetched IDs.
Transactions

Transactions & @Transactional

Core

A transaction groups operations into an atomic unit — all succeed or all roll back. Spring's @Transactional is implemented via AOP proxy: the proxy begins a transaction before the method and commits/rolls back after. This means self-invocation (calling an @Transactional method within the same bean) bypasses the proxy and the transaction.

Propagation Modes (most important)
  • REQUIRED (default): join existing transaction, or start a new one if none exists.
  • REQUIRES_NEW: always start a new transaction; suspend the existing one. Useful for audit logging that must commit even if the main transaction rolls back.
  • SUPPORTS: join if exists, run non-transactionally otherwise. Good for read-only methods that can work either way.
  • NOT_SUPPORTED: suspend any existing transaction. Rarely needed.
  • NEVER: throw if a transaction exists. For operations that must not run in a transaction.
  • MANDATORY: must have an existing transaction; throw if none.
JAVA@Transactional — rollback rules, readOnly, self-invocation trap
@Service
public class OrderService {

    // readOnly=true: hint to DB driver — read-only TX, no dirty checking, faster
    @Transactional(readOnly = true)
    public List<Order> findAll() {
        return repo.findAll();
    }

    // By default only RuntimeException/Error trigger rollback
    // rollbackFor includes checked exceptions too
    @Transactional(rollbackFor = Exception.class)
    public Order create(CreateOrderRequest req) throws InventoryException {
        Order order = repo.save(new Order(req));
        inventory.reserve(req.items());    // throws checked exception → rolls back
        return order;
    }

    // Audit log must persist even if caller rolls back
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void auditLog(String event) {
        auditRepo.save(new AuditEntry(event));
    }

    // SELF-INVOCATION BUG: proxy bypassed — auditLog runs in same TX
    @Transactional
    public void doSomething() {
        this.auditLog("did something"); // ← REQUIRES_NEW has NO effect here
    }
    // Fix: inject self (@Autowired private OrderService self), or extract to separate bean
}

Isolation Levels

Advanced

Isolation controls what a transaction sees when other transactions are running concurrently. Higher isolation = fewer anomalies, but more locking and lower throughput. Most databases default to Read Committed. PostgreSQL's default is also Read Committed; it can do Serializable Snapshot Isolation (SSI) without true locking.

LevelDirty ReadNon-Repeatable ReadPhantom ReadNotes
Read Uncommitted✓ Possible✓ Possible✓ PossibleRarely used. MySQL InnoDB ignores it.
Read Committed✗ Prevented✓ Possible✓ PossibleDefault for most DBs. Safe for most use cases.
Repeatable Read✗ Prevented✗ Prevented✓ Possible (in SQL std)MySQL InnoDB default. Phantom-safe in MySQL via gap locks.
Serializable✗ Prevented✗ Prevented✗ PreventedStrictest. Postgres uses SSI (snapshot, not locking).
Anomaly Definitions
  • Dirty Read: reading uncommitted data from another transaction that may still roll back.
  • Non-Repeatable Read: reading the same row twice in one transaction yields different values because another transaction committed a change in between.
  • Phantom Read: a range query returns different rows on second execution because another transaction inserted/deleted rows matching the predicate.
JAVASetting isolation in Spring @Transactional
// Serializable for financial balance reads — must see consistent snapshot
@Transactional(isolation = Isolation.SERIALIZABLE)
public BigDecimal transferFunds(Long from, Long to, BigDecimal amount) {
    Account src = accountRepo.findById(from).orElseThrow();
    Account dst = accountRepo.findById(to).orElseThrow();
    src.debit(amount);
    dst.credit(amount);
    return src.getBalance();   // guaranteed consistent under Serializable
}

// Note: isolation level is set per-connection; not all databases honor all levels
// PostgreSQL: SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

Optimistic / Pessimistic Locking

Advanced

Optimistic locking assumes conflicts are rare — reads are free, but at write time it checks a version column; if another transaction updated it, it throws OptimisticLockException. Pessimistic locking acquires a database lock immediately on read, blocking other writers — guaranteed consistency at the cost of throughput and deadlock risk.

OptimisticPessimistic
Mechanism@Version column checked at UPDATESELECT FOR UPDATE row lock
ContentionLow — reads don't lockHigh — readers block writers and vice versa
Failure modeOptimisticLockException → retryDeadlock or long wait
Best forInfrequent conflicts, long-running formsGuaranteed consistency, short transactions
JAVAOptimistic lock with @Version + pessimistic lock with LockModeType
// Entity with @Version — Hibernate adds version column to UPDATE WHERE clause
@Entity
public class Inventory {
    @Id private Long productId;
    private int stock;

    @Version
    private Long version;  // Hibernate: UPDATE inventory SET stock=? WHERE id=? AND version=?
}

// Service retries on optimistic conflict
@Retryable(retryFor = OptimisticLockingFailureException.class, maxAttempts = 3)
@Transactional
public void decrementStock(Long productId, int qty) {
    Inventory inv = invRepo.findById(productId).orElseThrow();
    if (inv.getStock() < qty) throw new InsufficientStockException();
    inv.setStock(inv.getStock() - qty);
}   // OptimisticLockException if concurrent update → @Retryable retries

// Pessimistic: SELECT ... FOR UPDATE — holds row lock until TX ends
@Query("SELECT i FROM Inventory i WHERE i.productId = :id")
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Inventory> findByIdForUpdate(@Param("id") Long id);
Performance

Query Optimization

Perf

Query optimization starts with EXPLAIN ANALYZE — never guess. The query planner shows the chosen execution plan, estimated vs actual row counts, index usage, and cost. Most slow queries are either missing an index, hitting a sequential scan on a large table, doing unnecessary work (SELECT *), or suffering from stale planner statistics.

Optimization Checklist
  • SELECT only what you need — avoid SELECT *, especially across JOINs. Use projections/DTOs.
  • Filter early — push WHERE clauses as deep as possible; avoid filtering in application code on full result sets.
  • Avoid functions on indexed columns: WHERE UPPER(email) = ? prevents index use. Use functional indexes or store normalized data.
  • Pagination: use LIMIT/OFFSET carefully — deep offsets scan and discard rows. Keyset pagination (WHERE id > last_seen_id) is O(1) regardless of page depth.
  • Analyze statistics: run ANALYZE (Postgres) or ANALYZE TABLE (MySQL) after bulk loads to refresh planner statistics.
  • Connection-level: use read replicas for reporting queries; don't compete with write traffic.
SQLEXPLAIN ANALYZE + keyset pagination
-- EXPLAIN ANALYZE: run in Postgres to see actual plan
EXPLAIN ANALYZE
SELECT id, customer_id, total
FROM   orders
WHERE  status = 'PENDING'
  AND  created_at > NOW() - INTERVAL '7 days'
ORDER BY created_at DESC;

-- Look for: Seq Scan on large table → missing index
--           Rows Removed by Filter: high → bad predicate selectivity
--           Hash Join vs Index Nested Loop → may need composite index

-- Keyset pagination — O(1) regardless of page depth
SELECT id, customer_id, total
FROM   orders
WHERE  status = 'PENDING'
  AND  id > :lastSeenId        -- cursor, not OFFSET
ORDER BY id
LIMIT  20;

-- OFFSET pagination (avoid for large pages)
SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 500000;
-- ↑ scans and discards 500 000 rows on each request

Indexes

Perf

An index is a separate data structure (typically a B-tree) that lets the database locate rows without a full table scan. Indexes speed up reads but slow down writes (every INSERT/UPDATE/DELETE must update all relevant indexes). A team lead reviews index choices in schema migrations — wrong indexes are as harmful as missing ones.

Index TypeUse Case
B-TreeDefault. Equality and range queries: =, <, >, BETWEEN, LIKE 'prefix%'.
HashEquality only (=). Faster for pure equality, no range support. Postgres only.
GIN / GiSTFull-text search, JSONB containment, arrays, geometric types.
PartialWHERE status = 'ACTIVE' — index only rows matching a predicate. Smaller, faster.
CompositeMulti-column. Column order matters: leftmost prefix rule. Put equality columns first, then range.
CoveringIncludes all columns the query needs — INCLUDE (total). Index-only scan, no heap access.
FunctionalIndex on expression: LOWER(email). Supports case-insensitive lookups.
SQLIndex design patterns
-- Composite index: equality first, range second, covering columns via INCLUDE
CREATE INDEX idx_orders_status_date
    ON orders (status, created_at DESC)
    INCLUDE (customer_id, total);
-- Supports: WHERE status = ? ORDER BY created_at DESC  → index-only scan

-- Partial index: only active orders (smaller, faster writes on archived rows)
CREATE INDEX idx_orders_active_customer
    ON orders (customer_id)
    WHERE status = 'ACTIVE';

-- Functional index for case-insensitive email lookup
CREATE UNIQUE INDEX idx_users_email_lower
    ON users (LOWER(email));

-- CONCURRENTLY: build index without locking table (Postgres)
CREATE INDEX CONCURRENTLY idx_orders_total ON orders (total);

-- JPA / Spring Data: declare in @Table
JAVADeclaring indexes in JPA entity
@Entity
@Table(name = "orders", indexes = {
    @Index(name = "idx_orders_customer_status",
           columnList = "customer_id, status"),
    @Index(name = "idx_orders_created",
           columnList = "created_at DESC")
})
public class Order { ... }
// Generated at schema creation time (ddl-auto=create/update)
// Production: use Flyway/Liquibase migrations instead
Index Anti-Patterns
  • Indexing every column — write amplification, optimizer confusion, wasted disk.
  • Leading wildcard: LIKE '%keyword' cannot use a B-tree index — use full-text search (GIN + tsvector).
  • Low-cardinality column index (e.g., boolean) — planner may prefer a seq scan anyway; partial index is better.
  • Unused indexes: query them via pg_stat_user_indexes; drop what's never scanned — every index costs write throughput.
Performance

Connection Pooling

Perf

A database connection is expensive to create (TCP handshake, auth, session setup — typically 20–100ms). A connection pool pre-creates connections and hands them out to threads, returning them after use. HikariCP is the Spring Boot default and the industry benchmark for throughput and reliability. Misconfigured pool size is a top cause of production connection timeouts.

HikariCP Critical Settings
  • maximumPoolSize: total connections the pool holds. Rule: connections = (core_count * 2) + effective_spindle_count. For Postgres: often 10–20 per app instance.
  • minimumIdle: set equal to maximumPoolSize in production — prevents cold-start latency spikes.
  • connectionTimeout: how long a thread waits for a connection from the pool (default 30s). Set to 3–5s and alert on timeouts.
  • idleTimeout: how long an idle connection lives before eviction (default 10min). Must be less than the database's wait_timeout.
  • maxLifetime: max age of a connection (default 30min). Prevents using connections the DB has already closed. Must be less than DB's connection_timeout.
  • leakDetectionThreshold: logs a warning if a connection is held longer than this (e.g., 5000ms). Set in dev/staging to catch leaks.
YAMLHikariCP production configuration
spring:
  datasource:
    url: jdbc:postgresql://db:5432/orders
    username: ${DB_USER}
    password: ${DB_PASS}
    hikari:
      maximum-pool-size: 20
      minimum-idle: 20         # equal to max in production
      connection-timeout: 3000  # 3s — fail fast, don't queue forever
      idle-timeout: 300000     # 5 min < Postgres wait_timeout
      max-lifetime: 1200000    # 20 min
      leak-detection-threshold: 5000   # dev/staging only
      connection-test-query: "SELECT 1"
      pool-name: OrdersPool
      register-mbeans: true   # expose pool stats via JMX
JAVAMonitoring pool health via Actuator + Micrometer
// HikariCP auto-exports metrics if Micrometer is on classpath:
//   hikaricp.connections.active   — currently in use
//   hikaricp.connections.idle     — available
//   hikaricp.connections.pending  — threads waiting ← alert on this
//   hikaricp.connections.timeout  — total timeout count ← page on this

// Alert rule example (Prometheus):
// ALERT HighConnectionWait
//   IF hikaricp_connections_pending{pool="OrdersPool"} > 5
//   FOR 30s

// Programmatic pool stats
@Autowired DataSource dataSource;

public PoolStats getStats() {
    HikariDataSource hikari = (HikariDataSource) dataSource;
    HikariPoolMXBean pool = hikari.getHikariPoolMXBean();
    return new PoolStats(
        pool.getActiveConnections(),
        pool.getIdleConnections(),
        pool.getThreadsAwaitingConnection()
    );
}
Pool Exhaustion — Common Causes
  • Long-running queries holding connections while the pool is empty — other threads queue, then time out.
  • Connection leak: a code path acquires a connection (opens a transaction) and never releases it — use leakDetectionThreshold to find it.
  • Pool too small for traffic spike — don't over-provision either; the DB has its own max_connections limit (Postgres default: 100).
  • Microservices each with 20 connections × 10 instances × 5 services = 1 000 connections to one DB — use PgBouncer or similar connection proxy to multiplex.
